# Feature Specification: 检索基础设施修正

**Feature Branch**: `dev-from-clean-start`（本 feature 不单开分支，沿用现有分支；调用 speckit 脚本时用 `SPECIFY_FEATURE=004-retrieval-infra-fix` 旁路 `check_feature_branch`）
**Created**: 2026-08-09
**Status**: Draft
**Input**: User description: "检索基础设施修正：修复 BM25 索引与 Chroma 数据 chunk_id 体系不一致（导致混合检索实际退化为纯 dense）、dense/sparse 的 collection 隔离口径不一致、CJK 字符在整条 sparse 链路被丢弃三个缺陷。范围：collection 物理隔离 + 复制式迁移脚本、--collection 语义改为真正切换检索范围、CJK 字符 bigram 切分且 tokenizer 抽为查询端与索引端共享的单一模块、从 Chroma 反向重建 BM25 索引并瘦身索引格式、重标 Feature-001 基线（旧基线保留并重标注为「纯 dense 参照」）。目标语料为现有 mt5_docs_chinese / mt5_docs_english。不做重新 ingest（ingest_source 原始文档已不存在，且 embedding 走 API 有成本）。"

## 背景：三个已确诊的缺陷

本 feature 不是新增能力，而是修复三个已被实测确认的既有缺陷。诊断过程与证据见 [docs/learning/agentic-retrieval-boundary.md § 6.3](../../docs/learning/agentic-retrieval-boundary.md)。

| # | 缺陷 | 实测证据 | 后果 |
|---|---|---|---|
| **D1** | 关键词索引与向量库的 chunk 标识体系不一致 | 抽 200 个关键词索引中的标识去向量库查，命中 **0/200** | 结果融合按标识合并，两边不相交 → **融合从未真正发生**；关键词检索路径取不到内容，返回空 → **混合检索实际是纯向量检索** |
| **D2** | 两路检索的语料集合隔离口径不一致 | 向量侧 52,757 条全在一个物理集合内靠元数据区分；关键词侧按集合分成独立文件。指定集合时向量侧搜全量、关键词侧只搜 5 篇 | 两路语料范围相差 4 个数量级；指定集合的参数是"检索后过滤"而非"缩小检索范围" |
| **D3** | 中文字符在整条关键词链路上被丢弃 | 名为 `mt5_docs_chinese` 的索引含 7,165 词条，**含汉字词条 0 个**；查询端与索引端各有一份只保留 ASCII 的切分逻辑 | 中文语料的关键词检索完全失效，且向融合结果注入 ASCII 噪音 |

**D1 是根因级的**：它使得 D2、D3 在被修复前都无法被验证——因为关键词路径的结果根本进不了最终结果集。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 混合检索真正生效 (Priority: P1)

作为检索服务的调用方，我发起一次查询时，希望关键词匹配和语义匹配两条路径的结果能够被真正合并——同一段内容被两路同时命中时应当获得更高排名，而不是像现在这样两路结果互不相识、关键词路径干脆返回空。

**Why this priority**: 这是本 feature 的根因修复。在它完成前，D2 和 D3 的修复都无法被观测到效果（关键词路径的结果进不了最终结果集）。同时它直接影响一项对外声称的核心能力——项目所有文档、评估报告和对外描述都称本系统提供"混合检索"，而实测表明该能力从未生效。

**Independent Test**: 对同一查询分别记录两路检索返回的内容标识集合，验证交集不再恒为空；并验证关键词路径返回的内容能被成功取回正文。完成此项即可独立交付价值——混合检索从"名义存在"变为"真实生效"。

**Acceptance Scenarios**:

1. **Given** 已完成索引重建，**When** 对英文语料发起一次含明确关键词的查询，**Then** 关键词路径返回非空结果，且其返回的内容标识能在向量库中被成功取回正文
2. **Given** 已完成索引重建，**When** 对同一查询同时执行两路检索，**Then** 存在至少一个被两路同时命中的内容，且它在融合后的排名高于仅被单路命中的内容
3. **Given** 重建过程，**When** 重建执行完毕，**Then** 未发生任何新的向量生成调用（重建仅消费向量库中已有的正文与标识）
4. **Given** 原始文档目录已不存在，**When** 执行重建，**Then** 重建仍能完成（数据来源为向量库自身，不依赖原始文档）

---

### User Story 2 - 中文内容能被关键词检索命中 (Priority: P2)

作为查询中文语料的使用者，我用中文提问时，希望关键词匹配能真正参与检索——现在中文查询的关键词路径提取不出任何中文词，等于只有语义匹配在工作，且还会把文档里夹杂的英文技术术语当作噪音混进结果。

**Why this priority**: 中文语料（21,193 条）占现有内容的四成，且是未来接入中文口语场景的地基。但它排在 P1 之后，因为在 D1 修复前，中文关键词结果即使被提取出来也进不了最终结果集。

**Independent Test**: 检查中文语料的关键词索引中含中文的词条数量，从 0 变为非零；并对中文查询验证关键词路径返回的内容与查询语义相关（而非当前的纯 ASCII 噪音匹配）。

**Acceptance Scenarios**:

1. **Given** 已应用新的切分逻辑并重建索引，**When** 检查中文语料的关键词索引，**Then** 含中文的词条数量占索引词条总数的多数
2. **Given** 已重建，**When** 用中文查询检索中文语料，**Then** 关键词路径返回的内容与查询主题相关，而非仅靠夹杂的英文术语匹配
3. **Given** 查询端与索引端使用同一份切分逻辑，**When** 用某段正文中出现过的中文短语作为查询，**Then** 该正文所在内容能被关键词路径命中（切分口径一致性的直接验证）
4. **Given** 中文文档中夹杂英文技术术语，**When** 用该英文术语查询，**Then** 仍能正常命中（中文支持不以牺牲既有英文能力为代价）

---

### User Story 3 - 评估结论可信且可追溯 (Priority: P3)

作为项目的评估者，我需要知道历史评估数字到底代表什么检索模式，以及修复后的数字相比之前变化了多少——现在归档的所有基线都标称"混合检索"，但实际是纯向量检索，这个标签错误会误导后续所有对比。

**Why this priority**: 不修复它不影响检索本身工作，但会让 P1/P2 的成果无法被正确度量和讲述。同时它顺带产出一组本来就需要的对比数据。

**Independent Test**: 检查归档基线是否带有明确的检索模式标注；检查金标集声明的语料集合与其实际引用内容是否一致；确认修复前后的对比数据可被生成。

**Acceptance Scenarios**:

1. **Given** 既有归档基线，**When** 查看任一历史基线记录，**Then** 能看到明确标注说明该基线实为纯向量检索模式，且原始数字未被删改
2. **Given** 金标集声明的语料集合标识，**When** 与其引用的内容实际所属集合比对，**Then** 两者一致
3. **Given** 修复完成，**When** 在相同金标上重跑评估，**Then** 能生成"纯向量检索 vs 混合检索"的逐指标对比
4. **Given** 修复后的评估结果，**When** 按问题难度分组统计检索召回，**Then** 能得出多跳类问题与简单问题的召回差距，作为后续是否投入检索规划能力的判断依据

---

### Edge Cases

- **正文为空的内容**：向量库中若存在正文缺失的条目，重建时如何处理？（应跳过并计入报告，不应中断重建）
- **重建中断**：重建过程中途失败，是否会留下半成品索引覆盖掉可用的旧索引？（新索引应先写临时位置，完整后再替换）
- **单字中文查询**：固定二字组合的切分策略对单个汉字的查询无法产生词条，此类查询的关键词路径将无结果（应确认降级到语义路径后行为可接受）
- **中英混排文本**：中文文档中夹杂大量英文技术术语，两种切分需并存且互不干扰
- **无归属残留数据**：向量库中存在 10 条来自临时文件、无法归属到任何语料集合的条目，需被识别并单独列出
- **迁移期间磁盘空间**：复制式迁移会临时占用双份空间
- **集合标识冲突**：同一内容标识若在多个集合的元数据中出现，归属如何判定
- **切分策略变更后的索引兼容**：旧格式索引文件与新格式共存时如何避免误加载

## Requirements *(mandatory)*

### Functional Requirements

**标识一致性（对应 D1）**

- **FR-001**: 关键词索引中的内容标识 MUST 与向量库中的内容标识来自同一体系，使两路检索结果可被正确识别为同一内容
- **FR-002**: 系统 MUST 支持从向量库现有内容重建关键词索引，该过程不依赖原始文档文件、不产生任何新的向量生成调用
- **FR-003**: 重建 MUST 先产出完整结果再替换现有索引，中途失败不得破坏当前可用的索引

**集合隔离（对应 D2）**

- **FR-004**: 每个语料集合 MUST 在向量存储与关键词索引两侧都拥有独立且相互对应的存储范围
- **FR-005**: 指定语料集合执行检索时，两路检索 MUST 都将检索范围限制在该集合内，而非在全量检索后过滤结果
- **FR-006**: 集合迁移 MUST 采用复制方式，原有数据在人工确认前保持完整可用
- **FR-007**: 无法归属到任何语料集合的残留数据 MUST 被识别并单独列出，删除前需要人工确认

**中文支持（对应 D3）**

- **FR-008**: 中文字符 MUST 能进入关键词索引，并能被中文查询命中
- **FR-009**: 查询端与索引端的切分逻辑 MUST 来自同一份实现，不允许各自维护副本
- **FR-010**: 新增中文支持 MUST NOT 削弱既有的英文/ASCII 术语匹配能力

**可追溯与验收**

- **FR-011**: 既有评估基线 MUST 被保留且原始数字不被修改，同时标注其真实的检索模式
- **FR-012**: 金标集声明的语料集合标识 MUST 与其实际引用内容所属的集合一致
- **FR-013**: 重建 MUST 输出可供验收核对的统计报告，至少包含每个集合的索引词条数、覆盖内容数、含中文词条占比、跳过条目数
- **FR-014**: 关键词索引的存储格式 MUST 避免同一信息的冗余重复存储

### Key Entities

- **语料集合（Collection）**：一批同源内容的逻辑与物理归属单位。当前有 `mt5_docs_chinese`、`mt5_docs_english`、`finpoints_handbook`、`default` 四个逻辑值，但物理布局与之不符——这正是 D2 要修复的
- **内容标识（Chunk 标识）**：切分后每段内容的唯一标识，是两路检索结果得以合并的唯一依据。当前存在两套互不相交的体系——这是 D1 的本质
- **关键词索引**：词条到内容的倒排映射，附带排序所需的统计量。当前存在三份，均与向量库不同源
- **切分逻辑（Tokenizer）**：把文本转为词条的规则。当前查询端与索引端各有一份独立实现，是口径漂移的温床
- **评估基线**：某次评估结果的归档快照，用于后续对比。当前缺少"该次评估实际使用何种检索模式"的标注

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对同一查询，两路检索结果的内容标识重合数量 > 0（当前恒为 0）
- **SC-002**: 对中英文金标各条查询，关键词检索路径返回非空结果，且其中至少一条命中该查询的金标期望内容（当前中文返回 ASCII 噪音、英文因标识不一致被整体丢弃，命中率恒为 0）
- **SC-003**: 中文语料的关键词索引中，含中文的词条占词条总数的比例 > 50%（当前为 0%）
- **SC-004**: 指定语料集合检索时，返回结果 100% 属于该集合
- **SC-005**: 整个修复过程产生的新增向量生成调用次数为 0
- **SC-006**: 修复后在中文金标上重跑评估，8 项主聚合指标无一项低于修复前
- **SC-007**: 迁移完成后，原有数据仍可完整回滚，不存在不可逆删除
- **SC-008**: 能产出一份"纯向量检索 vs 混合检索"的逐指标对比，覆盖中英文两套金标
- **SC-009**: 能给出英文金标中多跳类问题（multi_context + reasoning，20 条）与简单问题（simple，22 条）的检索召回差距数值，作为后续决策依据
- **SC-010**: 重建产出的统计报告可让验收者在不读代码的情况下确认 SC-002/SC-003/SC-004 是否达成
- **SC-011**: 尽管索引覆盖的词条数量因中文支持而大幅增加，检索服务的启动耗时不超过修复前的 2 倍（验证 FR-014 的存储瘦身确实抵消了词条增长带来的膨胀）

## Assumptions

**关于范围**

- 目标语料限定为现有的 `mt5_docs_chinese` 与 `mt5_docs_english`；门店知识库接入不在本次范围（用户已明确"先用现有的 RAG 知识库"）
- 不新增检索能力（查询改写、检索规划均不在本 feature），本 feature 只做既有能力的修复
- 不做重新 ingest：`ingest_source/` 原始文档目录已不存在，且向量生成走 API 有实际成本

**关于数据现状**

- 向量库中的内容是可信的：实测 52,580 条（99.4%）为金标引用的同一批次，329 条为 finpoints，仅 10 条为临时文件残留
- 向量库同时持有内容正文与标识，因此反向重建关键词索引在数据上是可行的
- 磁盘空间充足（可用 63GB，现有数据 626MB），复制式迁移的空间成本可忽略

**关于技术选择**（详细论证移交 plan 阶段）

- 中文切分采用固定长度字符组合策略而非词典分词：目标语料是技术文档，含大量专有名词（现有索引中有 7,165 个 ASCII 术语词条），词典分词对未登录词切分效果差，且会引入新依赖
- 现有的最小词条长度约束（2）与固定二字组合天然兼容，无需额外调整
- 索引格式变更不需要向后兼容旧格式：本次为全量重建，旧索引整体作废

**关于验收口径**

- 中文金标目前仅 6 条且全为 simple 难度，样本量不支持量化提升幅度的承诺，因此中文侧验收为**二元性质**（关键词路径从"完全失效"到"生效且相关"），不承诺具体提升百分比
- 英文金标 42 条（22 simple / 9 multi_context / 11 reasoning）是唯一可用于难度分组分析的样本
- 金标的期望内容标识为固定 5 条、由脚本按 top-5 回填而非人工标注，这会削弱召回类指标的判别力，解读 SC-009 结果时需计入此折扣

**关于配置默认值**

- 迁移后主配置指向的默认集合改为英文语料集合（金标 42 条的主力样本所在）；切换到中文语料通过配置或参数完成

## Dependencies

- 依赖向量库中现存的内容正文与标识完整可读
- 依赖 Feature-001 既有的评估体系（8 项指标 + 基线归档 + delta 对比）用于验收，本 feature 不新建评估能力
- 本 feature 的产出是后续「查询改写」与「检索规划」两个 feature 的前提——在混合检索真正生效前，任何检索改进的消融实验都不可信

## Out of Scope

- 查询改写（Multi-Query / HyDE / 策略路由）
- 检索规划器与证据充分性自查
- 细粒度检索工具的对外暴露
- 门店知识库语料的接入与 `KnowledgeSearchPort` 适配器
- 带权重的结果融合（是后续查询改写 feature 的前置，不在本次）
- 延迟分位数统计能力
- 中文金标集的扩充
