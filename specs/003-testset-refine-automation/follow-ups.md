# Feature-003 遗留与后续候选

**记录日期**: 2026-08-08(T018 实测期间)

本文件记录 Feature-003 实测中发现、但**超出本 feature 范围**的问题。按宪法 [Rule VIII](../../.specify/memory/constitution.md),这些需各自走 SDD 流程,不得直接塞进本 feature。

---

## F-1(高)zh 金标合成产出英文问题

**现象**:`tests/fixtures/candidates/zh.json` 中 **40/47 条 query 是纯英文**,而语料与 `tags.language` 均为中文。

**根因**(已记录于 `config/settings.yaml`):

> 2026-04-28 已知限制:minimax 无法完成 RAGAS adapt(中文 prompt 翻译需返 valid JSON),中文金标合成被 deferred。en 不受影响。

**影响**:该金标评估的是「英文问题 → 中文语料」的跨语言检索,不代表实际使用场景。用它跑出的 zh 指标不能反映真实质量。

**为何不在 Feature-003 修**:精修阶段的职责是筛选与确认,不是重写问题。机器翻译 40 条会让金标来源既非合成产出、也非人工撰写,不可追溯,且会掩盖上游问题。

**建议**:换一个能完成 RAGAS adapt 的合成端模型后重新合成 zh 候选。

## F-2(中)预筛的结构缺陷检测应下沉为确定性规则

**现象**:合成模型会把脚手架(`**Question:**`、`Based on the given context…`)甚至答案原文写进 `query` 字段。早期提示词下预筛完全漏检,对一条含 374 字符答案泄漏的用例仍判 keep。

**已做的缓解**:提示词新增「判据 1:QUESTION 必须只含问题本身」,实测 6/6 逮到。见 commit `e4acbe7`。

**仍建议下沉**:这类缺陷有确定性特征(正则可判),在调 LLM **之前**先跑一遍更可靠也更省:

- 100% 可复现,不受模型能力与版本波动影响
- 命中即可直接判 drop,省掉一次 API 调用
- 可作为提示词判据的兜底,双保险

**可复用的检测规则**(实测有效,见 T018 记录):

| 类型 | 特征 |
|---|---|
| 脚手架残留 | `**Question:**` / `**Answer:**` / `Based on the given context` / `here is a question` |
| 前缀残留 | 以 `question:` / `Q:` / `问题:` 开头 |
| 答案泄漏 | ground_truth 中 ≥40 字符的片段原样出现在 query |
| 形态异常 | query 含换行,或长度 > 150 字符 |
| 生造缩写 | query 中的全大写缩写未出现在 contexts 中 |

## F-3(低)`_review_metadata` 未记录预筛提示词版本

**现象**:审计记录含模型标识与阈值快照,但不含提示词版本。提示词一改(如本次新增判据 1),同一模型同一阈值也会给出不同判定,历史金标无法据审计字段还原当时的判定条件。

**建议**:在 `thresholds_snapshot` 旁增记提示词内容的 hash。改动很小,但要动 data-model 与 contracts,故仍走 SDD。

---

## F-4(低)自动化与人工精修的质量差距需要长期监测

**现象**:实测显示 Feature-001 的 100% 人工精修产出 `golden_test_set_en.json` 仅 1/42 有缺陷,而合成候选是 ~13/48。auto 模式在 F-2 修复前会放过其中一类。

**建议**:把「用确定性扫描器体检金标」纳入常规流程,而不只在出问题时才做。这既能量化 auto 模式的质量,也能在换预筛模型后立刻发现能力退化。
