# Feature Specification: 金标精修自动化(异源预筛 + borderline 路由)

**Feature Branch**: `dev-from-clean-start`(本 feature 不单开分支,沿用活跃分支)
**Created**: 2026-08-04
**Status**: Draft
**Input**: User description: "把 scripts/refine_testset.py 从 100% 逐条人工 prompt 改造成「异源 LLM 预筛 + borderline 路由 + 审计元数据落盘」"

## 背景

Feature-001 的 `SC-002` 原文要求:

> 中英金标集合各 ≥ 40 条用例,且**对每份金标集随机抽样 10% 用例做人工 review**,结构合规率(question 通顺 + ground_truth 可在原始语料中验证 + expected_chunk_ids 指向真实存在的 chunk)**≥ 90%**。

即质量门控的设计是「抽样 + 合规率阈值」。但当前 `scripts/refine_testset.py` 实现为**逐条 100% 人工确认**(每条 case 都要点 y/e/d/s/q),与 SC-002 的抽样意图不符,且实测 zh 47 / en 48 条用例需 30-60 分钟/语种,是 US2 金标制作的主要瓶颈。

本 feature 把「人工逐条」替换为「机器预筛 + 人工只看疑难 + 抽样合规自检」,在满足 SC-002 的前提下把耗时压到可接受范围。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 预筛后只人工处理疑难用例 (Priority: P1)

金标制作者拿到合成阶段产出的 candidate 文件后,启动自动精修模式。系统先请一个**与合成端不同来源**的评审模型逐条给出「保留 / 丢弃 / 存疑」判断及置信度;高置信度的保留与丢弃直接自动决策,只有「存疑」用例才停下来请人判断。制作者因此只需处理一小部分用例,而不是全部。

**Why this priority**: 这是本 feature 的核心价值,直接解决 30-60 分钟的瓶颈。单独交付这一条即可让金标制作时间大幅下降,构成可用的 MVP。

**Independent Test**: 准备一份含明显优质、明显劣质、以及模糊用例的 candidate 文件,以自动模式运行,验证仅模糊用例触发人工提示,且最终产出的金标文件包含预期保留的用例。

**Acceptance Scenarios**:

1. **Given** 一份 candidate 含 10 条用例、评审模型判定 7 条高置信保留 / 1 条高置信丢弃 / 2 条存疑,**When** 以自动模式运行,**Then** 系统只对那 2 条存疑用例请求人工输入,最终金标含 7 条自动保留用例加上人工处置结果。
2. **Given** 同一份 candidate,**When** 不带自动模式运行(默认),**Then** 行为与现状完全一致——逐条请求人工确认,不调用评审模型。
3. **Given** 评审模型对某条用例调用失败或返回无法解析的结果,**When** 以自动模式运行,**Then** 该用例被归入「存疑」交由人工处置,不被静默丢弃。
4. **Given** 配置的评审模型与合成端模型同源,**When** 启动自动模式,**Then** 系统拒绝以自动模式继续并说明原因(异源是本 feature 的前提)。

---

### User Story 2 - 金标自带可追溯的审计记录 (Priority: P2)

金标制作者或后续复核者打开产出的金标文件,能直接看到这份金标是怎么来的:多少条由机器自动决策、多少条经人工处置、丢弃多少条,以及预筛用的是哪个模型、判定阈值是多少。无需翻日志或回忆当时的操作。

**Why this priority**: SC-002 是一条审计要求,「机器参与了决策」这件事必须留痕,否则金标质量无从复核。但即使没有这一条,US1 已能交付效率收益,故列 P2。

**Independent Test**: 以自动模式跑完一份 candidate,检查产出金标文件中的审计字段是否完整记录了各路径计数、评审模型标识与阈值,且数字与实际运行过程一致。

**Acceptance Scenarios**:

1. **Given** 一次自动模式运行中 7 条自动保留、2 条人工处置、1 条丢弃,**When** 精修完成,**Then** 金标文件的审计字段如实记录这三个数字且其合计等于输入用例总数。
2. **Given** 任意一次运行,**When** 精修完成,**Then** 审计字段包含评审模型标识与判定阈值快照,使得换模型后的历史金标仍可追溯当时的判定条件。
3. **Given** 用户中途中断,**When** 进度被保存,**Then** 审计字段标明这是部分结果,避免被误当作完整金标使用。

---

### User Story 3 - 抽样合规自检作为质量门控 (Priority: P3)

金标制作者在精修收尾时,系统按 SC-002 的要求随机抽取 10% 的保留用例请其确认结构合规性,当场算出合规率并记入审计字段。合规率低于阈值时明确告警,提示这份金标不该直接用于验收。

**Why this priority**: 把 SC-002 的门控从「事后另找时间人工抽查」变成流程内的一步。依赖 US1/US2 已就位,故列 P3。

**Independent Test**: 以自动模式跑一份含 20 条保留用例的 candidate,验证系统抽取 2 条请求确认、正确计算合规率、并在低于阈值时给出告警。

**Acceptance Scenarios**:

1. **Given** 精修产出 20 条保留用例,**When** 进入抽样自检,**Then** 系统随机抽取 2 条(10%)请求人工确认结构合规性。
2. **Given** 抽样中 2 条全部合规,**When** 自检完成,**Then** 记录合规率 100%,不告警。
3. **Given** 抽样中仅 1 条合规(合规率 50%,低于 90% 阈值),**When** 自检完成,**Then** 系统明确告警说明未达 SC-002 门控。
4. **Given** 保留用例少于 10 条(10% 不足 1 条),**When** 进入抽样自检,**Then** 系统至少抽取 1 条,不跳过自检。

---

### Edge Cases

- **评审模型无区分力**:若绝大多数用例(例如 > 80%)都被判为「存疑」,自动模式实际退化为全人工。系统应告警提示预筛未产生效益,让使用者去调阈值或换模型,而不是让人白等。
- **无法确认异源**:candidate 文件缺少合成端模型信息时,系统无法验证异源前提,应告警并要求使用者显式确认后才继续。
- **评审模型整体不可用**:评审模型完全无法访问(如网络中断、凭据失效)时,应明确失败并提示改用默认全交互模式,而不是把全部用例默默判为存疑后仍宣称「自动完成」。
- **用户中断**:自动模式下人工处置存疑用例期间中断,已完成的决策须保留(与现状一致),且审计字段标明为部分结果。
- **空输入**:candidate 不含任何用例时,不调用评审模型,直接产出空金标并说明。
- **重复运行**:对同一份 candidate 重复运行时,不应因随机抽样的偶然性导致既有金标被静默覆盖成质量更差的版本;覆盖行为须与现状一致或更保守。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 为每条候选用例产出「保留 / 丢弃 / 存疑」三态判定,并附带一个可比较的置信度。
- **FR-002**: 系统 MUST 使用与合成端不同来源的评审模型;当检测到两者同源时,MUST 拒绝以自动模式继续并说明原因。
- **FR-003**: 在自动模式下,系统 MUST 仅对「存疑」用例请求人工输入;高置信度的保留与丢弃 MUST 自动决策。
- **FR-004**: 系统 MUST 保持现有默认行为不变——不启用自动模式时,逐条请求人工确认且不调用评审模型,既有命令行契约与既有测试 MUST 继续通过。
- **FR-005**: 系统 MUST 在产出的金标文件中写入审计记录,至少包含:自动决策数、人工处置数、丢弃数、评审模型标识、判定阈值快照,以及该结果是否为中断产生的部分结果。
- **FR-006**: 系统 MUST 支持对保留用例随机抽样 10%(不足 1 条时取 1 条)请求人工确认结构合规性,计算合规率并记入审计记录。
- **FR-007**: 当抽样合规率低于 90%(Feature-001 SC-002 的门控值,阈值本身由配置驱动)时,系统 MUST 明确告警,说明该金标未达质量门控。告警为提示性质,不阻止文件写出——是否升级为硬失败留待后续按需决定。
- **FR-008**: 评审模型调用失败或返回无法解析的结果时,系统 MUST 将该用例归入「存疑」交由人工处置,MUST NOT 静默丢弃或静默保留。
- **FR-009**: 评审模型的选择 MUST 由配置驱动,MUST NOT 在代码中硬编码具体模型或厂商。
- **FR-010**: 系统 MUST 保留现有的中断保存能力——中断时已完成的决策不丢失。
- **FR-011**: 当「存疑」用例占比超过配置上限(默认 40%,即显著偏离 10-20% 预期区间)时,系统 MUST 告警提示预筛未产生预期效益。

### Key Entities

- **候选用例(Candidate Case)**:合成阶段产出的单条待评审用例,含问题、参考答案与预期命中片段标识。
- **预筛判定(Screening Verdict)**:针对一条候选用例的机器判断,含三态结论、置信度与判断理由。理由用于人工处置存疑用例时提供上下文。
- **审计记录(Review Metadata)**:附着在金标文件上的一组事实,描述这份金标的产生过程——各决策路径计数、评审模型标识、阈值快照、抽样合规率、是否为部分结果。
- **抽样自检结果(Compliance Sample)**:被抽中的用例集合及逐条合规判断,连同汇总合规率。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 单语种金标精修的人工耗时从 30-60 分钟降至 ≤ 15 分钟(含抽样自检)。
- **SC-002**: 在自动模式下,需要人工处置的用例占比 ≤ 25%(存疑用例 + 抽样自检用例)。
- **SC-003**: 抽样合规率 ≥ 90%,即继承并满足 Feature-001 SC-002 的质量门控。
- **SC-004**: 默认全交互模式的行为零变化——Feature-001 既有的精修相关测试全部继续通过,无需修改断言。
- **SC-005**: 任意一份自动模式产出的金标,仅凭文件自身即可回答「多少条由机器决定、用的哪个评审模型、当时阈值多少、抽样合规率多少」,无需外部日志。
- **SC-006**: 机器自动保留的用例中,经抽样人工复核判定不合规的比例 ≤ 10%,即自动决策的准确性可被量化验证。

## Assumptions

- **抽样对象为全部保留用例**:SC-002 原文是「对每份金标集随机抽样 10%」,故抽样池为最终保留的全部用例,而非仅机器自动决策的部分。这样自检结果与 SC-002 可直接对齐。
- **合规判定沿用 SC-002 的三项结构标准**:question 通顺、ground_truth 可在原始语料中验证、expected_chunk_ids 指向真实存在的 chunk。本 feature 不新增或改动合规定义。
- **存疑比例预期 10-20%**:据此设定 FR-011 的告警上限。实际分布需在首轮真实运行后校准,阈值本身由配置控制而非写死。
- **置信度阈值需要校准**:不同评审模型的置信度标度不可直接互换。切换评审模型后阈值须重新校准,这与 Feature-001 已确立的「换 Judge 后阈值失效」结论一致;阈值快照因此必须落盘(FR-005)。
- **评审成本可接受**:预筛需对每条用例调用一次评审模型(约 50 条/语种)。相对于节省的 30-45 分钟人工时间,该成本视为可接受,不在本 feature 内做批量或缓存优化。
- **沿用既有可插拔模型工厂**:评审模型通过项目已有的模型工厂与配置体系接入,本 feature 不引入新的模型接入机制。
- **不做界面**:本 feature 只覆盖命令行流程,不含面板界面改动。
- **依赖 Feature-001 产出**:输入格式为 Feature-001 合成阶段产出的 candidate 文件;若该格式变化,本 feature 需同步调整。

## Out of Scope

- 改动合成阶段(candidate 的生成逻辑与提示词)。
- 重新定义 SC-002 的合规标准。
- 面板/界面形式的精修入口。
- 预筛结果的缓存、批量并发或成本优化。
- 自动修正用例内容(本 feature 只做保留/丢弃/存疑分流,不让机器改写用例)。
