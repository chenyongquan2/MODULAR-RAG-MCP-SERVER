## 1. 检索路径（Route）

一条独立的召回通道。本 feature 让每条路径获得一个可配置的分量。

**本 feature 不为它引入新的 Python 类型** —— 路径在代码中就是映射里的一个键（`str`）。此处定义的是它的**标识约定**，因为标识的稳定性正是 FR-002 的全部依据。

| 路径键 | 对应实现 | 语义 |
|---|---|---|
| `dense` | `DenseRetriever`（向量相似度） | 语义匹配 |
| `sparse` | `SparseRetriever`（BM25） | 关键词匹配 |

### 校验规则

| 规则 | 说明 |
|---|---|
| 路径键是权重查找的唯一依据 | **不得**按传入顺序对应 —— 见下方「为什么」 |
| 配置中缺失的路径键 | 缺省权重 `1.0`，不报错。新增检索路径时不应强制所有部署同步改配置 |
| 配置中多余的路径键 | 忽略并记录警告 —— 可能是笔误（如 `spare`），但不足以拒绝启动 |

### 为什么标识必须稳定、而顺序不可信

代码中已存在一处**顺序写反的注释**：

```python
# src/core/query_engine/fusion.py:87
# 这里的result_lists=[sparse_result, dense_result]，...
```

而实际调用相反：

```python
# src/core/query_engine/hybrid_search.py:204
self._fusion.fuse([dense_results, sparse_results], ...)
```

等权时这个错误**完全无害**，所以它一直存活至今。加权重后，同样的混淆会让语义路径拿到关键词路径的权重 —— 而系统照常运行、不报错、只是效果悄悄变差。

**这是本 feature 最危险的失败模式，也是把入参从位置列表改为命名映射的全部理由。**

## 2. 路径权重（Weight）

非负实数，表示该路径在融合中的相对分量。

### 关键性质：只有相对比例有意义

`{dense: 1.0, sparse: 0.5}` 与 `{dense: 2.0, sparse: 1.0}` 产出**完全相同的排序** —— 所有得分等比缩放，而排序对单调变换不变。

两个推论：

- 校准只需扫一个自由度（固定 `dense=1.0`，扫 `sparse`），二维网格是冗余的
- 文档与报告中应写比值（如 `dense:sparse = 1:0.25`），不应让读者误以为绝对值有意义

### 校验规则（启动期，宪法原则三）

| 规则 | 违反时 |
|---|---|
| 每个权重 ≥ 0 | 抛 `SettingsError`，指明字段名 |
| 权重必须是数值 | 抛 `SettingsError` |
| **不得全部为 0** | 抛 `SettingsError` —— 否则所有得分归零，排序退化为字典序，且**不会有任何报错** |
| 单条路径权重为 0 | **合法**。等价于关闭该路，是 SC-005 的直接测试手段 |

## 3. 融合平滑参数（`rrf_k`）

控制排名靠后结果衰减速度的常数。当前硬编码为 `Fusion.DEFAULT_K = 60`，本 feature 纳入配置。

| 属性 | 值 |
|---|---|
| 默认值 | `60`（保持当前硬编码值，确保升级后行为不变） |
| 约束 | 正整数 |
| 违反时 | 抛 `SettingsError` |

**为什么 `k ≤ 0` 必须拒绝**：`k=0` 时第 1 名得分 `1/1`、第 2 名 `1/2`、第 3 名 `1/3` —— 衰减过陡，第 1 名的分量几乎压过其后全部结果之和，融合退化为"谁排第一谁赢"，失去平滑意义。负数则会让分母可能为 0 或负，得分符号翻转。

## 4. 融合得分公式

### 变更前后

```
变更前：score(c) = Σ_routes  1 / (k + rank_r(c))
变更后：score(c) = Σ_routes  w_r / (k + rank_r(c))
```

其中 `rank_r(c)` 是内容 `c` 在路径 `r` 结果中的名次（从 1 起）；未被路径 `r` 命中的内容，该项不计入。

### 不变量

| 不变量 | 说明 |
|---|---|
| 全部 `w_r` 相等时，排序与变更前逐条一致 | FR-003 / SC-006 的数学依据：等权时新公式是旧公式的常数倍，排序不变 |
| 某路为空时，其余路的相对排序不变 | 空路贡献 0，加法不受影响（FR-004 / SC-013）。**靠不引入动态归一化来满足，而非新增代码** |
| 交换路径的传入顺序，输出逐条不变 | FR-002 / SC-012。权重按键查找，与顺序无关 |
| `w_r = 0` 时路径 `r` 不影响任何结果 | SC-005。该路的贡献恒为 0 |

### 刻意不做的事

**不按有效路数动态归一化权重。** 若某路为空就把权重重新分配给剩余路径，会：

- 让同一内容的绝对得分随「另一路是否恰好为空」跳变，跨查询不可比
- **不改变任何可观测排序**（等比缩放是单调变换）
- 引入一个只在边界触发、且无可观测收益的分支

详见 [research.md](./research.md) Decision 4。需要测试守住它不被后人"优化"进来。

## 5. 校准缓存（Calibration Cache）

校准的中间产物，也是校准记录的可复现依据。

### 为什么需要它

权重**只影响融合，不影响检索**。两路各自的召回结果与权重完全无关，因此可以「检索一次、重放多次」：

| | 检索次数 | embedding API 调用 |
|---|---|---|
| 朴素扫描（8 组权重 × 48 条金标） | 384 | 384 |
| 缓存重放 | **48** | **48** |

Feature-004 期间反复遭遇网关 503 与超时，长批量任务极易夭折 —— 把 API 调用集中在第一步且只做一遍，是让校准能跑完的前提。

### 结构

| 字段 | 说明 |
|---|---|
| `collection` | 缓存产出时生效的语料集合，重放前须核对一致 |
| `created_at` | 产出时间 |
| `cases[]` | 每条金标一项 |
| `cases[].query` | 查询文本 |
| `cases[].expected_chunk_ids` | 金标期望标识（用于算指标） |
| `cases[].difficulty` | 难度标签（用于分组分析） |
| `cases[].routes` | 路径键 → 该路返回的**有序**标识列表 |

### 不变量

- `routes` 中每条列表**保持检索返回的原始顺序** —— 名次就是信息，重排即破坏
- 缓存与 `collection` 绑定；换集合后旧缓存作废（重放前须校验，不匹配即报错而非静默重放）

## 6. 三方对比结果（Comparison）

US3 的交付物。对同一批金标，在三种配置下的逐指标对比。

| 配置 | 权重 | 含义 |
|---|---|---|
| 纯语义 | `{dense: 1.0, sparse: 0}` | 对照组下界 |
| 等权混合 | `{dense: 1.0, sparse: 1.0}` | 本 feature 之前的行为 |
| 带权混合 | 校准选出的推荐值 | 本 feature 的产物 |

指标覆盖：`hit_rate` / `recall` / `MRR` / `nDCG`，中英文两套金标各一份。

**三种配置全部由同一份缓存重放得出**，因此三者之间不存在检索层面的随机差异 —— 差异纯粹来自融合权重，这正是对照实验想要的干净。

## 7. 复用而不改动的既有类型

| 类型 | 位置 | 角色 |
|---|---|---|
| `RetrievalResult` | `src/core/types.py` | 融合的输入与输出元素，字段不变 |
| `RetrievalSettings` | `src/core/settings.py` | 新增两个字段，既有字段不动 |
