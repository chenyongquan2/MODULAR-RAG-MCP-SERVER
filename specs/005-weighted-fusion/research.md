# Phase 0 Research: 带权重的结果融合

**Feature**: 005-weighted-fusion
**Date**: 2026-08-10
**Input**: [spec.md](./spec.md)

---

## Decision 1：权重以「乘在整个 RRF 项上」的形式引入

**Decision**：融合得分改为 `Σ_routes weight_r / (k + rank_r)`，即权重乘在该路的整个倒数项上。

**Rationale**：

- 这是加权 RRF 的标准形式，语义直白：权重 = 该路每个名次贡献的分量倍数
- 保持 RRF 的核心优点 —— **只依赖排名、不依赖原始分数**。语义相似度与 BM25 分数的量纲完全不同（前者 0~1、后者可到几十），基于排名规避了归一化难题
- 权重为 0 时该路彻底不贡献，等价于关闭该路（SC-005 直接可测）
- 权重全相等时退化为原公式，逐条结果不变（FR-003 / SC-006）

**Alternatives considered**：

- *`1 / (k + rank/weight)`*：权重改为影响排名衰减速度。语义更绕（"权重高 = 名次显得更靠前"），且 weight=0 时除零，边界处理难看
- *分数归一化后线性组合*：spec 的 Out of Scope 已排除。它要求两路分数可比，而这正是 RRF 当初被选用的原因所在
- *按路数动态归一化权重*（`w / Σw`）：**刻意不做**。见 Decision 4

## Decision 2：接口从「位置列表」改为「命名映射」

**Decision**：`fuse()` 的入参从 `List[List[RetrievalResult]]` 改为按路径名索引的映射，权重按**名字**查找，与传入顺序完全无关。

**Rationale**：这是 FR-002 的落地方式，而它的必要性有一个现成的反面例证 —— **代码里已经存在一处顺序错误的注释**：

```python
# src/core/query_engine/fusion.py:87
# 这里的result_lists=[sparse_result, dense_result]，...
```

而实际调用是：

```python
# src/core/query_engine/hybrid_search.py:204
fused_results = self._fusion.fuse([dense_results, sparse_results], ...)
```

**注释把两路顺序写反了。** 在等权时这个错误完全无害，所以它一直没被发现。一旦引入权重，同样的混淆就会让 dense 拿到 sparse 的权重 —— **而系统照常运行、不报错，只是效果悄悄变差**。

这正是 spec 把「权重与路径错配」列为最危险失败模式的原因，也是 SC-012（交换传入顺序，输出必须逐条不变）的由来。

**影响面可控**：生产调用点只有 `hybrid_search.py:204` 一处，加 `tests/unit/test_fusion_rrf.py` 的 9 个用例与一处 docstring 示例。

**Alternatives considered**：

- *保留位置列表 + 平行权重列表*：仍靠下标对应，没有解决问题，只是把错配的机会从一处变成两处
- *`(name, results)` 元组列表*：等价可行，但映射形态在调用侧更难写错

## Decision 3：权重与平滑参数纳入配置，扁平放在 `retrieval` 段

**Decision**：

```yaml
retrieval:
  fusion_algorithm: rrf
  rrf_k: 60                 # 此前硬编码在 Fusion.DEFAULT_K
  fusion_weights:
    dense: 1.0
    sparse: 1.0
```

**Rationale**：

- **修掉一处既有的配置驱动违规**：`Fusion()` 在 `hybrid_search.py:91` 不带参数构造，`DEFAULT_K = 60` 硬编码，`retrieval` 配置段没有对应字段。宪法原则二要求「所有可调参数有对应 dataclass 字段」
- 扁平结构与 `retrieval` 段现有风格一致（`sparse_backend` / `top_k_dense` / `top_k_final` 都是扁平的），不为一个 feature 引入嵌套层级
- `fusion_weights` 用映射而非固定两字段，可容纳未来第三条检索路径（spec Edge Cases 已预见）
- 默认值保持 `1.0 / 1.0` 与 `k=60`，确保既有部署升级后行为逐条不变（FR-003）

**校验**（宪法原则三，启动期快速失败）：

| 非法输入 | 处理 |
|---|---|
| 负权重 | 抛 `SettingsError`，指明字段名 |
| 权重全为 0 | 抛 `SettingsError` —— 否则所有得分归零，排序完全随机 |
| 非数值 | 抛 `SettingsError` |
| `rrf_k` ≤ 0 | 抛 `SettingsError` —— `k=0` 会让第 1 名得分为 `1/1`、第 2 名 `1/2`，衰减过陡失去平滑意义 |
| 权重映射缺某条路 | **缺省为 1.0**，不报错。理由：新增检索路径时不应强制所有部署同步改配置 |

## Decision 4：不做「按有效路数动态归一化」

**Decision**：权重按配置原样使用，**不**在某路返回空时把权重重新归一化到剩余路径。

**Rationale**：这条是针对 FR-004 的，结论有点反直觉 —— **什么都不做恰恰是正确的**。

RRF 是各路得分相加。某路为空时它贡献 0，另一路的得分完全不受影响，相对排序天然保持（FR-004 自动满足）。

如果反过来做动态归一化（例如两路配 `1.0/0.5`，sparse 空时把 dense 提到 `1.0/1.0`），后果是：

- 排序**仍然不变**（等比缩放是单调变换，不改变顺序）
- 但同一 chunk 的绝对得分会随「另一路是否恰好为空」而跳变，让跨查询的得分不可比
- 引入一个只在边界触发、且不改变可观测排序的分支 —— 纯粹是复杂度，没有收益

**因此这条要求靠「不引入某段逻辑」来满足，而非靠新增代码。** 需要一条测试守住它不被后人"优化"进来（SC-013）。

## Decision 5：校准用「一次检索、多次离线融合」

**Decision**：校准时对每个查询**只执行一次**两路检索，把两路的排名列表缓存下来；权重扫描纯粹在缓存上重放融合。

**Rationale**：这是让校准可行的关键 —— 权重**只影响融合，不影响检索**。两路各自的召回结果与权重无关。

若不这样做，扫 8 组权重 × 48 条金标 = 384 次检索，每次含一次 embedding API 调用；而 Feature-004 期间已经反复遇到网关 503 与超时，长批量任务极易中途夭折。

采用缓存重放后：

| | 检索次数 | API 调用 |
|---|---|---|
| 朴素扫描（8 组权重） | 384 | 384 |
| 缓存重放 | **48** | **48** |

且离线重放是纯计算，可秒级完成，天然可复现（FR-010）—— 同一份缓存重跑必得同一结论。

**附带好处**：缓存文件本身就是校准记录的一部分，第三方拿到它即可复算，无需访问 API。

## Decision 6：校准的搜索范围与选择判据

**Decision**：

- **搜索范围**：固定 `dense = 1.0`，扫 `sparse ∈ {0, 0.1, 0.25, 0.5, 0.75, 1.0, 1.5, 2.0}`
- **判据**（按优先级）：
  1. **硬约束**：英文金标 recall ≥ 纯语义检索的 recall（45.7%）—— 这是本 feature 存在的理由，倒退必须消除
  2. 在满足硬约束的候选中，选 **MRR 最大**者
  3. 若无候选满足硬约束，选 recall 最大者，并在校准记录中说明未达成及原因

**Rationale**：

- **只扫一个自由度**：RRF 权重只有相对比例有意义（同乘一个常数不改变排序），因此固定一路为 1.0、只扫另一路即可覆盖全部有意义的配置。这把二维搜索降到一维
- **范围下界含 0**：`sparse=0` 等价于纯语义检索，是天然的对照组，也验证 SC-005
- **范围上界 2.0**：已实测等权（1.0）时 sparse 噪音过大，最优解几乎必然在 1.0 以下；上界取 2.0 只为确认曲线形状、避免"边界即最优"的假象
- **judge 主看 recall**：倒退发生在 recall 与 hit_rate，MRR 本就是增益项。若以综合分调优，可能选出一个"MRR 很高但 recall 仍倒退"的点，那等于没解决问题

**中英文取舍**：中文金标仅 6 条，单条 case 即 16.7% 摆动，**不作为调优目标**，只用于验证选定权重在中文上不倒退（spec Assumptions 已声明）。

**Alternatives considered**：

- *二维网格扫描*：冗余 —— 相对比例相同的配置结果完全一致
- *更细的步长*（如 0.05）：金标样本量（42 条）支撑不了这么细的分辨率，会是过拟合噪音
- *以综合分（如 recall 与 MRR 的加权和）为判据*：权重之上再引入一层主观权重，且可能掩盖 recall 未达标

## 预先承认的一种可能结果

spec 的 Assumptions 已声明：**最优权重可能落在 `sparse` 极低处**（如 0.1），使带权混合收敛到接近纯语义检索。

若如此：

- SC-001 / SC-002（消除倒退）**成立** —— 这是本 feature 的核心目标
- SC-011（严格优于任一单路）**可能不成立**
- 校准记录须明确给出这一结论与曲线数据，而非粉饰

这不是验收放水。「关键词路径在当前语料上贡献有限」本身就是一个有价值的、可量化的工程结论 —— 它会直接影响后续是否值得投入查询改写去提升关键词路径的质量。
