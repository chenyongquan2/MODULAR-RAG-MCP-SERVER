## 一、最重要的发现：判据用的尺子偏向 dense

这条放在最前面，因为它改变了本 feature 全部数字的读法。

金标的 `expected_chunk_ids` 是 [`scripts/backfill_chunk_ids.py`](../../scripts/backfill_chunk_ids.py) 回填的，而它的做法是：

```python
# scripts/backfill_chunk_ids.py:85
results = vector_store.query(vector=query_vec, top_k=top_k)
```

**直接查向量库 —— 纯 dense 检索，没有 BM25、没有融合。**

也就是说，金标的"正确答案"就是 dense 当初返回的那批 chunk。后果：

- `recall` 与 `hit_rate` 衡量的是「有没有复现 dense 的选择」
- 任何 sparse 贡献只要挤掉一条 dense 命中，**按构造就只能拉低这两项**
- 因此 spec 的 SC-001 / SC-002（recall / hit_rate 不低于纯语义）是**用 dense 自己的布裁的尺子**去要求混合检索

**这不是事后找借口**：Feature-004 已经独立发现同一批检索结果上 `custom__recall` 0.42 而 `ragas__context_recall` 0.83 —— 语义支撑率是 id 精确重合率的两倍。两个 feature 从不同角度指向同一结论。

**解读原则**：`MRR` / `nDCG` 比 `recall` / `hit_rate` 可信。前两者衡量的是「找到的东西排得对不对」，不依赖 id 集合与 dense 的重合度。

## 二、完整扫描曲线（SC-010）

`dense` 固定 1.0，扫 `sparse`。权重只有相对比例有意义，故一维扫描已覆盖全部有意义的配置。

| 1 : 1.5 | 61.9% | 37.1% | 0.4943 | 0.3630 |
| 1 : 2 | 61.9% | 37.1% | 0.5068 | 0.3644 |

### 两个语种的方向相反 —— 这是本次校准最有信息量的观察

| | 英文（42 条） | 中文（6 条） |
|---|---|---|
| sparse 增大对 recall | **单调变差**（45.7% → 37.1%） | **单调变好**（26.7% → 33.3%） |
| sparse 增大对 MRR | 先升后降，峰值在 0.75 | 单调变好至 0.75 后持平 |
| hit_rate | 只有纯语义能到 69.0% | 全程 66.7% 不动 |

**可能的解释**（未经进一步验证，标为推测）：中文查询经 CJK bigram 切分后，技术术语（函数名、错误码）成为强锚点，关键词路径贡献真实信息；而英文金标的期望 id 本就由英文 ground truth 经 dense 回填，dense 在自己的尺子上占优。

**中文样本量的限制**：6 条 case，单条即 16.7% 摆动。recall 从 26.7% 到 33.3% 很可能只是 1 条 case 的变化。**中文结论置信度低，仅用于验证不倒退，不作为调优依据**（spec Assumptions 已声明）。

## 三、选定权重与判据（SC-010）

**采用 `dense : sparse = 1 : 0.1`。**

判据是 [research.md](./research.md) Decision 6 **预先登记**的（在看到结果之前）：

1. 硬约束：英文 recall ≥ 纯语义的 45.7%
2. 满足者中取 MRR 最大
3. 无人满足则取 recall 最大并标注

执行结果：7 个候选（排除 `sparse=0`，它不构成"混合"）中**只有 1 个**满足硬约束 —— `sparse=0.1`（recall 恰好持平 45.7%），其 MRR 0.4693。

**我没有在看到结果后改判据。** 尽管第一节的发现说明硬约束所用的尺子偏向 dense，但 SC-001 / SC-002 是 spec 层面已确认的成功判据，不能因为不喜欢它的答案就折扣掉。因此按预登记判据交付 `0.1`，并在下一节把另一个选择摆出来供决策。

### 采用 0.1 的实际效果

| | recall | hit_rate | MRR | nDCG |
|---|---|---|---|---|
| 英文 vs 纯语义 | 持平 45.7% | **↓ 66.7% vs 69.0%** | ↑ 0.4693 vs 0.4365 | ↑ 0.4106 vs 0.3889 |
| 中文 vs 纯语义 | 持平 26.7% | 持平 66.7% | ↑ 0.5833 vs 0.5333 | ↑ 0.3176 vs 0.2814 |

**两个语种的排序质量都提升、召回都持平，代价是英文 42 条里 1 条丢了唯一命中**（69.0% = 29/42 → 66.7% = 28/42）。

### 另一个值得考虑的选择：`sparse = 0.75`

若认可第一节的结论（`recall`/`hit_rate` 偏向 dense，`MRR`/`nDCG` 更可信），则 `0.75` 明显更优：

| | 0.1 | 0.75 | 差 |
|---|---|---|---|
| 英文 MRR | 0.4693 | **0.5395** | **+0.070** |
| 英文 nDCG | 0.4106 | **0.4237** | +0.013 |
| 英文 recall | 45.7% | 44.3% | −1.4pp |
| 中文 MRR | 0.5833 | **0.6667** | **+0.083** |
| 中文 nDCG | 0.3176 | **0.3426** | +0.025 |
| 中文 recall | 26.7% | 26.7% | 持平 |

`0.75` 在两个语种上都是 MRR/nDCG 的（近）最优点，代价仅是英文 recall −1.4pp（约 0.6 条 case）。

**这是一个需要人来定的取舍**，取决于是否接受「金标的 recall 不是中立裁判」这一判断。切换只需改一行配置。

## 四、三方对比（SC-009）

三种配置**全部由同一份检索缓存重放**，因此差异纯粹来自融合权重，不含检索层面的随机波动。

### 英文金标（42 条）

| 配置 | hit_rate | recall | MRR | nDCG |
|---|---|---|---|---|
| 纯语义 | 69.0% | 45.7% | 0.4365 | 0.3889 |
| 等权混合（改造前） | 64.3% | 42.4% | 0.5115 | 0.3995 |
| **带权混合 1:0.1** | 66.7% | **45.7%** | 0.4693 | **0.4106** |

### 中文金标（6 条）

| 配置 | hit_rate | recall | MRR | nDCG |
|---|---|---|---|---|
| 纯语义 | 66.7% | 26.7% | 0.5333 | 0.2814 |
| 等权混合（改造前） | 66.7% | 30.0% | 0.6667 | 0.3645 |
| **带权混合 1:0.1** | 66.7% | 26.7% | 0.5833 | 0.3176 |

**相比改造前（等权）的净变化**：英文 recall +3.3pp、hit_rate +2.4pp、nDCG +0.011，MRR −0.042；中文 recall −3.3pp、MRR −0.083、nDCG −0.047。

> 中文侧相比等权是**变差**的 —— 因为中文的最优方向是 sparse 更高。这是「用英文校准、单一全局权重」的必然代价，已在 spec Assumptions 中预见（"中英文两套金标的最优权重不同时，记录中说明取舍理由"）。

| **SC-012** | 交换路径顺序输出不变 | ✅ **达成** | 含「对调权重排序必翻转」的反向断言，排除假通过 |
| **SC-013** | 空路不影响他路 | ✅ **达成** | 同时断言绝对得分而非仅排序 |

**10/13 达成。三项未达成的原因是同一个，值得说清楚。**

### SC-002 为何不可能达成

英文金标 42 条中有 1 条，其唯一命中在 dense 排名靠后；一旦 sparse 参与融合（任何正权重），该条的命中就被挤出 top-10。因此 `hit_rate` 69.0% **只有 `sparse=0` 能达到** —— 而那就是纯语义检索，不是混合。

结合第一节：金标期望 id 由 dense 回填，这条 case 的"正确答案"本就是 dense 的输出。要求混合检索在这把尺子上不输，等于要求它别改变 dense 的任何结果。

### SC-001 与 SC-003 在英文上不可同时满足

- 满足 SC-001（recall ≥ 45.7%）只有 `sparse=0.1`，其 MRR 0.4693
- 满足 SC-003（MRR ≥ 0.5115）需要 `sparse ≥ 0.25`，其 recall ≤ 44.3%

这是一条真实的 Pareto 前沿，不是实现缺陷。spec 把两者都列为 SC 时未预见它们互斥 —— **这是 spec 的疏漏，记录在此**。

### 那么本 feature 到底解决了什么

诚实地讲：

- ✅ **消除了 recall 倒退**：改造前等权混合 42.4% < 纯语义 45.7%；现在 45.7% 持平
- ✅ **两个语种的排序质量都优于纯语义**：MRR / nDCG 均提升
- ✅ **权重成为可配置、可观测、可校准的一级参数**（此前 `k` 硬编码、无权重概念）
- ❌ **没能让混合检索在所有指标上严格优于单路** —— 在当前语料 + 当前金标构造方式下，这个目标本身可能是不可达的

最后一条是有价值的负面结论：**它说明提升混合检索的下一步不在融合权重，而在关键词路径的质量本身（查询改写）或金标的构造方式（人工标注答案边界）。**

## 六、唯一的行为变化：同分排序

排序键从 `score` 改为 `(-score, chunk_id)`。

旧实现是 `sort(key=score, reverse=True)`。Python 排序稳定，因此**同分项的相对次序由插入顺序决定，而插入顺序随路径遍历顺序变化** —— 即旧行为在同分时本来就是顺序依赖的（同分在 RRF 里不罕见：两个不同 chunk 分别在两路拿到相同名次即同分）。

因此加 `chunk_id` 次级键**不是破坏向后兼容，而是把一处原本不确定的行为变确定**。SC-006 的「逐条一致」相应只对非同分输入断言；测试里内嵌了旧实现的逐行复刻做对照，并显式断言旧实现在同分时会随传入顺序翻转。

## 七、实施期间的关键发现

| 发现 | 说明 |
|---|---|
| **代码里已存在一处顺序写反的注释** | `fusion.py` 原注释写 `[sparse_result, dense_result]`，而 `hybrid_search.py` 实际传 `[dense, sparse]`。**等权时完全无害所以一直存活** —— 这正是「按位置对应权重会出错」的现成例证，也是把入参改为命名映射的全部理由 |
| **金标的 recall 不是中立裁判** | 见 § 一。两个 feature 从不同角度指向同一结论 |
| **SC-001 与 SC-003 互斥** | spec 疏漏，见 § 五 |
| **中英文最优权重方向相反** | 英文 sparse 越低越好、中文越高越好。单一全局权重必然牺牲一侧 |
| **「不做动态归一化」需要测试守** | 它不改变任何可观测排序，因此后人极易当作"优化"加回来。已由 SC-013 守住 |
