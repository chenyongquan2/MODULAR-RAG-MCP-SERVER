# Feature Specification: 带权重的结果融合

**Feature Branch**: `dev-from-clean-start`（本 feature 不单开分支，沿用现有分支；调用 speckit 脚本时用 `SPECIFY_FEATURE=005-weighted-fusion` 旁路 `check_feature_branch`）
**Created**: 2026-08-10
**Status**: Draft
**Input**: User description: "带权重的结果融合：修复混合检索劣于单路检索的问题。Feature-004 实测显示混合检索在英文金标 42 条上 recall 42.4% 低于纯 dense 的 45.7%（-3.3pp），而 MRR 0.502 高于 0.437（+0.065）—— 根因是 fusion.py:102 的 RRF 公式 1/(k+rank) 没有权重项，sparse 与 dense 被平等对待，BM25 在中文 bigram 上的噪音命中挤掉了 dense 的正确结果。范围：为融合引入按检索路径的权重、把硬编码的平滑参数与权重纳入配置、改造融合入参形态使权重与路径可靠对应、用中英文两套金标校准权重并给出推荐默认值、产出「纯 dense / 等权混合 / 带权混合」三方对比证明带权混合优于任一单路。不改检索器本身，不引入查询改写与检索规划。"

## 背景：一个已被实测确认的倒退

Feature-004 修好了混合检索的三个基础缺陷（标识体系、集合隔离、中文切分），使两路检索首次真正融合。但在同一批金标上做「纯语义检索 vs 混合检索」对照时，发现了一个**反直觉且明确的倒退**：

| 英文金标（42 条） | 纯语义 | 混合 | 差 |
|---|---|---|---|
| hit_rate | 69.0% | 61.9% | **−7.1pp** |
| recall | 45.7% | 42.4% | **−3.3pp** |
| MRR | 0.437 | 0.502 | +0.065 |

| 中文金标（6 条） | 纯语义 | 混合 | 差 |
|---|---|---|---|
| hit_rate | 66.7% | 66.7% | 0 |
| recall | 26.7% | 30.0% | +3.3pp |
| MRR | 0.533 | 0.667 | +0.134 |

**混合检索在英文上拉低了命中与召回，却在两个语种上都抬高了排序质量。**

根因明确：融合算法对每条检索路径**一视同仁**。关键词路径产生的噪音命中挤占了语义路径正确结果的名次，压低召回；而两路同时命中的内容得分叠加、排名上升，抬高 MRR。

**这意味着当前系统处在一个尴尬状态：开启混合检索会让英文场景的召回变差。** 本 feature 要消除这个倒退。

详见 [Feature-004 验收记录 § 四](../004-retrieval-infra-fix/acceptance.md)。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 融合权重可配置且真实生效 (Priority: P1)

作为检索服务的维护者，我希望能够指定「语义匹配和关键词匹配各占多大分量」，而不是被迫接受两者平等对待——因为实测表明平等对待会让英文场景的召回不升反降。

**Why this priority**: 这是本 feature 的能力本体。没有它，后面的校准与验证都无从谈起。同时它修复了一处既有的配置驱动违规：融合的平滑参数当前是**硬编码**的，融合器构造时不读任何配置。

**Independent Test**: 修改权重配置并重启，对同一查询观察融合后的排序发生可预期的变化；把权重调到极端（关键词路径权重为 0）时，结果应与纯语义检索一致。完成此项即可独立交付价值——运维者获得了调节两路配比的手段。

**Acceptance Scenarios**:

1. **Given** 权重配置为两路相等，**When** 执行查询，**Then** 融合结果与本 feature 之前的行为完全一致（向后兼容）
2. **Given** 关键词路径权重配置为 0，**When** 执行查询，**Then** 融合结果的排序与纯语义检索一致
3. **Given** 语义路径权重高于关键词路径，**When** 某内容仅被关键词路径命中，**Then** 它的排名低于同等名次下仅被语义路径命中的内容
4. **Given** 配置了非法权重（负数、全部为零、非数值），**When** 系统启动，**Then** 立即报错拒绝启动，而非静默回退到默认值
5. **Given** 融合执行完毕，**When** 查看该次查询的追踪记录，**Then** 能看到本次实际生效的各路权重

### User Story 2 - 权重经金标校准并给出推荐值 (Priority: P2)

作为使用者，我不想自己猜权重该设多少。我希望项目给出一组有依据的推荐默认值，并且能看到这个值是怎么得出的。

**Why this priority**: 可配置但没有推荐值等于把难题丢给用户。但它排在 P1 之后，因为校准的前提是权重机制已经能用。

**Independent Test**: 查看校准记录，能看到搜索了哪些权重组合、用什么判据选出推荐值、推荐值在两套金标上的表现；换一个人按记录重跑能得到相同结论。

**Acceptance Scenarios**:

1. **Given** 校准已完成，**When** 查看校准记录，**Then** 能看到候选权重范围、选择判据、以及每个候选在两套金标上的得分
2. **Given** 推荐权重已写入默认配置，**When** 不做任何修改直接运行评估，**Then** 得到的结果与校准记录中该权重对应的数字一致
3. **Given** 中英文两套金标的最优权重不同，**When** 选定单一推荐值，**Then** 记录中说明了取舍理由

---

### User Story 3 - 三方对比证据留档 (Priority: P3)

作为项目的评估者，我需要一份「纯语义 / 等权混合 / 带权混合」的逐指标对比，用来确认这次改动确实解决了问题，而不是换了个说法。

**Why this priority**: 不做不影响功能，但没有它就无法证明本 feature 达成了目的——而"混合优于单路"正是这次改动存在的全部理由。

**Independent Test**: 存在一份覆盖中英文两套金标、三种配置的对比表，且其中带权混合一列在关键指标上不低于其余两列。

**Acceptance Scenarios**:

1. **Given** 三种配置各跑一轮评估，**When** 汇总结果，**Then** 得到覆盖两个语种、四项检索指标的对比表
2. **Given** 对比表已产出，**When** 查看英文金标的召回一列，**Then** 带权混合不低于纯语义（即倒退已消除）
3. **Given** 某项指标带权混合仍不占优，**When** 查看记录，**Then** 有明确说明为何如此以及是否可接受

### Edge Cases

- **某一路检索返回空**：另一路的权重是否需要重新归一化？（例如关键词路径异常返回空时，语义路径的结果不应因权重小于 1 而整体降分）
- **两路权重都为 0**：应被启动期校验拒绝，否则所有结果得分归零、排序完全随机
- **权重为极小值**：例如 0.001，是否与 0 有实质区别？行为需可预期
- **只提供部分路径的权重**：未指定的路径按什么处理？（缺省值 vs 报错）
- **未来新增第三条检索路径**：权重配置的形态是否能容纳，还是必须改结构
- **权重与路径错配**：这是本 feature 最危险的失败模式——错配后系统照常运行、不报错，只是效果变差且极难察觉

## Requirements *(mandatory)*

### Functional Requirements

**权重机制**

- **FR-001**: 融合 MUST 支持为每条检索路径设置独立权重
- **FR-002**: 权重与检索路径的对应关系 MUST NOT 依赖调用时的参数顺序 —— 当前融合接口接收的是一个位置列表、靠下标区分两路，引入权重后按下标对应极易错配，且**错配不会报错**（见 Edge Cases 末条）
- **FR-003**: 未配置权重时 MUST 退化为各路等权，行为与本 feature 之前完全一致
- **FR-004**: 某路检索返回空结果时，其余路的相对排序 MUST NOT 因此改变

**配置化**

- **FR-005**: 权重 MUST 通过配置控制，业务代码中不得硬编码
- **FR-006**: 融合的平滑参数 MUST 一并纳入配置 —— 它当前是硬编码值，且融合器构造时不读取任何配置，属既有的配置驱动违规
- **FR-007**: 非法权重（负数、全部为零、非数值）MUST 在系统启动期被拒绝并抛出明确错误，禁止静默回退到默认值

**可观测**

- **FR-008**: 融合阶段的追踪记录 MUST 包含本次实际生效的各路权重

**校准与证据**

- **FR-009**: 推荐权重 MUST 有金标校准依据，不得凭经验直接给定
- **FR-010**: 校准过程 MUST 可复现：记录候选范围、选择判据、各候选的得分
- **FR-011**: MUST 产出「纯语义 / 等权混合 / 带权混合」三方逐指标对比，覆盖中英文两套金标

### Key Entities

- **检索路径（Route）**：一条独立的召回通道（当前有语义匹配与关键词匹配两条）。本 feature 让每条路径获得一个可配置的分量
- **路径权重（Weight）**：非负数值，表示该路径在融合中的相对分量。绝对大小无意义，只有相对比例有意义
- **融合平滑参数**：控制排名靠后结果衰减速度的常数。当前硬编码，本 feature 纳入配置
- **校准记录**：候选权重组合及其在金标上的表现，是推荐默认值的依据

## Success Criteria *(mandatory)*

### Measurable Outcomes

**核心目标：消除倒退**

- **SC-001**: 带权混合在英文金标上的召回**不低于**纯语义检索（当前等权混合低 3.3pp）
- **SC-002**: 带权混合在英文金标上的命中率**不低于**纯语义检索（当前等权混合低 7.1pp）
- **SC-003**: 带权混合在两个语种上的排序质量**不低于**等权混合当前水平（即改善召回不以牺牲已有的排序增益为代价）

**能力可用**

- **SC-004**: 调整权重配置后重启，同一查询的融合排序发生可观测变化
- **SC-005**: 关键词路径权重设为 0 时，融合结果排序与纯语义检索一致
- **SC-006**: 未配置权重时，结果与本 feature 之前逐条完全一致
- **SC-007**: 非法权重配置导致启动失败，错误信息指明具体字段
- **SC-008**: 任一次查询的追踪记录中可读出本次生效权重
- **SC-012**: 改变各路结果传入融合的先后顺序，融合输出**逐条完全不变** —— 这是 FR-002 的直接判据。权重与路径错配是本 feature 最危险的失败模式：错配后系统照常运行、不报错，只是效果悄悄变差
- **SC-013**: 任一路返回空结果时，另一路结果的相对排序与该路单独检索时一致（即空路不得因权重小于 1 而拖低另一路的整体得分）

**证据完备**

- **SC-009**: 存在一份三方对比表，覆盖中英文两套金标、四项检索指标
- **SC-010**: 存在一份校准记录，含候选范围、判据与各候选得分，第三方按记录可复现结论
- **SC-011**: 至少在一个语种上，带权混合在召回与排序质量两项上**同时严格优于**任一单路 —— 这是「混合检索确实带来增益」的正面证据，而非仅仅"不比单路差"

## Assumptions

**关于范围**

- 只改融合环节。检索器本身（语义召回、关键词召回）不做任何改动
- 不引入查询改写、子查询分解、检索规划 —— 那些属于后续 feature
- 沿用现有的融合算法族（基于排名的倒数融合），只增加权重维度；不替换为其他融合范式（如分数归一化后线性组合）

**关于评估**

- 校准与验证使用现有的两套金标（中文 6 条 / 英文 42 条）与现有评估体系，本 feature 不新建评估能力
- **中文金标仅 6 条，样本量不支持精细校准**。因此推荐权重主要依据英文金标（42 条），中文金标用作"不倒退"的验证而非调优目标
- 金标的期望内容标识是脚本按固定 top-5 回填的，非人工标注的答案边界。这会让召回类指标的绝对值偏低（Feature-004 实测：同一批结果，语义支撑率 83% 而标识精确重合仅 30–42%）。**校准应关注相对变化而非绝对值**

**关于结果的不确定性**

- **有可能最优权重就是"关键词路径权重极低"**，即带权混合收敛到接近纯语义检索。若如此，这仍是有效结果（倒退被消除），但 SC-011 可能无法达成——届时校准记录须说明这一结论及其依据
- 权重是语料相关的。本次校准结论绑定当前语料（MT5 技术文档），换语料需重新校准 —— 这与项目既有的"换 Judge 需重新校准阈值"是同一类约束

**关于默认值**

- 未配置权重时退化为等权，确保既有部署升级后行为不变（FR-003）
- 融合平滑参数纳入配置后，其默认值保持当前硬编码的数值，避免本 feature 顺带改变既有行为

## Dependencies

- 依赖 Feature-004 已完成 —— 在两路检索真正融合之前，任何关于融合权重的测量都不可信
- 依赖 Feature-001 的评估体系（8 项指标 + 基线归档 + delta 对比）用于校准与验证
- 依赖当前生效的语料集合与索引（`default_text-embedding-v4`）

## Out of Scope

- 查询改写（Multi-Query / HyDE / 策略路由）
- 子查询分解与检索规划器
- 替换融合算法族（如改用分数归一化的线性组合）
- 检索器内部改动（召回数量、打分公式、索引结构）
- 按查询类型动态调整权重（本 feature 只做静态配置权重；动态路由属后续 feature）
- 门店知识库语料接入
