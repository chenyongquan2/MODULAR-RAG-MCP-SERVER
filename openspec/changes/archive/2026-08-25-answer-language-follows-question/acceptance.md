# 验收记录 —— answer-language-follows-question

**日期**：2026-08-25　**分支**：`dev-from-clean-start`　**状态**：10/10 任务完成。

## 一、一句话结论

**主判据大幅超标：英文问题的答案语言一致率 39.0% → 100.0%；RAGAS 降级率 41.5% → 4.9%，首次低于 5% 门槛。**

而这轮验收最值钱的产出不是这两个数，是两个**关于测量本身**的发现（§四）：一次 embedding 超时就能污染回归判据；`judge_llm.temperature = 0.0` **并没有**让托管 judge 变确定。

## 二、实测结果

英文金标 41 条 `pooled-llm-judged`，集合 `default_text-embedding-v4`，`fusion_weights.sparse=0.75`。
改前 = run `728a77ab`，改后 = run `6985e140`。

| `ragas__context_recall` | 41 / 41 | 41 / 41 |

`faithfulness` 的降级率从 34% 降到 5% —— 这是四项里病得最重的一项，也是本变更最直接的作用点。

## 三、⚠️ RAGAS 分数本身不能作为成功证据

四项里两项被自动标进 `delta_incomparable_metrics`（分母变了）：

| 指标 | 分母 | 可比性 |
|---|---|---|
| `ragas__faithfulness` | 27 → 39 | ⛔ 不可比 |
| `ragas__context_precision` | 33 → 40 | ⛔ 不可比 |
| `ragas__answer_relevancy` | 41 → 41 | 分母稳定，但见 §四② |
| `ragas__context_recall` | 41 → 41 | 分母稳定，但见 §四② |

后两项分母未变却**下降了**（`answer_relevancy` −0.046、`context_recall` −0.049）。
**这不是本变更造成的退步** —— 归因见 §四②。

**本变更的成功依据是「语言一致率」与「降级率」，不是 RAGAS 的分数。** 前两者一个是
纯字符统计（确定性）、一个是计数（确定性）；后者是 LLM 判定的均值，既受分母浮动
影响、又不可复现。

## 四、这轮最值钱的两个发现（都关于测量本身）

### ① 一次 embedding 超时就能污染「逐位不变」的回归判据

T-3.2 要求检索侧指标**逐位不变**（本变更不碰检索）。首次比对**失败**：

```
custom__ndcg     0.7184211735 -> 0.7151117724   CHANGED
custom__recall   0.4583584126 -> 0.4539238228   CHANGED
dense__hit_rate  0.9756097561 -> 0.9512195122   CHANGED
（sparse 四项逐位不变）
```

逐条定位后**只有 case 39** 变了，且它的 dense 单路从 `1.0/1.0/0.8182/0.89`
**全部归零** —— 那是「dense 返回空列表」的形态。日志证据：

```
18:49:13 [ERROR] src.libs.embedding.openai_embedding: OpenAI Embedding API call failed: Request timed out.
```

`HybridSearch` 捕获 dense 异常并降级为空列表（既有设计，正确），于是该路指标按
「未命中」计零。**重放该 case 后 dense 单路完全恢复到改前的值**
（`1.0/1.0/0.8182/0.89`），且 dense 检索连跑三次逐位稳定、embedding 对同一文本
两次调用逐位相同。

**结论：T-3.2 的失败与本变更无关，是一次网关抖动。** 判据实质通过。

⚠️ **但这条本身是个该记住的教训**：项目此前写着「检索侧完全可复现 —— 这几个数在
三次独立运行里逐位重合」。那是真的，**前提是网关不抖**。一次超时就足以让一条 case
的某一路归零，进而改变两项融合后指标。**做「逐位不变」类回归判定时，必须先按
`ERROR` 过滤日志**，否则会把基础设施抖动读成代码回归 —— 这与「限流会伪装成降级」
是同一类陷阱的另一个面。

### ② `judge_llm.temperature = 0.0` 并没有让托管 judge 变确定

`context_recall` 只依赖 `(question, ground_truth, contexts)` —— **不依赖答案**，
所以本变更按理不该动它。但它变了 −0.049。逐条定位：

| case | 改前 | 改后 | query 相同 | ground_truth 相同 | contexts 相同 |
|---|---|---|---|---|---|
| 9 | 0.50 | 0.00 | ✅ | ✅ | ✅ |
| 19 | 1.00 | 0.00 | ✅ | ✅ | ✅ |
| 26 | 1.00 | 0.00 | ✅ | ✅ | ✅ |
| 36 | 0.50 | 1.00 | ✅ | ✅ | ✅ |

**三个输入全部逐字相同，`temperature=0.0`，判定却翻转了。** 4/41 = 9.8% 的翻转率。

（另：`answer_relevancy` 在 **38/41** 条上都变了 —— 那个是预期的，它依赖答案，
而 `llm.temperature` **这个字段根本不存在**，答案生成用的是 provider 默认温度，
所以答案每轮都不同。）

**含义 —— 这修正了一个此前的隐含假设**：

- 项目已知「不要用重跑 `evaluate.py` 做 judge 对照，因为 `llm.temperature` 未设为 0」，
  对策是**冻结元组**（拿归档的四元组喂不同 judge）。
- 现在知道：**即使元组完全冻结、judge 温度设为 0，判定仍会翻转约 10%。**
  `temperature=0` 在托管模型上不等于确定性（批处理、内核非确定性都会引入抖动）。
- 所以 **RAGAS 的 ±0.05 级 delta 即使分母稳定也不可归因**。真要比较，需要多次重复
  取均值并给出区间，而不是拿单次两个数做减法。

## 六、与计划的偏差

| 计划 | 实际 | 原因 |
|---|---|---|
| T-1.3 跑一轮记录改前的语言一致率 | **改为离线完成** | 归档 run `728a77ab` 就是「改前 + 同配置 + 同金标」的运行，把它的问答对喂进**生产代码** `compare_languages()` 得 16/41 = 39.0%，与立项时的外部算法逐条吻合。省 ~2 小时网关时间，且验的是真实代码路径在真实历史数据上的结果 —— 证据更强 |

## 七、已知上限：中文侧的 RAGAS 仍不可用

中文 6 条改后仍有 3/6 降级、`faithfulness` 只有 3/6 有效 —— 而它们**6/6 语言一致**。

这与立项时的判断一致：**`ragas==0.1.21` 的内部提示词是英文的，它处理中文答案本身
就不行**，与答案是否跟随问题、与上下文什么语言都无关。这和「`adapt(language=chinese)`
在三个模型上全部产出 0.0% 中文」是同一句话的两面。

**RAGAS 在本项目的中文内容上永远不会好，而语料 81.4% 是中文。** 要解决那一半只有
换掉 RAGAS 或绕开它 —— 属另一个量级的决定，尚未立项。

## 八、回写的教训

已写入 `CLAUDE.md` 与 `openspec/config.yaml`：

1. **降级的判据是「答案是不是英文」，不是「答案与上下文是否一致」**（修正既有归因）。
   实测：答案匹配上下文 42% 降级、不匹配 41% —— 没有区别；而「中文上下文 + 英文答案」
   是 **0%**。
2. **RAGAS 实质只能工作在英文上，而让它支持中文的机制（`adapt`）是坏的** ——
   把语言错乱与 adapt 失败两件事接成了同一个根因。
3. **`temperature=0` 不等于可复现**（§四②）。做 RAGAS 对照时冻结元组还不够。
4. **做「逐位不变」回归判定前先按 `ERROR` 过滤日志**（§四①）—— 一次网关抖动会
   伪装成代码回归。
