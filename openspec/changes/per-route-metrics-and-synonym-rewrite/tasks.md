## 1. 分路径评估口径（硬前置）

- [x] 1.1 `HybridSearch` 新增返回「融合结果 + 各路原始有序结果」的通道，`search()` 原样保留并转调它（design D1）。**不改 `search()` 的签名与返回类型** —— MCP 与 `scripts/query.py` 都在用。配套单测：两路都有结果 / 某一路为空 / 两路皆空，且断言 `search()` 的返回与改造前逐条相同（这条是防回归的关键）

- [x] 1.2 `EvalRunner` 消费上述通道，为每一路复用**同一套**指标函数产出 `hit_rate` / `mrr` / `ndcg` / `recall`，写进报告（design D2）。**不得为分路径另写一套打分公式** —— 两套必然漂移且漂移是静默的。某一路在某条 case 上无结果时按「未命中」计入，分母仍是全部用例数。配套单测覆盖：分路径与融合后指标并存且可区分、空路径不被跳过、字段在只启用纯计算类指标时照常产出

- [x] 1.3 **自检用例（本组的验收判据）**：把 `fusion_weights` 配成只留一路（其余为 0），断言该路的分路径指标**等于**此时的融合后指标。这是它们在定义上应当相等的情形 —— 没有这条，分路径指标算错了也没人会知道

- [x] 1.4 用当前生产配置（`strategy` 尚未引入，`sparse=0.1`）在 `golden_test_set_en_v2.json` 上跑一次，**记录 dense 单路与 sparse 单路的四项基准数**。这是 §2 唯一的对照基线。跑法：`--lang en --no-generate-answers` + `backends: [custom]`（纯检索改动，带答案生成会把耗时推到小时级并引入无关方差）

  **基准结果**（run `0147ce03`，英文 41 条，`pooled-llm-judged`，`sparse=0.1`）：

  | | hit_rate | MRR | nDCG | recall |
  |---|---|---|---|---|
  | 融合后 | 0.9756 | 0.8585 | 0.7140 | 0.4584 |
  | **dense 单路** | 0.9756 | **0.7793** | 0.6835 | 0.4584 |
  | **sparse 单路** | 0.9024 | **0.8104** | 0.6342 | 0.3925 |

  ⚠️ **两个意料之外的发现**：

  1. **sparse 单路的 MRR 反而高于 dense**（0.8104 vs 0.7793），而它的融合权重只有 0.1。
     项目一直写着「瓶颈在 sparse 的信噪比」—— 在 `recall`(0.3925 vs 0.4584) 与
     `hit_rate`(0.9024 vs 0.9756) 上确实成立（噪音命中多、漏得也多），但在**排序质量**上
     sparse 更强：它命中的时候排得更靠前。这与「把 sparse 权重从 0.1 提到 0.75 会让融合后
     MRR 上升」那条实测互相印证。**§3.1 的 A/B 要盯着这一点** —— 若同义词扩展提升的是
     sparse 的 recall（而非 MRR），那才是补上它真正的短板。
  2. **交叉验证成立**：dense 单路 MRR `0.7793` 与 `calibrate_fusion_weights.py --sweep`
     里「1:0（纯语义）」那一行**逐位相同**。两条完全独立的实现路径给出同一个数 ——
     分路径口径的正确性除了 T-1.3 的自检外，又多了一重外部佐证。

## 3. 验收与文档

- [x] 3.1 A/B：`strategy: none` vs `synonym`，英文 41 条，`--no-generate-answers` + `backends: [custom]`。**主判据是 `sparse` 单路的 `MRR` / `nDCG`**（本变更唯一直接作用的对象）；融合后指标只看有无显著倒退，且**看 `MRR` / `nDCG` 不看 `recall` / `hit_rate`**（后两者结构性偏向 dense）。中文 6 条只跑一次确认无明显倒退，**其 delta 按噪声处理，不作判定依据**

  ### 结果：**负增益，保持默认关闭**

  英文 41 条，`pooled-llm-judged`，`--no-generate-answers` + `backends: [custom]`，
  `fusion_weights.sparse = 0.1`：

  | 臂 | sparse MRR | sparse nDCG | sparse recall | 融合后 MRR |
  |---|---|---|---|---|
  | `none`（基准，run `0147ce03`） | **0.8104** | 0.6342 | 0.3925 | 0.8585 |
  | v1 广词表 32 组（run `af5475d9`） | 0.7311　**−0.0793** | 0.5753 | 0.3567 | 0.8585 |
  | v2 IDF 筛 12 组（run `7db1fd72`） | 0.7494　**−0.0610** | 0.5910 | 0.3686 | 0.8748 |

  **dense 单路三臂完全一致**（0.7793 / 0.6835 / 0.4584）—— 印证了「只改 keywords、
  不碰 dense 输入」这条实现口径确实成立。

  ### 为什么会有害（机制已量化）

  第一版的选词判据是「缩写零信号、全称大量存在」，看着合理 —— 那个词原本对 BM25
  贡献为 0。**但「大量存在」恰恰是 BM25 里最没用的性质**：

  | 扩展目标 | 占语料 | IDF |
  |---|---|---|
  | `manager` | **26.3%** | **1.030** |
  | `value` | 22.3% | 1.250 |
  | `server` | 12.4% | 1.951 |
  | `config` | 11.9% | 1.998 |

  而被它们补充的缩写在存在时 IDF 极高（`grp` 8.257 / `func` 8.845 / `idx` 9.944）。
  扩展做的事是**往一个高区分度的查询里塞进一个匹配全语料四分之一的词** ——
  BM25 逐词求和，这个词把几千个弱相关文档拉进候选，把真命中挤了下去。

  按 IDF ≥ 3.0 重筛（32 组 → 12 组）后伤害减半，但**没有翻转符号**。推测更深层的
  原因：这份语料是 API 参考文档，sparse 的判别力集中在**罕见标识符**
  （`IMTServerAPI::PositionGetByLoginsSymbol` 之类，IDF 8~10），任何加入**普通英文
  词汇**的扩展都在稀释它 —— 即便那个词 IDF 有 3~4。

  ### 判定

  **不启用。`settings.yaml` 保持 `strategy: none`。**

  ⚠️ 融合后那个 `+0.0163 MRR` **不构成正面证据**：41 条里一条 case 从第 2 位升到
  第 1 位就值 0.0122，它落在**单条噪声量级**内；而 sparse 的 −0.0610 约合 5 条 case
  的量级，且两版词表方向一致。拿融合后的数说「其实有用」是幸存者式解读。

  ### 这次 A/B 最重要的产物

  **融合后指标的 delta 是 `+0.0000` / `−0.0006`** —— 也就是说，**没有分路径指标的话，
  这次会被读成「改写没效果」，而实际上它在明确地造成伤害**。§1 被定为硬前置是对的，
  而且这个判断在本变更内部就得到了验证。

  ⚠️ 中文 6 条未跑：`strategy` 已判定不启用，跑它拿到的只会是同一结论的 6 条噪声版。
