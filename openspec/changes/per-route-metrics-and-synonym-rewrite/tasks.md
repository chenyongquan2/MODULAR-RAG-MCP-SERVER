## 1. 分路径评估口径（硬前置）

- [x] 1.1 `HybridSearch` 新增返回「融合结果 + 各路原始有序结果」的通道，`search()` 原样保留并转调它（design D1）。**不改 `search()` 的签名与返回类型** —— MCP 与 `scripts/query.py` 都在用。配套单测：两路都有结果 / 某一路为空 / 两路皆空，且断言 `search()` 的返回与改造前逐条相同（这条是防回归的关键）

- [x] 1.2 `EvalRunner` 消费上述通道，为每一路复用**同一套**指标函数产出 `hit_rate` / `mrr` / `ndcg` / `recall`，写进报告（design D2）。**不得为分路径另写一套打分公式** —— 两套必然漂移且漂移是静默的。某一路在某条 case 上无结果时按「未命中」计入，分母仍是全部用例数。配套单测覆盖：分路径与融合后指标并存且可区分、空路径不被跳过、字段在只启用纯计算类指标时照常产出

- [x] 1.3 **自检用例（本组的验收判据）**：把 `fusion_weights` 配成只留一路（其余为 0），断言该路的分路径指标**等于**此时的融合后指标。这是它们在定义上应当相等的情形 —— 没有这条，分路径指标算错了也没人会知道

- [x] 1.4 用当前生产配置（`strategy` 尚未引入，`sparse=0.1`）在 `golden_test_set_en_v2.json` 上跑一次，**记录 dense 单路与 sparse 单路的四项基准数**。这是 §2 唯一的对照基线。跑法：`--lang en --no-generate-answers` + `backends: [custom]`（纯检索改动，带答案生成会把耗时推到小时级并引入无关方差）

  **基准结果**（run `0147ce03`，英文 41 条，`pooled-llm-judged`，`sparse=0.1`）：

  | | hit_rate | MRR | nDCG | recall |
  |---|---|---|---|---|
  | 融合后 | 0.9756 | 0.8585 | 0.7140 | 0.4584 |
  | **dense 单路** | 0.9756 | **0.7793** | 0.6835 | 0.4584 |
  | **sparse 单路** | 0.9024 | **0.8104** | 0.6342 | 0.3925 |

  ⚠️ **两个意料之外的发现**：

  1. **sparse 单路的 MRR 反而高于 dense**（0.8104 vs 0.7793），而它的融合权重只有 0.1。
     项目一直写着「瓶颈在 sparse 的信噪比」—— 在 `recall`(0.3925 vs 0.4584) 与
     `hit_rate`(0.9024 vs 0.9756) 上确实成立（噪音命中多、漏得也多），但在**排序质量**上
     sparse 更强：它命中的时候排得更靠前。这与「把 sparse 权重从 0.1 提到 0.75 会让融合后
     MRR 上升」那条实测互相印证。**§3.1 的 A/B 要盯着这一点** —— 若同义词扩展提升的是
     sparse 的 recall（而非 MRR），那才是补上它真正的短板。
  2. **交叉验证成立**：dense 单路 MRR `0.7793` 与 `calibrate_fusion_weights.py --sweep`
     里「1:0（纯语义）」那一行**逐位相同**。两条完全独立的实现路径给出同一个数 ——
     分路径口径的正确性除了 T-1.3 的自检外，又多了一重外部佐证。
