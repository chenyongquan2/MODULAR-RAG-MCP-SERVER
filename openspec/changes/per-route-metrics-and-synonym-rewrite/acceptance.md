# 验收记录 —— per-route-metrics-and-synonym-rewrite

**日期**：2026-08-25　**分支**：`dev-from-clean-start`　**状态**：13/13 任务完成。

## 一、一句话结论

**分路径指标做成了并且立刻还了本；同义词扩展做成了但被自己的指标判了死刑 —— 这正是它该有的样子。**

同义词扩展在这份语料上对 sparse 单路**有害**（MRR −0.0610 ~ −0.0793），已判定
**不启用**，`settings.yaml` 保持 `strategy: none`。

而**融合后的 delta 是 `+0.0000` / `−0.0006`** —— 也就是说，**没有分路径指标的话，
这次会被读成「改写没效果」，而它实际在明确造成伤害**。把分路径定为硬前置而不是
配套设施，这个判断在本变更内部就得到了验证。

## 二、A/B 实测（T-3.1）

英文 41 条 `pooled-llm-judged`，`--no-generate-answers` + `backends: [custom]`，
集合 `default_text-embedding-v4`，`fusion_weights.sparse = 0.1`：

| 臂 | sparse MRR | sparse nDCG | sparse recall | sparse hit_rate | 融合后 MRR |
|---|---|---|---|---|---|
| `none`（基准，`0147ce03`） | **0.8104** | 0.6342 | 0.3925 | 0.9024 | 0.8585 |
| v1 广词表 32 组（`af5475d9`） | 0.7311　**−0.0793** | 0.5753 | 0.3567 | 0.8780 | 0.8585 |
| v2 IDF 筛 12 组（`7db1fd72`） | 0.7494　**−0.0610** | 0.5910 | 0.3686 | 0.9024 | 0.8748 |

**dense 单路三臂逐位一致**（0.7793 / 0.6835 / 0.4584）—— 印证「只改 `keywords`、
不碰 dense 输入」这条实现口径确实成立，不是嘴上说说。

⚠️ **融合后那个 `+0.0163 MRR` 不构成正面证据**。41 条里一条 case 从第 2 位升到第 1 位
就值 `0.5/41 = 0.0122`，它落在**单条噪声量级**内；而 sparse 的 −0.0610 约合 5 条 case
的量级，且两版词表方向一致。拿融合后的数说「其实有用」是幸存者式解读。

## 三、为什么有害 —— 机制已量化

**第一版的选词判据用反了。**

判据是「缩写在语料里近乎零信号、全称大量存在」，看上去很合理：那个词原本对 BM25
的贡献是 0，扩展后才第一次有分。**但「大量存在」恰恰是 BM25 里最没用的性质** ——
BM25 逐词求和，每词贡献按 IDF 加权，一个词出现在越多文档里区分度越低：

| 扩展目标 | 占语料（52,069 chunk） | IDF |
|---|---|---|
| `manager` | **26.3%** | **1.030** |
| `value` | 22.3% | 1.250 |
| `server` | 12.4% | 1.951 |
| `config` | 11.9% | 1.998 |

而被它们「补充」的缩写在存在时 IDF 极高：`grp` 8.257 / `func` 8.845 / `idx` 9.944。

**于是扩展做的事是：往一个高区分度的查询里，塞进一个匹配全语料四分之一的词。**
那个词把几千个弱相关文档拉进候选，把真命中挤了下去。

按 **IDF ≥ 3.0** 重筛（32 组 → 12 组）后伤害**减半但没有翻转符号**。推测更深层的原因：
这份语料是 **API 参考文档**，sparse 的判别力集中在**罕见标识符**
（`IMTServerAPI::PositionGetByLoginsSymbol` 之类，IDF 8~10），任何加入**普通英文词汇**
的扩展都在稀释它 —— 即便那个词 IDF 有 3~4。

> ⚠️ 第二版按 **IDF（语料先验统计）** 筛选，**不是**按 A/B 结果筛。前者与金标标签无关，
> 后者才会造成对测试集的过拟合。这个区别在只有 41 条样本时尤其要紧。

## 四、分路径指标（§1，本变更的真正产出）

`HybridSearch.search_with_routes()` 返回 `SearchOutcome(results, routes)`，
`EvalRunner` 对每一路复用**同一套**指标函数打分，报告新增
`aggregate_metrics_by_route`。

**基准数**（`0147ce03`，英文 41 条，`sparse=0.1`）：

| | hit_rate | MRR | nDCG | recall |
|---|---|---|---|---|
| 融合后 | 0.9756 | 0.8585 | 0.7140 | 0.4584 |
| **dense 单路** | 0.9756 | **0.7793** | 0.6835 | 0.4584 |
| **sparse 单路** | 0.9024 | **0.8104** | 0.6342 | 0.3925 |

**一个意料之外的发现**：**sparse 单路的 MRR 高于 dense**（0.8104 vs 0.7793），
而它的融合权重只有 0.1。项目一直写着「瓶颈在 sparse 的信噪比」—— 在 `recall`
(0.3925 vs 0.4584) 与 `hit_rate` (0.9024 vs 0.9756) 上确实成立（噪音命中多、漏得也多），
但在**排序质量**上 sparse 更强：它命中的时候排得更靠前。这与「把 sparse 权重从 0.1
提到 0.75 会让融合后 MRR 上升」那条独立实测互相印证。

**两重正确性佐证**：

1. **自检**（T-1.3）：把其余路权重配成 0 时，该路的分路径指标**等于**融合后指标 ——
   它们在定义上应当相等，参数化覆盖两路。
2. **外部交叉验证**：dense 单路 MRR `0.7793` 与
   `calibrate_fusion_weights.py --sweep` 的「1:0（纯语义）」一行**逐位相同**。
   两条完全独立的实现路径给出同一个数。

## 六、⚠️ 招牌病第十例 —— 又在本变更内部

T-3.1 准备跑 A/B 时，改完 `settings.yaml` 顺手打印了一下配置，发现读出来仍是
`strategy='none'`。

根因：`QueryRewriteSettings` 加了、`_validate_query_rewrite_settings` 写了并挂进了
`validate_settings`、`settings.yaml` 也写了 —— **但 `load_settings()` 构造 `Settings(...)`
时漏了 `query_rewrite=` 这一行**。无论 YAML 写什么，运行时永远是 dataclass 默认值。

**最值得记的是它被发现的时机**：当时本变更已有 100+ 条用例全绿，**包括一整个专门守
「改了配置结论就该变」的文件**（`test_query_rewrite_not_dead_config.py`）。它们全都直接
构造 `QueryRewriteSettings(...)`，**绕过了 YAML 加载这一段** —— 与 `_labeling_method`
那次一模一样：测了端点，没测那条线。

**如果当时没顺手打印，这次 A/B 会跑出「改写毫无效果」的结论，而根因与改写实现无关。**

已补 `TestWiredIntoLoadSettings` 两条（写临时 `settings.yaml` 走真实 `load_settings()`），
并**验证过拆掉接线它会红** —— 一条抓不到 bug 的回归测试等于没有。

## 七、与原计划的偏差（都是看了语料之后改的）

| 计划 | 实际 | 原因 |
|---|---|---|
| `config/synonyms_zh.yaml` + `synonyms_en.yaml` | 一个 `config/synonyms.yaml` | `query_rewrite.synonym_dict` 是**单个路径**，没有按语种路由的机制；写两个只会有一个生效、另一个是死文件 |
| 词条是「止损·SL·stop loss、点差·spread」 | API 缩写（`mgr`/`grp`/`bal`/`evts`） | 语料实际是 **MT5 Server API 开发文档**，不是交易概念文档。原计划的词表一个都命中不了 |
| 中文侧跑一次确认无倒退 | **未跑** | `strategy` 已判定不启用，跑它拿到的只会是同一结论的 6 条噪声版 |

**刻意排除的三类词条**（各有理由，混进来会让 A/B 失去意义）：

- **缩写本身也常见的组**（`ret` 11859 / `pos` 2435 / `err` 1868）—— 它们在 API 文档里
  多是**参数名**，与「返回 / 持仓 / 错误」不是一回事，扩展等于引入语义漂移
- **中文词条** —— 中文金标只有 6 条，**验证不了**。凭印象加就是编证据
- **单复数对**（`parameter` 1692 / `parameters` 8428）—— 缺口真实（tokenizer 不做词干
  还原），但它是**另一种机制**，混进同一次 A/B 会分不清增益来自哪边

## 八、回写的两条通用教训

### ① 融合后的指标会把单路的变化藏起来 —— 两个方向都会

项目此前的担心是「sparse 的**改善**会被 `weight=0.1` 稀释到看不见」。实测发现
**伤害同样被藏住**：sparse MRR 掉了 0.061，融合后只动了 0.0006。

所以分路径指标不只是「为了看见增益」，更是**为了看见代价**。任何只作用于单路的改动
（查询改写、sparse 的分词策略、BM25 参数），都必须看分路径指标才能判定，
**看融合后指标会得出方向相反的结论**。

### ② 为 BM25 选扩展词，判据是「扩展目标够不够稀有」，不是「够不够常见」

这条反直觉，也是本次翻车的直接原因。**一个词在语料里越常见，它对 BM25 的判别力越低**
（IDF 越小）。往查询里加一个匹配 26% 语料的词，等于加噪。

可操作的判据：扩展目标的 **IDF 要与查询里其他词处于同一量级**。在 API 参考类语料上，
查询的判别力集中在罕见标识符（IDF 8~10），**任何普通英文词汇的扩展都在稀释它** ——
这类语料上同义词扩展可能根本不适用，而不是「词表没选好」。
