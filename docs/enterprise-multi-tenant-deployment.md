# 企业多部门 RAG 部署方案（学习文档）

> **文档性质**：学习与设计参考，2026-04-23 创建。
> **适用场景**：把 RAG 系统从"单一语料 Demo"推广到"企业内多部门使用"时的架构决策依据。
> **前置阅读**：[CLAUDE.md](../CLAUDE.md)（项目架构）、[docs/rag-acceptance-plan.md](rag-acceptance-plan.md)（评估验收方案）。

---

## 0. 核心问题

> 把 RAG 系统推广到整个企业，每个部门（行政、技术、法务、客服、财务…）有自己的文档库，预料风格完全不同，**需要对每个部门单独调优吗？**

**简短答案**：不需要为每个部门从头调一套系统。**共享框架与模型，隔离数据与提示词，按需微调参数，每部门独立评估**。80% 的部门用默认配置，20% 需定向调优，告诉你哪些属于 20% 的，正是 RAGAS 评估指标。

---

## 1. 分层视角：什么是共享的，什么是专属的

把 RAG 系统拆成 5 层：

```
┌─────────────────────────────────────────────────────────────┐
│ L5. 知识层（文档 + 向量索引 + BM25 索引）                   │ 部门专属 ← 100% 独立
├─────────────────────────────────────────────────────────────┤
│ L4. Prompt 层（系统提示词、回答风格、术语表）               │ 大多专属 ← 80% 需调整
├─────────────────────────────────────────────────────────────┤
│ L3. 参数层（chunk_size、top_k、RRF 权重、reranker 阈值）    │ 部分专属 ← 按需调整
├─────────────────────────────────────────────────────────────┤
│ L2. 模型层（LLM、embedding、reranker）                      │ 基本共享 ← 90% 可复用
├─────────────────────────────────────────────────────────────┤
│ L1. 框架层（MCP server、factory、tracing、dashboard）       │ 100% 共享
└─────────────────────────────────────────────────────────────┘
```

**关键洞察**：L1-L2 完全共享，L3 按需调，L4-L5 必须专属。本项目的 pluggable architecture 天然适合这种分层复用。

---

## 2. 必须部门专属的两层

### 2.1 L5 知识层 —— 必须隔离

每个部门一个独立 `collection`：

```
行政部 → collection: "admin_docs"
技术部 → collection: "tech_docs"
法务部 → collection: "legal_docs"
财务部 → collection: "finance_docs"
客服部 → collection: "customer_service_docs"
```

**隔离原因不仅是"质量"，更是"权限"**：
- 技术部员工不应该能搜到法务部的合同文件
- 财务数据涉及保密，必须做访问控制
- 这是企业级部署的**硬性合规要求**

### 2.2 L4 Prompt 层 —— 大概率要调

不同部门的用户期望的回答风格完全不同：

| 部门 | 回答风格特征 | 示例 Prompt 片段 |
|---|---|---|
| 行政部 | 流程化、列点 | "请按步骤列出审批流程，每步标明角色和动作" |
| 技术部 | 代码精确、引用 API | "若涉及代码，必须给出可运行示例；引用函数签名" |
| 法务部 | 严谨、引用条款 | "每个结论必须引用合同/法规的具体条款编号" |
| 客服部 | 友好、口语化 | "用客户能理解的语言回答，避免专业术语" |
| 财务部 | 数字精确、带时间戳 | "所有金额保留两位小数，标明适用期间" |

## 3. 基本可共享的两层

### 3.1 L1 框架层 —— 100% 共享

```
MCP Server、Factory、HybridSearch、Tracing、Dashboard、Evaluation
```

这一层是代码，不承载业务，零成本复用。

### 3.2 L2 模型层 —— 90% 共享

**一个 LLM（如 GLM-4）+ 一个 embedding 模型（如 BGE-large-zh）** 给企业所有部门共用，理由：

1. **成本**：不同部门跑不同模型，GPU 资源翻倍、API 调用成本翻倍
2. **统一性**：答案风格一致性是企业形象的一部分
3. **维护**：升级模型时一处改动全部生效
4. **采购谈判**：统一模型，集中采购 API 额度更有议价空间

**什么时候才有必要换模型？**
- 英文文档密集的部门（国际业务部）→ 换成英文能力更强的 embedding
- 代码密集部门（技术部）→ 考虑 code-embedding 专用模型
- 涉密部门（法务/合规）→ 换成本地部署模型

这些是**例外**，不是默认。

## 4. 灰色地带：L3 参数层

不同部门可能差异显著的参数：

| 参数 | 行政部（FAQ 类） | 技术部（API 手册） | 法务部（合同） | 客服部（Q&A） |
|---|---|---|---|---|
| `chunk_size` | 300-500 | 800-1200（保代码块） | 1500+（法条需完整） | 300-500 |
| `splitter.strategy` | recursive | semantic | 按条款切（定制） | recursive |
| `retrieval.top_k_final` | 3-5 | 5-10 | 10+（多引证） | 3-5 |
| `rerank.backend` | none 或 cross_encoder | cross_encoder（必开） | cross_encoder + llm | none |
| `fusion.rrf_weight_dense` | 0.5 | 0.6（术语偏语义） | 0.4（条款偏关键词） | 0.5 |

**最佳实践**：**不要一开始就每部门单独调**。先用一套"默认最优配置"铺开，**根据评估结果再决定哪些部门需要单独调**。

## 5. 三阶段部署策略

### 阶段 1：单配置铺开（Week 1-2）

```
✅ 用一套默认 settings.yaml
✅ 每个部门建一个 collection，摄入各自文档
✅ 每个部门准备 20-30 条评估集（用 RAGAS TestsetGenerator 合成）
✅ 跑一遍 RAGAS，拿到每个部门的基线指标
```

**产出**：各部门指标基线表，像这样：

```
部门       context_recall  context_precision  faithfulness  answer_relevancy
---------- -------------- ------------------ ------------- ---------------
行政部     0.85           0.80               0.88          0.91
技术部     0.65           0.55               0.78          0.83
法务部     0.70           0.72               0.55          0.72
财务部     0.82           0.78               0.85          0.88
客服部     0.80           0.82               0.82          0.90
```

### 阶段 2：分诊优化（Week 3-4）

根据基线指标，分诊到以下四类：

| 类别 | 判断依据 | 处理方式 |
|---|---|---|
| 🟢 **默认配置够用** | 所有指标 > 0.75 | 不动 |
| 🟡 **检索层问题** | context_recall / context_precision < 0.7 | 调 L3 参数 |
| 🔴 **生成层问题** | faithfulness / answer_relevancy < 0.7 但 context_recall 正常 | 调 L4 prompt |
| ⚫ **模型能力不够** | 所有指标都低且调参无效 | 考虑 L2 换模型 |

以上面的示例表格为例：

- 行政部：默认配置够用 ✅
- 技术部：context_recall 低 → 开 semantic splitter + chunk_size 调到 1200 + 开 reranker
- 法务部：faithfulness 低（but recall 正常）→ 改 prompt 强制引用条款 + 开 llm reranker
- 财务部：默认配置够用 ✅
- 客服部：默认配置够用 ✅

### 阶段 3：配置分层管理（Week 5+）

在 `settings.yaml` 之上引入"部门覆盖层"。目录结构设计：

```
config/
├── settings.yaml              # 全局默认
└── departments/
    ├── admin.yaml             # 行政部覆盖（空或少量覆盖）
    ├── tech.yaml              # 技术部覆盖
    ├── legal.yaml             # 法务部覆盖
    ├── finance.yaml           # 财务部覆盖
    └── customer_service.yaml  # 客服部覆盖
```

示例覆盖文件：

```yaml
# config/departments/tech.yaml
splitter:
  strategy: semantic
  chunk_size: 1200
rerank:
  backend: cross_encoder
  enabled: true
retrieval:
  top_k_final: 8
# prompt 覆盖
prompt:
  system_template: |
    你是技术文档助手。回答时：
    1. 若涉及代码/API，必须引用真实函数签名
    2. 给出可运行的代码示例
    3. 标注版本兼容性
```

```yaml
# config/departments/legal.yaml
splitter:
  strategy: recursive
  chunk_size: 1500
rerank:
  backend: llm  # 法务对精度要求最高
retrieval:
  top_k_final: 12
prompt:
  system_template: |
    你是法务助手。回答时：
    1. 每个结论必须引用合同/法规的条款编号（如"第 3 条第 2 款"）
    2. 无明确依据时直接说"合同未涉及"
    3. 使用严谨正式的法律语言
```

**代码改造点**：在 `src/core/settings.py` 的 `load_settings()` 中增加合并逻辑：

```python
def load_settings(department_id: Optional[str] = None) -> Settings:
    base = _load_yaml("config/settings.yaml")
    if department_id:
        override_path = f"config/departments/{department_id}.yaml"
        if os.path.exists(override_path):
            override = _load_yaml(override_path)
            base = _deep_merge(base, override)
    return _parse_settings(base)
```

**生效公式**：`默认配置 + 部门覆盖 = 实际生效配置`。

## 6. 三种部署模式对比

### 模式 A：单实例 + 多 collection + 路由 ⭐ 推荐（中小企业）

```
┌─────────────────────────────────────┐
│         MCP Server (1 个实例)        │
│  ┌───────────────────────────────┐  │
│  │   请求路由 (by department_id)  │  │
│  └───────────────────────────────┘  │
│     │         │         │         │ │
│     ▼         ▼         ▼         ▼ │
│  [admin]  [tech]   [legal]  [finance]│
│                                      │
│  共享：LLM, Embedding, Reranker       │
└─────────────────────────────────────┘
              │
              ▼
        ┌──────────┐
        │ ChromaDB │
        │  多集合   │
        └──────────┘
```

**优势**：成本最低、维护简单、配置集中
**适用**：<10 部门，<1000 用户，无强合规隔离要求

### 模式 B：多实例 + 共享模型服务（中大型企业）

```
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ MCP (admin)  │  │ MCP (tech)   │  │ MCP (legal)  │
│ + 独立配置   │  │ + 独立配置   │  │ + 独立配置   │
└──────┬───────┘  └──────┬───────┘  └──────┬───────┘
       │                 │                 │
       └─────────────────┼─────────────────┘
                         ▼
            ┌────────────────────────┐
            │  共享模型服务 (LLM/Emb)  │
            │  via HTTP/gRPC         │
            └────────────────────────┘
```

**优势**：部门间配置隔离充分，故障不互相影响
**适用**：配置差异大的大型企业、有部门级 SLA 要求的场景

### 模式 C：完全独立部署（强合规场景）

每个部门从模型到数据库完全独立部署。

**适用**：涉密部门、金融合规、跨地域隔离
**代价**：成本最高、运维复杂
**建议**：除非必须，不要用

## 7. RAGAS 评估的角色

> 这是回到原始问题的关键：**每个部门都必须有自己独立的 RAGAS 评估集和基线**。

```
行政部 → golden_test_set_admin.json   → admin collection   → 基线 A
技术部 → golden_test_set_tech.json    → tech collection    → 基线 B
法务部 → golden_test_set_legal.json   → legal collection   → 基线 C
财务部 → golden_test_set_finance.json → finance collection → 基线 D
```

### 为什么必须每部门独立？

1. **独立验收**：每个部门要能回答"我的 RAG 达标了吗"——必须基于该部门自己的问题集
2. **定向优化**：指标告诉你哪个部门哪一层出了问题，才能定向调参
3. **防止回归**：改技术部配置时，跑一下行政部基线确保没误伤
4. **跨部门对比无意义**：技术部 context_recall=0.85 vs 法务部 0.70，不能说明哪个系统更好——语料难度本来就不同

### 评估集分布建议

| 部门 | 规模 | 构建重点 |
|---|---|---|
| 每个部门 | 40-80 条 | 覆盖该部门 **真实用户会问的问题** |

**建议**：每个部门找 2-3 位**一线员工**参与精修——他们最了解真实工作场景的问题长什么样。这一步远比调参数重要。

## 8. 决策 Checklist

部署到新部门时，按顺序判断：

```
[ ] 1. 建立独立 collection（必做）
[ ] 2. 用默认配置摄入文档
[ ] 3. 让该部门 2-3 位员工合作生成 40-80 条评估集
[ ] 4. 跑 RAGAS 拿基线
[ ] 5. 读基线 → 判断属于哪一类（见 §5 阶段 2）
[ ] 6. 只对"不达标"的部门做定向调整：
       - 检索差 → L3 参数
       - 生成差 → L4 prompt
       - 都差 → L2 模型
[ ] 7. 在 config/departments/{dept}.yaml 写覆盖配置
[ ] 8. 重跑 RAGAS 验证，打标为该部门 baseline
[ ] 9. 部门上线使用
[ ] 10. 每月回归一次 RAGAS，观察指标漂移
```

## 9. 常见坑与反模式

### ❌ 反模式 1：一开始就为每个部门调参数
**后果**：部署成本线性膨胀，维护地狱
**正解**：默认配置铺开 → 根据评估分诊 → 只调需要调的

### ❌ 反模式 2：把所有部门文档放一个 collection
**后果**：权限泄露、检索噪声大（财务问题召回了法务文档）
**正解**：每个部门一个 collection，强制隔离

### ❌ 反模式 3：用行政部的评估集评价技术部
**后果**：指标好看但不代表技术部真实体验
**正解**：每部门独立评估集

### ❌ 反模式 4：换模型"包打天下"
**后果**：换 GPT-4 后某些部门指标反降（专业领域过拟合通用模型不一定赢）
**正解**：先用评估说话，再决定换不换

### ❌ 反模式 5：只看总指标均值
**后果**：一个部门拉跨被其他部门掩盖，用户体验崩了还不自知
**正解**：每个部门独立看、设独立阈值

---

## 10. 一句话总结

> **共享框架与模型，隔离数据与提示词，按需微调参数，每部门独立评估。**

企业级 RAG 部署不是"为每个部门从头调一套系统"，而是"建立一个可复用的默认配置 + 一套基于 RAGAS 的分诊机制 + 针对性的部门覆盖层"。

**核心循环**：铺开默认配置 → 跑 RAGAS 评估 → 分诊出需要调的部门 → 定向调优 → 打基线 → 持续回归。
