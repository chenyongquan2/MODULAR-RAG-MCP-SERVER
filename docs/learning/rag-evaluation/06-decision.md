# 06 · 从分数到决策：这个改动到底算不算改进

> **专题**：[RAG 评估系统学习](README.md) 第 06 章
> **前置**：[05 章](05-meta-evaluation.md)（四类偏差）。不知道尺子有偏就直接看 delta，会把噪声当成绩。
> **本章目标**：拿到两份报告，能按固定次序判断这个 delta 能不能用、该不该采纳改动。
> **预计**：25 分钟
> 📖 **遇到不认识的词** → [术语速查表](glossary.md)（查表用，不用顺读）

> ### 用人话说，这章解决什么
>
> 上一章告诉你尺子有偏。那还怎么做决定？
>
> 本章处理最日常的那个场景：**这次考了 62 分、上次 60 分 —— 该不该说「进步了」？**
>
> 答案通常是「不该」，而且原因往往不是「2 分太少」，而是更荒谬的东西：**两次考的不是同一张卷子**、或者**这次的 6 道题里只批了 2 道**。
>
> 本章给你四道「闸门」，按顺序过一遍，就能判断手上这个分数差能不能用。
>
> 💡 一个提前预告：**工具会把毫无意义的分数差老老实实算给你看**，旁边挂一句小字说「这个不能比」。读不读那句小字，是你的事。

---

## 1. 评估的日常用途是回归，不是打分

01 章开头埋了一句：

> 【推断】评估真正的日常用途是**回归** —— 你改了一行代码，需要知道有没有把别的地方弄坏。**分数的绝对值远不如两次分数的差值有用。**

学完前五章，这句话可以说得更硬了：

**绝对值几乎不可解释。** `custom__recall = 0.42` 是好是坏？取决于金标是哪代标的、一条 case 值多少分、`k` 取了多少。这些全部变动之后，0.42 这个数字什么也不是。

**差值可解释，但有前提。** 而本章的全部内容就是那几条前提。

---

## 2. 基线机制

本项目的做法：把某一次运行标记为**基线（baseline）**，之后每次运行自动算出相对它的 delta 并写进报告【代码】。

报告里对应这几个字段：

```
baseline_id                 : "80a82405-..."          ← 参照的是哪一次
delta_aggregate_metrics     : { 每项指标的差值 }
delta_comparable            : true / false             ← 工具的可比性判断
delta_incomparable_metrics  : { 指标 -> 不可比的原因 }  ← 逐项说明
```

【代码】可比性判断在 [baseline_manager.py:310 `_find_incomparable_metrics`](../../../src/observability/evaluation/baseline_manager.py#L310)。

> ⚠️ **工具只负责标注，不负责拒绝。** 它会把一个毫无意义的 delta 老老实实算出来，旁边挂一句「这个不可比」。**读不读那句话是你的事** —— § 7 有一个真实例子，四道闸门全部不通过，delta 照样算了出来。

## 3. 判读 delta 的四道闸门

**按顺序过。任何一道不通过，后面的都不用看了。**

### 闸门 1：分母一样吗

看两份报告的 `metric_integrity.<指标>.valid_count`。

不一样就意味着 delta 里混着「分母变了」。回到 [05 章 § 5](05-meta-evaluation.md#5-偏差四幸存者偏差)：降级不是随机的，它系统性地偏向扔掉差样本，**所以分母缩小通常伴随分数虚高**。

> 特例：`custom__*` 四项永远不降级（不调 LLM），这道闸门对它们恒通过。

### 闸门 2：标注口径一样吗

看 `_labeling_method` / 报告里的 `labeling_method` 字段。

跨代比较时本项目会标 `delta_comparable: false`。实测新旧标准答案 Jaccard 只有 0.328（[04 章 § 5.3](04-golden-set.md#53-换代到底换出了什么一个数字)）—— **跨代 delta 几乎全是口径差，不是质量差。**

### 闸门 3：是同一份测试集、同一个集合、同一个 judge 吗

三个字段一起对：

```
test_set_path            两份必须相同   ← 不同卷子的分数不能比
collection               两份必须相同   ← 语料不同等于换了考纲
judge_llm_identifier     两份必须相同   ← 见 05 章 § 3
```

### 闸门 4：差异大到超过一条 case 的分辨率了吗

回到 [00 章 § 6](00-prerequisites.md#6-小样本一条-case-值多少分)：

| 测试集条数 | 一条 case 的分辨率 |
|---|---|
| 6 条 | 16.7% |
| 42 条 | 2.4% |

**把 delta 除以分辨率，换算成「几条 case」再判断。**

```
42 条上 delta = 0.048  →  2 条 case
6  条上 delta = 0.167  →  1 条 case
```

> 【推断】**小于 5% 的差异应默认按噪声处理**，除非你去逐条看了是哪几条变了、为什么变。这不是统计检验，只是一条防止自欺的经验线。真要下结论，做配对显著性检验（05 章 § 3.2 那种）。

## 4. `acceptance_status` 是怎么来的

报告里有个 `acceptance_status: pass / fail`。它的判定有**两个部分**：

```
① 8 项聚合指标逐项与 acceptance_thresholds 比较
② 降级率 ≤ evaluation.degradation.max_ratio（默认 0.05）
```

【代码】阈值在 [config/settings.yaml:340](../../../config/settings.yaml#L340)，降级率闸门在 [:358](../../../config/settings.yaml#L358)，判定逻辑在 [eval_runner.py:391-399](../../../src/observability/evaluation/eval_runner.py#L391)。

**第二条是后加的，而且是本项目一次真实教训的产物**：run `80a82405` 的降级率 54.8%，是门槛的 11 倍，而这个事实**在报告 JSON 里躺了很久没人读到** —— 因为它不在聚合指标里。

> 💡 **设计洞察**：`degraded_case_count` 早就有了，问题在于它**不参与任何判定**，于是没人看。把它接进 `acceptance_status` 之后，它从「一个可选的诊断字段」变成了「一道必过的闸门」。**一个不参与判定的指标，等于没有这个指标。**

阈值快照会一并写进报告（`acceptance_thresholds_snapshot`），所以历史报告即使阈值改过也能追溯。

## 5. 消融：只改一个变量

四道闸门管的是「能不能比」。这一节管的是「比出来的差异能不能归因」。

01 章开头那个例子：

> 就算真的变好了，是重排的功劳，还是你同时调的那个 `top_k` 的功劳？

**答案是：同时改两个就永远不知道。** 唯一的解法是一次只改一个变量，这在实验设计里叫**消融（ablation）**。

本项目做过的两次标准消融：

| 实验 | 冻结了什么 | 只变什么 |
|---|---|---|
| 融合权重校准（Feature-005） | 语料、金标、检索代码 | `fusion_weights.sparse` 从 0 扫到若干值 |
| judge 配对实验（05 章 § 3.1） | **query / answer / contexts / ground_truth 四元组** | judge 模型 |

第二个尤其值得学：**它把整条链路的输出冻成了数据文件**，于是「重跑」这个动作彻底不需要了。

> 💡 **可复用的形状**：想测 X 的影响，先问「我能不能把 X 之外的一切冻成文件」。能，就不会有归因问题。

## 6. 不要只看聚合数字

聚合值把 N 条 case 压成一个数，**压缩掉的信息往往才是结论**。

三件该做的事：

1. **按 tag 切片看**。报告里有 `aggregate_metrics_by_tag` 和 `per_tag_delta`，维度是 `content_type` / `difficulty`【代码】。总分不变但难题上掉了 —— 这是聚合值看不见的。
   > ⚠️ 切片样本量 < `tag_slice_min_samples`（默认 5）时会标 null + `_skipped_reason` —— 6 条的中文金标基本切不动。

2. **去看具体是哪几条 case 变了**。`case_results` 里每条都有完整的 query / answer / contexts。42 条上 0.048 的差异就是 2 条，**读那 2 条比看聚合值有用一百倍**。

3. **对齐方向再解读**。`hit_rate` 跌 `MRR` 涨不是矛盾（02 章 § 4.1），是「牺牲覆盖面换排序质量」。该不该接受取决于下游 LLM 实际读几条。

## 7. 演练：一个四道闸门全不通过的真实 delta

拿本项目一份真实报告走一遍。**这一节是本章的重点。**

【实测】run `5efa34ab`（2026-08-16）与它的基线 `80a82405`：

```
delta_hit_rate                          : +0.0476
delta_aggregate_metrics.faithfulness    : +0.111
delta_aggregate_metrics.context_precision: +0.126
delta_aggregate_metrics.answer_relevancy : -0.161
delta_comparable                        : true      ← 注意这个
```

看起来：三项涨、一项跌，整体像是个改进。**逐道闸门过一遍：**

| 闸门 | 检查 | 结果 |
|---|---|---|
| **1 分母** | 本次 `faithfulness.valid_count = 2`；基线 `metric_integrity = null`（早于该字段），只知道 `degraded_case_count = 23/42` | ❌ **分母未知 vs 分母为 2**，无法比较 |
| **2 口径** | 两份都是 `dense-top-k` | ✅ 通过 |
| **3 同一份测试集** | 本次 `golden_test_set_zh.json`（6 条中文）<br>基线 `golden_test_set_en.json`（**42 条英文**） | ❌ **完全不同的卷子** |
| **4 分辨率** | 6 条上的 `+0.0476`… 而 6 条的最小刻度是 **0.167** | ❌ **这个数在结构上不可能是真实差异** |

**四道闸门三道不通过。这个 delta 一条都不能用。**

而报告里 `delta_comparable` 写的是 `true` —— 它只检查了分母口径这一维。同一份报告的 `delta_incomparable_metrics` 里倒是八项全部标了不可比，原因是「基线早于 `metric_integrity`，分母未知」。

> ⚠️ **闸门 4 那条特别值得咀嚼**：6 条测试集上 `hit_rate` 只能取 0/6、1/6、2/6…… 的离散值，最小间隔 0.1667。**一个 0.0476 的 delta 在这个尺度上根本不存在** —— 它是跨测试集相减的产物（42 条的 0.6190 减 6 条的 0.6667）。**看到一个「不可能存在的刻度」，说明你在比两把不同的尺子。**

**这就是为什么必须自己会判读**：工具算了 delta，标了部分警告，但没有任何一处会拦住你把这份对比写进结论。

## 8. 决策清单

拿到「改了 X，分数变了」的场景，按这个次序走：

```
1. 四道闸门        →  这个 delta 能不能用
2. 换算成条数      →  差异有几条 case
3. 读那几条 case   →  为什么变
4. 尺子检查        →  这个改动和标注方法是不是对立的（05 章 § 2）
5. 对齐下游        →  LLM 实际读几条，哪个指标才对应真实收益
6. 记录条件        →  金标版本 / judge / collection / 阈值快照
```

> **第 4 步是学完 05 章之后新增的**。它在本项目里救过一次：重排指标全跌，但那是尺子在惩罚正确的改动 —— 若按前三步就下结论，会把一个有效模块判死。

## 9. 自测

<details><summary><b>Q1.</b> 为什么说分数的绝对值几乎不可解释？</summary>

它取决于金标是哪代标的、一条 case 值多少分、`k` 取了多少、judge 是谁、分母有没有缩。这些全变动之后，绝对值不承载信息。差值才可解释 —— 但需要四道闸门都通过。（§ 1、§ 3）
</details>

<details><summary><b>Q2.</b> 判读 delta 的四道闸门是什么？</summary>

① 分母一样吗（`metric_integrity`）；② 标注口径一样吗（`_labeling_method`）；③ 同一份测试集 / 集合 / judge 吗；④ 差异超过一条 case 的分辨率了吗。（§ 3）
</details>

<details><summary><b>Q3.</b> 6 条测试集上看到 <code>delta_hit_rate = +0.0476</code>，你的第一反应是什么？</summary>

**这个数不可能存在。** 6 条的 hit_rate 只能取 1/6 的整数倍，最小刻度 0.167。出现更细的刻度说明是跨测试集相减。（§ 7）
</details>

<details><summary><b>Q4.</b> <code>acceptance_status</code> 判什么？为什么把降级率也接进来？</summary>

① 8 项指标各自过阈；② 降级率 ≤ 5%。接进来是因为 `degraded_case_count` 早就存在但不参与判定，于是长期没人读到（54.8% 的降级率躺在报告里）。**一个不参与判定的指标等于没有。**（§ 4）
</details>

<details><summary><b>Q5.</b> 你想测「重排到底有没有用」，怎么设计？</summary>

冻结一切、只开关重排（消融）。但更重要的是第 4 步：**先检查尺子** —— `custom__*` 四项锚定 dense 输出，结构上惩罚重排，用它们测不出来。要么换 v2 金标，要么用 `context_precision`（唯一不锚定 chunk_id 的），要么用集成测试这种机制对照。（§ 5、§ 8）
</details>

<details><summary><b>Q6.</b> 总分没变，能说明这次改动无害吗？</summary>

不能。去看 `per_tag_delta`（难题上是不是掉了）和具体 case。聚合值压缩掉的信息往往才是结论。（§ 6）
</details>

## 本章小结

| 问题 | 答案 |
|---|---|
| 评估的日常用途 | **回归**，看差值不看绝对值 |
| 四道闸门 | 分母 / 口径 / 同一份测试集 / 分辨率 |
| 工具的边界 | **只标注不拒绝** —— `delta_comparable: true` 也可能完全不能比 |
| `acceptance_status` | 8 项过阈 **+ 降级率 ≤ 5%** |
