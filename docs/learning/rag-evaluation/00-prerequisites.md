## 先用人话说：这一章在干什么

整个专题在学的事，可以用一个比喻概括：**给 RAG 系统改卷子。**

把 RAG 当成一个学生，它答题分两步 ——

1. **翻书**：从资料库里找出几段可能有用的材料
2. **答题**：照着找到的材料写答案

你要给它打分。难点在于**你没法像批数学题那样对答案**：同一个意思有一百种说法，字面完全不同却都对。

**这一章不讲怎么打分**（那是 02、03 章的事）。这一章只做一件事：**把「改卷子」这套流程里的零件先认一遍。** 后面每一章都默认你认识这些零件，不认识就会读得很痛苦 —— 这也是为什么它排在最前面。

## 先认 9 个词（本专题 90% 的困惑来自这几个）

**不用背，看一眼有个印象就行**，后面遇到再回来查。每个词都会在本章里详细讲。

| 词 | 用人话说 | 打个比方 |
|---|---|---|
| **chunk（片段）** | 一份文档被切碎后的一小段，检索的最小单位 | 书里的**一页** |
| **chunk_id** | 每个片段的身份证号 | 页码 |
| **金标**（golden test set） | 出题人准备好的考卷：题目 + 参考答案 | 卷子 |
| **case** | 考卷上的**一道题** | 第 3 题 |
| **ground_truth** | 参考答案的**文字**版 | 「标准答案：因为会锁表」 |
| **expected_chunk_ids** | 参考答案的**页码**版：该翻到哪几页 | 「见第 12、37 页」 |
| **judge（裁判）** | 专门用来打分的那个 AI，它不参与答题 | 改卷老师 |
| **指标**（metric） | 把「好不好」算成一个 0~1 的数的某种算法 | 某种给分规则 |
| **降级**（degradation） | 裁判没能给出分数，这道题的这一项作废 | 这题没批，空着 |

> 💡 **最容易混的是 `ground_truth` 和 `expected_chunk_ids`** —— 它们是同一道题的两种参考答案（一份文字、一份页码），给两组完全不同的打分规则用。§ 3 会细讲。

## 1. 评估的基本单位是 chunk，不是文档

### 1.1 为什么切开

RAG 不能把一整份 PDF 塞给 LLM —— 上下文窗口装不下，且大部分内容与问题无关。所以入库前要**切块**：

```
一份文档 (Document)  ──[splitter]──>  几十到几千个片段 (Chunk)
```

检索返回的是**片段**，评估自然也以片段为单位。这条看起来平淡，但它决定了后面所有指标的形状：

> **「答对了没有」在检索段被翻译成了「捞上来的片段 ID，和标准答案列的片段 ID，重合了多少」。**

### 1.2 一个真实的 chunk_id 长什么样

本项目的 chunk_id 是这样的【实测】（读自 `tests/fixtures/golden_test_set_zh_v2.json`）：

```
C:\workspace\MODULAR-RAG-MCP-SERVER\ingest_source\MetaTrader5SDK_Chinese.chm_2835_610f192b
└──────────────────── 源文件绝对路径 ─────────────────────┘ └──┘ └──────┘
                                                          序号   内容哈希
```

三件事值得注意：

- **它带绝对路径**。换机器、换目录，同一份文档会产出不同的 chunk_id —— 金标就跟着失效了。
- **它带序号**。重新切分（换 splitter 或改 chunk_size）会让序号整体错位，**旧金标的 ID 会大面积对不上**。
- **它带内容哈希**。同样内容重复入库不会产出两个不同 ID。

> ⚠️ **推论（后面会反复用到）**：金标里的 `expected_chunk_ids` 是**绑定在一次具体的切分与入库结果上的**。语料重切、集合重建之后，金标不重新标注就不能用。这就是为什么本项目在评估入口做了 `chunk_id` 存在性校验【代码】（`evaluation.chunk_id_validation`，[config/settings.yaml:382](../../../config/settings.yaml#L382)）—— 它挡的正是这类「ID 悄悄全部失效」的情况。

### 1.3 检索返回的不是「对/错」，是一个排好序的列表

第二个必须先建立的直觉：**检索没有「命中」这个二值概念，它给的是相似度排序**。

```
查询 → 编码成向量 → 与库里每个 chunk 向量算相似度 → 从高到低排序 → 取前 k 条
```

所以一次检索的输出长这样（k = 10）：

```
rank 1  chunk_2835   相似度 0.83
rank 2  chunk_2552   相似度 0.79
...
rank 10 chunk_0467   相似度 0.61
```

**「排第几」是免费附赠的信息，而且它很重要** —— 这就是为什么检索指标里有一半（MRR、nDCG）是在量排序，而不只是量「有没有」。第 02 章五个指标的差异，本质上全都源于「怎么使用这个 rank 信息」。

**这一节撑起后面**：02 章 § 1 直接从「相关性标注」讲起，默认你已经知道被标注的对象是 chunk、检索结果是有序列表。

## 插曲：为什么需要 8 个指标，而不是 1 个

**下一节会甩给你一份真实报告，上面有 8 个指标名。先看这一节，否则那 8 个名字就是 8 个需要死记的符号。**

这一节不解释每个指标怎么算（那是 02、03 章的事）。它只回答一个问题：**为什么会有这么多？**

### 从最自然的想法开始：给一个总分

批完一张卷子给个「62 分」。对学生够用了 —— 但**对修系统完全没用**。

因为你要的不是「知道它考了多少分」，而是**「知道该改哪里」**。而「62 分」这个数，对「该改哪里」一个字都没说。

**下面每一次「拆」，都是因为上一层的数答不了一个具体的问题。**

### 第一次拆：总分答不了「该改哪里」

62 分。**是没翻到该看的那页，还是翻到了但瞎写？**

| 是哪种病 | 该吃什么药 |
|---|---|
| 没翻到 | 改检索：换 embedding、改切分方式、加关键词搜索 |
| 翻到了但瞎写 | 改生成：改 prompt、换更强的模型、要求标注引用 |

**两副药完全不相干。** 拿着一个总分，你只能瞎试 —— 见过太多「换了个更强的模型但答案还是错」的案例，因为病在检索段，换生成模型是在给错的器官吃药。

→ **所以至少要拆成两个数：检索段一个，生成段一个。**（这是 [01 章](01-mental-model.md) 的全部内容）

### 第二次拆：检索段一个数还是不够

假设「翻书翻得怎么样」给一个数：**0.5**。

下面三种情况**都可能给出 0.5**，但它们是完全不同的病：

| | 实际发生了什么 | 该怎么改 |
|---|---|---|
| **A** | 一半的题**连一页有用的都没翻到** | 根本没找到 → 换 embedding / 加关键词搜索 |
| **B** | 每题都翻到了有用的页，但**排在第 8 页之后**（而学生只看前 3 页） | 找到了但排序烂 → **加重排** |
| **C** | 每题都翻到 1 页有用的，但**其实该翻 5 页** | 找得不全 → 加大返回条数 / 改切分 |

**一个数分不出 A / B / C，而这三种病的药也完全不同。** 于是就有了四个专门的问法：

| 这个数专门回答 | 它的名字 | 专抓哪种病 |
|---|---|---|
| **至少翻到一页有用的了吗？** | `hit_rate` | **A**（彻底抓瞎） |
| **第一页有用的，排第几？** | `mrr` | **B**（排序烂） |
| **该翻的页，翻到了几成？** | `recall` | **C**（找不全） |
| **整体排序质量如何？**（综合位置和数量） | `ndcg` | B + C 的综合 |

> 💡 **这就是「为何需要存在」的答案**：
>
> **每个指标都是为了回答一个「上一个指标答不出的问题」而存在的。**
>
> 它们不是四种「差不多的算法」让你挑一个用，而是**四个不同的问题**。所以看报告时不该问「哪个指标最重要」，该问「我现在想知道哪件事」。

### 第三次拆：生成段也有两种病

「瞎写」也不是一种病：

| 病 | 长什么样 | 这个数叫 |
|---|---|---|
| **编** | 材料里压根没这句话，模型自己造的 | `faithfulness`（忠实度） |
| **答偏** | 每句话都有出处，但**没回答你问的那个问题** | `answer_relevancy`（答案相关性） |

### 还剩一块中间地带

材料捞上来了 —— 但**够不够、干不干净**？这既不是纯检索（不只看页码对不对，还要看内容），也不是生成：

| 问什么 | 这个数叫 |
|---|---|
| 参考答案里的每句话，材料里都有出处吗？（**够不够**） | `context_recall` |
| 捞上来的材料，有用的比例高吗、排前面了吗？（**干不干净**） | `context_precision` |

### 于是就是 8 个

```
                        ┌─ hit_rate            至少翻到一页了吗
        ┌─ 检索段 ──────┼─ mrr                 第一页排第几
        │               ├─ recall              该翻的翻了几成
        │               └─ ndcg                整体排序质量
一次评估 ┤
        ├─ 中间地带 ────┬─ context_recall      材料够不够
        │               └─ context_precision   材料干不干净
        │
        └─ 生成段 ──────┬─ faithfulness        有没有编
                        └─ answer_relevancy    有没有答到点上
```

**8 个不是「指标越多越好」的堆砌，是 8 个互相答不了的问题。**

### 指标名字怎么读（这个不讲会一直懵）

报告里的名字长这样：`custom__hit_rate`、`ragas__faithfulness`。**双下划线只是分隔符**，前面那截是「**谁算的**」：

| 前缀 | 谁算的 | 花钱吗 | 会算不出来吗 |
|---|---|---|---|
| `custom__` | **本项目自己写的代码**，纯算术 | ❌ 不花 | ❌ 永远算得出来 |
| `ragas__` | **第三方库 RAGAS**，靠 AI 判 | 💰 花 | ⚠️ **会失败**（§ 5 的主题） |

> **看到一个指标名，先看前缀。** 这一眼就决定了：这个数可不可靠、要不要花钱、以及**它有没有可能是假的**。
>
> 巧的是这个分界和上面的拆分几乎重合：**检索段那四个全是 `custom__`（读页码，纯算术），中间地带和生成段那四个全是 `ragas__`（读文本，必须 AI 判）。** 记住这一条，8 个名字就有秩序了。

### 别背名字，记两个前缀 + 六个问题

```
custom__  = 自己算的，免费，铁打的     ragas__ = AI 判的，花钱，会失败
           ├ 有没有翻到                        ├ 材料够不够
           ├ 排第几                            ├ 材料干不干净
           ├ 全不全                            ├ 有没有编
           └ 排序整体好不好                    └ 有没有答到点上
```

**下一节那份报告，就照这个结构去读。**

## 2. 一次评估运行，完整走一遍

这是本章最该花时间的一节。**大部分「这个数字到底从哪来的」的困惑，都是因为没在脑子里跑过一遍这条流水线。**

### 2.1 六步

命令：

```bash
python -u scripts/evaluate.py --pretty --collection default_text-embedding-v4
```

发生的事【代码】（主流程在 [eval_runner.py:629 `_evaluate_case`](../../../src/observability/evaluation/eval_runner.py#L629)）：

| # | 步骤 | 输入 | 输出 | 花钱吗 |
|---|---|---|---|---|
| 1 | 读金标 | `golden_test_set_zh.json` | N 条 case（每条含 query / ground_truth / expected_chunk_ids） | ❌ |
| 2 | 校验 chunk_id | 每条的 `expected_chunk_ids` | 存在性检查，不存在就直接失败 | ❌ |
| 3 | **检索** | `query` | `retrieved_chunk_ids`（有序）+ `contexts`（片段原文） | 💰 embedding 调用 |
| 4 | **生成答案** | `query` + `contexts` | `answer` | 💰 LLM 调用 |
| 5a | **算 custom 指标** | `retrieved_chunk_ids` × `expected_chunk_ids` | hit_rate / mrr / recall / ndcg | ❌ **纯集合运算** |
| 5b | **算 RAGAS 指标** | `query` / `answer` / `contexts` / `ground_truth` | 四项 ragas 指标 | 💰💰 **judge LLM，每条 case 十几次调用** |
| 6 | 聚合 + 归档 | 所有 case 的指标 | `logs/evaluation_reports/<run_id>.json` | ❌ |

**盯着第三列看**。同一次运行里，**每个指标读的字段是不一样的**：

- `custom__*` 四项只看两列 ID，**完全不碰文本**
- `ragas__context_*` 看 `contexts` + `ground_truth`
- `ragas__faithfulness` 看 `answer` + `contexts`，**根本不看 ground_truth**
- `ragas__answer_relevancy` 看 `answer` + `query`

这就是 02 章 § 6.3 那个「两个都叫 recall 却差三倍」的机械解释：**它们读的根本不是同一批数据**。

### 2.2 步骤 4 有个容易漏的含义

第 4 步是**跑真实的答案生成链路**，不是从金标里读答案。所以：

> **评估报告里的分数，同时受检索、生成 prompt、生成模型三者影响。**

【代码】答案由 `response_builder.build()` 产出（[eval_runner.py:659](../../../src/observability/evaluation/eval_runner.py#L659)）。这带来一条重要纪律：

> ⚠️ 如果生成用的 LLM `temperature` 不是 0，**同一份代码跑两次分数就会不同**。想做 A/B 对照时，这个波动会和你要测的效应混在一起，无法归因。CLAUDE.md 里那条「不要用重跑 `evaluate.py` 做 judge 对照」讲的就是这件事 —— 正确做法是拿归档报告里已经存好的 `answer` / `contexts` 四元组重新判定。

### 2.3 一条真实 case 的完整数据

来自 run `5efa34ab`【实测】（读自 `logs/evaluation_reports/5efa34ab-fe4e-498e-abf7-b69018dcf51a.json`，2026-08-16，中文 6 条）：

```
query        : 只能在主服务器上运行的应用程序才能添加或更新配置吗？
ground_truth : 是的，文档明确说明只能从在主服务器上运行的应用程序添加或更新配置。
               对于其他应用程序，将返回错误代码 MT_RET_ERR_NOTMAIN。
contexts[0]  : "注意\n\n只能从主服务器上运行的应用程序添加或更新配置。对于所有其他
                应用程序，将返回响应代码[MT_RET_ERR_NOTMAIN](retcodes_api.htm)。..."
answer       : 是的，只能从主服务器上运行的应用程序添加或更新配置。对于所有其他应用
               程序，将返回响应代码 `MT_RET_ERR_NOTMAIN` [1][2][3]...[10]。

metrics:
  custom__hit_rate         1.0
  custom__mrr              1.0
  custom__recall           0.2
  custom__ndcg             0.3392
  ragas__answer_relevancy  0.8375
  ragas__context_recall    1.0
  ragas__faithfulness      nan     ← 注意这两个
  ragas__context_precision nan
degradation_reasons:
  {'ragas__faithfulness': 'unparseable', 'ragas__context_precision': 'unparseable'}
```

**这条 case 值得反复看**：答案明显是对的（和 ground_truth 几乎逐字一致），`hit_rate` 和 `mrr` 都是满分，但 `custom__recall` 只有 0.2，而两项 RAGAS 指标干脆算不出来。

- `recall = 0.2` 是因为金标列了 5 个期望 chunk，只捞到 1 个 —— 但答案已经完全正确了。**说明那 5 个 ID 里至少 4 个不是回答这个问题的必需品。** 这是第 04、05 章的主题。
- 两个 `nan` 是 judge 输出解析失败。**它们不会让报告报错，只会悄悄退出平均。** 这是 § 5 的主题。

**这一节撑起后面**：01 章 § 5 让你「分段定位」、02 章 § 6.3 让你解释两个 recall 的差距、05 章讲降级 —— 全都建立在你知道这条流水线上每一步产出什么。

## 3. 金标文件的字段解剖

### 3.1 一条 case 的全部字段

【实测】（读自 `tests/fixtures/golden_test_set_zh.json`）：

```json
{
  "query": "只能在主服务器上运行的应用程序才能添加或更新配置吗？",
  "ground_truth": "是的，文档明确说明只能从在主服务器上运行的应用程序添加或更新配置。对于其他应用程序，将返回错误代码 MT_RET_ERR_NOTMAIN。",
  "expected_chunk_ids": [ "...chm_2401_9ff41a18", "...chm_2886_a5237051", … 共 5 条 ],
  "expected_sources": [],
  "tags": { "content_type": "text", "difficulty": "simple",
            "language": "zh", "doc_version": "v1" }
}
```

逐字段说明**谁消费它**（对照 § 2.1 的表）：

| 字段 | 是什么 | 谁读它 |
|---|---|---|
| `query` | 提给系统的问题 | 检索（步骤 3）、`answer_relevancy` |
| `ground_truth` | **参考答案文本**，给人和 judge 看 | `context_recall`、`context_precision` |
| `expected_chunk_ids` | **期望捞到的片段 ID 列表** | 四项 `custom__*`，**仅此而已** |
| `expected_sources` | 期望命中的源文件。**本项目所有真实金标里全空**【实测】 | `source_hit_rate` —— 因此该字段在报告里**恒为 0**，含义是「没标过」不是「没命中」（[07 章 §⑤](07-this-project.md)） |
| `tags` | 切片维度 | by-tag 聚合（看「难题上是不是特别差」） |

> ⚠️ **必须记住的一条**：`ground_truth` 和 `expected_chunk_ids` 是**两种完全不同的「标准答案」**，供给两组互不相干的指标。新手常把它们当成一件事的两种写法 —— 不是。深文 [golden-test-set-explained.md § 2](../golden-test-set-explained.md) 专门讲这个分岔。

### 3.2 顶层元数据

同一个文件的顶层还有一批 `_` 开头的字段，它们**不参与计算，但决定你能不能相信这份金标**：

```
version                     : "v0.1-partial"       ← 金标自己的版本
_labeling_method            : "pooled-llm-judged"  ← expected_chunk_ids 是怎么挑的（关键！）
source_corpus_collection    : "default"            ← 在哪个集合上标的
_labeling_metadata          : { labeling_llm_identifier, mean_dense_jaccard, judge_failed_count, … }
_review_metadata            : { 精修各路径计数、阈值快照、抽样合规率 }
```

`_labeling_method` 是**第 05 章整章的入口**。本项目有两个取值：

| 取值 | 含义 | 一句话 |
|---|---|---|
| `dense-top-k` | 拿参考答案去 dense 检索，top-5 就是标准答案 | **标准答案是 embedding 挑的** |
| `pooled-llm-judged` | 多路召回取并集，再让 LLM 逐条判 0-3 分 | 标准答案是另一个 LLM 挑的 |

现在只要记住「**标准答案本身也是某个模型的产物**」这一件事。为什么它是个大问题，05 章讲。

## 4. 「LLM 当裁判」不神秘：它就是一次普通 API 调用

这是新手最容易把它想得太玄的地方。

### 4.1 锚点：你已经会了

你写过这种代码：

```python
resp = client.chat.completions.create(
    model="...",
    messages=[{"role": "user", "content": "把下面这段翻译成英文：..."}],
)
text = resp.choices[0].message.content
```

**LLM-as-judge 就是同一个函数，只是 prompt 换成了「请你判定」，并要求它按固定格式回答。** 没有任何特殊 API、特殊模型类别、特殊调用方式。

本项目的 judge 就配在 `settings.yaml` 里，和普通 LLM 用同一套 provider 机制【代码】（[config/settings.yaml:184](../../../config/settings.yaml#L184)）：

```yaml
evaluation:
  judge_llm:
    provider: glm
    model: minimax/minimax-m2.7
    temperature: 0.0          # 判定要尽量确定，所以取 0
```

### 4.2 那它凭什么吐出 0.889 这种连续分数

**不是让模型直接打分。** RAGAS 的套路是「**拆开 → 逐条判是/否 → 数比例**」，分数是算出来的，不是模型说的。

以 `faithfulness` 为例【文献】：

```
第 1 步（一次 LLM 调用）：把 answer 拆成原子陈述
   answer → ["MT5 建议按账户分别执行组操作",
             "批量操作会锁表",
             "该限制自 build 2000 起生效"]

第 2 步（一次 LLM 调用）：拿 contexts 逐条判「能不能被支撑」
   陈述 1 → 能  (1)
   陈述 2 → 能  (1)
   陈述 3 → 不能(0)   ← 编的

第 3 步（纯算术，没有 LLM）：
   faithfulness = 2 / 3 = 0.667
```

**为什么要先拆**：直接问「这段回答有没有依据」只能得到一个笼统的 yes/no，而真实回答通常是「大部分有依据、一句是编的」。拆开才有分辨率。这个「拆解 → 逐条判 → 求比例」的模式在 RAGAS 四个指标里**反复出现**，记住它，03 章会省一半力气。

### 4.3 顺带认识一个词：NLI

第 2 步那个「陈述 X 能不能被 contexts 支撑」的判断，在 NLP 里有个正式名字：**自然语言推理（Natural Language Inference, NLI）**【文献】。给定一段「前提」和一句「假设」，判断三选一：

| 关系 | 含义 |
|---|---|
| entailment（蕴含） | 前提能推出假设 → 支撑 |
| contradiction（矛盾） | 前提否定假设 |
| neutral（中立） | 前提既不支持也不否定 |

RAGAS 把它简化成了二值（支撑 / 不支撑）。你会在 RAGAS 文档和论文里频繁看到 NLI 这个词，它指的就是这一步。

### 4.4 judge 会失败，而且失败得很安静

judge 是一次普通 API 调用 ⟹ **它会以普通 API 调用的所有方式失败**。本项目把失败原因做了机械分类【代码】（[src/core/types.py:588](../../../src/core/types.py#L588)）：

| 原因 | 含义 |
|---|---|
| `empty_response` | judge 返回空串。本项目在标注路径踩过：`max_tokens` 给少了，模型没写完就被截断 |
| `unparseable` | 返回了内容，但不符合 RAGAS 期待的结构，解析不出判定 |
| `timeout` | 判定调用超时 |
| `upstream_error` | 上游拒绝（鉴权、限流、模型下架）。本项目所在网关**模型下架是常态** |
| `unknown` | 归不进上面任何一类。**不是垃圾桶** —— 它的占比本身就是「归因能力有没有盲区」的指标 |

⚠️ **`unparseable` 是最常见的一种，而它的根因往往在评估之外** —— 「怎么让模型稳定返回可被代码消费的结构」是一个独立主题，本项目另有专题：[结构化输出学习专题](../structured-output/README.md)。本专题只需要你知道：**judge 失败是常态，不是异常**。

**这一节撑起后面**：03 章讲四个 RAGAS 指标的算法、05 章讲 judge 偏差 —— 都默认你知道 judge 只是一次会失败的普通调用。

## 5. 平均值的分母是会变的

这是本章**最反直觉、也最值钱**的一节。

> 📖 **第一遍只读 5.1 和 5.2 就够了**，5.3 / 5.4 可以等读到 03 章再回来。

### 先讲个场景（一个术语都不用）

一张卷子 6 道题，改卷老师批到第 2 题时，看不懂学生写的是什么，**跳过了**。第 4、5、6 题也一样跳过。

最后他把批出来的那 **2 道题**的分数一平均，报上去：

> **「满分！」**

这句话不算撒谎 —— 那 2 道题确实满分。但它**绝对不是这张卷子的真实水平**，因为跳过的 4 道题很可能恰恰是学生答得烂的（看不懂往往就是因为答得乱）。

**问题的要害不在「老师跳过了题」，在于那份报告上只写了「满分」，没写「6 道题里只批了 2 道」。**

这件事在本项目的评估里**天天发生**。下面把这个场景翻译成机器的语言。

### 5.1 机器怎么处理「没批出来」的题

上一节（§ 4.4）说过：裁判是一次普通的 API 调用，它会失败。失败时这道题的这个指标就算不出来。

算不出来的地方，程序里会放一个特殊值 **`NaN`**（读作「囡」，Not a Number，意思就是「这儿不是一个数」）。它有个很恶劣的性质 —— **一旦混进去，整列平均值都毁了**：

```python
>>> import math
>>> vals = [1.0, 0.8, math.nan]
>>> sum(vals) / len(vals)
nan                      # ← 一个 NaN 污染整列
```

所以当 judge 失败、某条 case 的某个指标算不出来时，实现**必须**做个选择：要么让整个聚合值变成 `nan`（报告直接不可用），要么**把这条排除掉**。

本项目选了排除【代码】（[eval_runner.py:350-381](../../../src/observability/evaluation/eval_runner.py#L350)）：NaN 不计入分母。

**这个选择本身是对的。** 但它的副作用是：

> **分母静默收缩 —— 报告里那个数，不一定是全样本的均值。**

### 5.2 一个真实到扎心的例子

run `5efa34ab`【实测】，中文金标 6 条：

```
aggregate_metrics:
  ragas__faithfulness      1.0      ← 满分！
  ragas__context_precision 0.8906
  custom__hit_rate         0.6667
```

看起来 faithfulness 完美。但同一份报告里还有一个字段：

```
metric_integrity:
  ragas__faithfulness      { valid_count: 2, degraded_count: 4,
                             degradation_ratio: 0.667, reasons: {unparseable: 4} }
  ragas__context_precision { valid_count: 3, degraded_count: 3,
                             degradation_ratio: 0.5,   reasons: {unparseable: 3} }
  custom__hit_rate         { valid_count: 6, degraded_count: 0, ... }
```

**那个 1.0 是 2 条样本的均值，不是 6 条。** 6 条里 4 条的 judge 判不出来，被悄悄扔了。存活下来的两条恰好都满分 —— 这叫**幸存者偏差**，不是质量证据。

对比一下 `custom__hit_rate`：`valid_count = 6`，分母完整。**纯计算类指标不会降级**（§ 2.1 表里它不花钱、不调 LLM），只有 LLM 判定类会。

### 5.3 两个字段的分工

| 字段 | 粒度 | 回答什么 |
|---|---|---|
| `degraded_case_count` | case 级 | 有多少条 case **至少有一个**指标算不出来 |
| `metric_integrity` | **指标级** | **每个指标各自的分母是多少** |

【代码】前者是老字段（向后兼容），后者是 change `evaluation-degradation-governance` 新加的真相来源（[src/core/types.py:616](../../../src/core/types.py#L616)）。**看 RAGAS 分数前先看 `metric_integrity`。**

### 5.4 直接推论：两次运行可能根本不可比

如果 run A 的 faithfulness 分母是 27，run B 是 42，那么 `B - A = +0.03` 这个 delta **同时包含了「质量变了」和「分母变了」两件事，无法拆开**。

本项目把这条写进了报告【实测】—— 同一份 `5efa34ab` 里：

```
delta_aggregate_metrics.ragas__faithfulness : +0.111
delta_incomparable_metrics.ragas__faithfulness :
  "baseline report predates metric_integrity and had 23 degraded case(s);
   per-metric denominators unknown"
```

**delta 算出来了，同时旁边挂着一句「这个 delta 不可比」。** 这是 06 章的核心纪律。

**这一节撑起后面**：03 章的分数、05 章的降级归因、06 章的 delta 判读 —— 全部依赖你先接受「分母会变」这件事。

## 6. 小样本：一条 case 值多少分

新手看到 `0.6190 → 0.6667` 会觉得「涨了 4.8%，是个提升」。先算一下这 4.8% 是几条 case。

| 测试集条数 | 一条 case 翻转 = hit_rate 变动 |
|---|---|
| 6 条 | **16.7%** |
| 42 条 | **2.4%** |
| 100 条 | 1.0% |
| 500 条 | 0.2% |

本项目的中文金标是 **6 条**，英文是 **42 条**【实测】。所以：

- 中文集上任何小于 16.7% 的差异**在结构上不可能存在** —— 分数只能是 0/6、1/6、2/6…… 的离散取值
- 英文集上 0.048 的 hit_rate 差异 = **恰好 2 条 case**

> 【推断】42 条上 2 条 case 的翻转，是不是「真实改进」？没有统计检验就无法回答。经验上，**小样本上小于 5% 的差异应默认按噪声处理**，除非你去逐条看了是哪几条变了、为什么变。这是 06 章「不要只盯聚合数字」的量化理由。

再看一条更狠的：`0.6190 → 0.6667` 这个 delta，实际是**跨测试集**的 —— 前者 42 条英文，后者 6 条中文【实测】（run `5efa34ab` 的 `baseline_id` 指向 run `80a82405`，而两者 `test_set_path` 一个是 `golden_test_set_en.json` 一个是 `golden_test_set_zh.json`）。

**不同测试集之间的分数没有任何可比性**，就像用两张不同的卷子的分数比较两个学生。工具算了这个 delta，但它没有意义 —— **这正是「必须自己会判读」的原因，报告不会替你拒绝无意义的比较。**

## 8. 自检清单

回答开头那 7 个问题。答不上就回对应小节。

<details><summary><b>Q1.</b> 为什么以 chunk 为单位？chunk_id 长什么样、由什么决定？</summary>

因为 RAG 检索返回的就是片段，不是整份文档。chunk_id 形如 `<源文件绝对路径>_<序号>_<内容哈希>`，由**路径 + 切分方式 + 内容**共同决定 —— 所以换机器、重切分都会让旧金标的 ID 失效。（§ 1）
</details>

<details><summary><b>Q2.</b> 为什么需要 8 个指标，给一个总分不行吗？</summary>

不行 —— 总分答不了「**该改哪里**」。每一次拆分都是因为上一层答不了一个具体问题：总分分不清「没翻到」还是「瞎写」（→ 拆两段）；检索段一个数分不清「彻底没找到 / 找到了但排最后 / 找到了但不全」（→ 拆四个）；生成段分不清「编的」还是「答偏了」（→ 拆两个）；再加中间地带两个 = 8 个。

**每个指标都是为了回答一个「上一个指标答不出的问题」而存在的。**（见 § 插曲）
</details>

<details><summary><b>Q3.</b> 跑一次评估发生了哪几步？哪几步花钱？</summary>

六步：读金标 → 校验 chunk_id → **检索**（💰 embedding）→ **生成答案**（💰 LLM）→ 算指标（custom 免费 / **RAGAS 💰💰**）→ 聚合归档。四项 `custom__*` 只读两列 ID，一次 LLM 都不调。（§ 2.1）
</details>

<details><summary><b>Q4.</b> `ground_truth` 和 `expected_chunk_ids` 分别喂给谁？</summary>

`ground_truth`（文本）→ `ragas__context_recall` / `context_precision`；`expected_chunk_ids`（ID 列表）→ 四项 `custom__*`。两者互不相干，**不是同一件事的两种写法**。（§ 3.1）
</details>

<details><summary><b>Q5.</b> LLM-as-judge 在代码里是什么形态？0~1 的分怎么来的？</summary>

就是一次普通 `chat.completions.create`，prompt 换成「请判定」。分数**不是模型直接说的**，而是「拆成原子陈述 → 逐条判是/否 → 数比例」算出来的。（§ 4）
</details>

<details><summary><b>Q6.</b> `faithfulness: 1.0` 可能只是 2 条样本的均值吗？怎么看出来？</summary>

可能，而且真实发生过。看报告的 `metric_integrity.<指标>.valid_count` —— run `5efa34ab` 里它是 **2**（另外 4 条 `unparseable` 被排除）。**聚合值本身完全看不出分母。**（§ 5.2）
</details>

<details><summary><b>Q7.</b> 6 条测试集上，一条 case 翻转 hit_rate 变多少？</summary>

**16.7%**。所以中文金标上任何小于 16.7% 的差异在结构上不可能存在；英文 42 条上 0.048 的差异 = 2 条 case。（§ 6）
</details>

<details><summary><b>Q8.</b> 三处的 recall / precision 是同一个东西吗？</summary>

不是。判别窍门：**看它读 ID 还是读文本**。`custom__recall` 读 ID（纯集合运算），`ragas__context_recall` 读文本（LLM 逐句判归因）。实测同一批结果两者可以是 0.30 与 0.83。（见 [术语速查表 § 2](glossary.md)）
</details>
