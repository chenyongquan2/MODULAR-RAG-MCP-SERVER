## 1. 先问：为什么需要评估

假设你给 RAG 系统加了一个重排模块。你拿三个问题试了试，感觉答得更好了。

**这个「感觉」有三个致命问题**：

1. **样本太小** —— 三个问题里有两个变好，可能只是这三个问题恰好受益。40 个问题里可能有 25 个变差。
2. **不可重复** —— 明天你再试，记不清昨天的答案长什么样，无法对比。
3. **无法归因** —— 就算真的变好了，是重排的功劳，还是你同时调的那个 `top_k` 的功劳？

评估要解决的就是这三件事：**把主观感觉变成可重复、可对比、可归因的数字。**

> 【推断】新手常把评估理解成「给系统打个分证明它好」。这是错的定位。评估真正的日常用途是**回归**——你改了一行代码，需要知道有没有把别的地方弄坏。分数的绝对值远不如两次分数的差值有用。

## 2. 评估的本质是造一个裁判

理想的裁判是人：找领域专家，读问题、读检索到的材料、读答案，给个判断。这是**唯一真正可信的**评估。

但人有三个缺点：贵、慢、每天状态不一样。40 个问题 × 每次改代码都要重跑 = 做不起。

所以整个 RAG 评估领域在做的事，可以用一句话概括：

> **造一个比人便宜、比人一致、但一定比人差的裁判。**

这句话值得记住 —— **后面所有的坑，都是「比人差」这三个字在不同地方冒出来**：

| 「比人差」表现在哪 | 具体后果 | 在第几层处理 |
|---|---|---|
| 裁判不理解语义，只能比对 ID | 换个说法表达同一个意思，判为不相关 | 02 检索指标 |
| 裁判是个 LLM，有自己的偏好 | 偏爱长答案、偏爱排在前面的、偏爱自家模型的输出 | 03 生成指标 |
| 标准答案本身是机器造的 | 标准答案错了，越接近它分越高 | 04 测试集 |
| 造标准答案的方法自带立场 | 用检索器 A 标注，就会偏袒 A —— 循环论证 | 05 元评估 |

**没有一层能做到「和人一样」。** 学评估不是学怎么消除这些误差，是学**每个数字带着多少误差、什么时候可以忽略、什么时候会把你带沟里**。

## 3. 三条必须先划清的边界

新手的混乱往往来自三组概念糊在一起。先分清楚，后面会轻松很多。

### 3.1 离线评估 vs 在线评估

| | 离线评估 | 在线评估 |
|---|---|---|
| 怎么做 | 拿一套固定测试集，跑分 | 真实用户流量做 A/B、看点踩率 |
| 优点 | 快、便宜、可重复 | 反映真实效果 |
| 缺点 | 测试集不等于真实用户问题 | 慢、要流量、有风险 |
| 本专题 | ✅ 讲这个 | ❌ 不讲 |

**你现在学的全部是离线评估。** 离线分数高不等于用户满意 —— 这是离线评估的天花板，不是可以修的 bug。

### 3.2 三个不同的东西：指标 / 测试集 / 元评估

| 概念 | 回答的问题 | 例子 |
|---|---|---|
| **指标** | 怎么把「好」变成一个数 | MRR = 0.5 |
| **测试集** | 拿什么当标准答案 | 42 条问题 + 每条的正确 chunk 列表 |
| **元评估** | 这些数字凭什么信 | 「标准答案是 dense 检索器挑的，所以它偏袒 dense」 |

**新手最常见的错误是只学第一个。** 指标公式很好学（第 02 章一小时能学完），但一个 MRR = 0.5 是好是坏、能不能拿来和另一个系统比，答案完全取决于后两个。

### 3.3 检索段 vs 生成段

这是下一节的主题，也是最重要的一条。

## 4. 核心动作：把 RAG 拆成两段

### 4.1 为什么必须拆

RAG 回答一个问题要经过两步：

```
问题 ──[检索]──> 一堆材料(chunks) ──[生成]──> 答案
```

这两步**独立失败**。假设最终答案是错的，只可能是两种病：

| 病因 | 现象 | 药 |
|---|---|---|
| **检索没捞到** | 正确材料压根不在给 LLM 的上下文里 | 改 embedding / 改切分 / 加 BM25 / 加重排 |
| **生成搞砸了** | 材料就在上下文里，LLM 却编了个别的 | 改 prompt / 换更强的模型 / 加引用约束 |

**这两种病的药完全不相干。** 如果你只有一个「最终答案质量 = 0.6」的分数，你不知道该吃哪副药，只能瞎试。

> 【推断】这是我认为新手最该先建立的一条直觉。见过太多「换了个更强的 LLM 但答案还是错」的案例 —— 因为病在检索段，换生成模型是在给错的器官吃药。

### 4.2 拆完之后各自怎么评

拆开后，两段的评估方法**根本不同**，这也是为什么它们要分两章讲：

| | 检索段 | 生成段 |
|---|---|---|
| 要判断什么 | 对的材料捞上来了吗？排第几？ | 答案有没有编？有没有答到点上？ |
| 怎么判断 | **比对 ID**。标准答案是一个 chunk 列表，看重合 | **让 LLM 读**。没有唯一正确字符串可比对 |
| 需要 LLM 吗 | ❌ 不需要，纯数学 | ✅ 必须要（LLM-as-judge） |
| 结果稳定吗 | ✅ 完全确定，同样输入永远同样输出 | ⚠️ 有波动，换裁判模型分数会漂 |
| 本专题第几章 | 02 | 03 |

### 4.3 一个中间地带

严格说还有第三块：**「捞上来的材料，质量如何」**。它既不是纯检索（不只看 ID 对不对，还看内容够不够支撑答案），也不是生成。

这块由 RAGAS 的 `context_recall` / `context_precision` 负责，用 LLM 判断。**它和检索指标名字很像但量的不是一回事** —— 这是本项目文档里反复强调的一个陷阱，第 02 章 § 在本项目里会用真实数字展示。

## 5. 在本项目里对应什么

本项目默认输出 **8 项聚合指标**，按上面的拆分归位如下【代码】（见 [composite_evaluator.py](../../../src/observability/evaluation/composite_evaluator.py)）：

| 段 | 指标 | 谁算的 | 需要 LLM |
|---|---|---|---|
| **检索段** | `custom__hit_rate` | 本项目自己实现，纯数学 | ❌ |
| | `custom__mrr` | 同上 | ❌ |
| | `custom__recall` | 同上 | ❌ |
| | `custom__ndcg` | 同上 | ❌ |
| **中间地带** | `ragas__context_recall` | RAGAS | ✅ |
| | `ragas__context_precision` | RAGAS | ✅ |
| **生成段** | `ragas__faithfulness` | RAGAS | ✅ |
| | `ragas__answer_relevancy` | RAGAS | ✅ |

> ### ⚠️ 「自己实现」≠「自己发明」，更不是「教学玩具」
>
> 这一栏原本写的是「自研」，容易读成「本项目编出来的土办法，没有生产价值」。**恰好相反** —— 这四个指标一个都不是本项目发明的，全是信息检索领域的标准量具【文献】：
>
> | 指标 | 出处 |
> |---|---|
> | Hit Rate / Recall@K | IR 教科书基础指标，TREC 评测的通用语言 |
> | MRR | TREC-8 QA track（1999）起就是官方指标 |
> | nDCG | Järvelin & Kekäläinen, 2002，搜索/推荐排序的事实标准 |
>
> 「自己实现」只是说 [custom_evaluator.py:114-145](../../../src/libs/evaluator/custom_evaluator.py#L114) 那 30 行公式是手写的、没引第三方库 —— 因为它确实只值 30 行。**RAGAS 不提供它们，不是因为没必要，而是因为一个通用库无法假设你的 chunk ID 长什么样**（原因见 [07 章 § 对标业界 ②](07-this-project.md)）。
>
> **它们在生产中的位置**：确定性 + 零 token + 毫秒级，所以是**唯一跑得起 CI 回归、唯一能做参数扫描**的那一半。本项目的融合权重 `sparse=0.1` 就是靠 MRR 曲线扫出来的【实测】；而全世界挑 embedding 模型看的 MTEB / BEIR 榜单，主指标就是 `nDCG@10`。完整论证在 [07 章 § 对标业界](07-this-project.md)，两组指标怎么分工在 [02b 章](02b-metrics-in-practice.md)。
>
> 真正该打折扣的**不是这四个指标，是喂给它们的标注** —— 本项目的标准答案是脚本用 dense top-5 回填的（04、05 章）。**公式没问题，尺子的刻度是歪的。**

一份真实报告长这样【实测】（`run_id = 80a82405`，英文金标 42 条，collection `default_text-embedding-v4`）：

```
custom__hit_rate         0.619     ← 检索段
custom__mrr              0.5016
custom__recall           0.4238
custom__ndcg             0.4012
ragas__context_recall    0.8333    ← 中间地带
ragas__context_precision 0.7643
ragas__faithfulness      0.8887    ← 生成段
ragas__answer_relevancy  0.8473
```

**现在就用本章学的东西读一遍这组数字**：检索段四项都在 0.4-0.62，生成段两项都在 0.85 以上。按 § 4.1 的诊断框架，这个系统的**瓶颈明显在检索段**，去调 prompt 或换更强的生成模型不会有什么用。

⚠️ 但先别急着下结论 —— 检索段这四项低到什么程度算「真的低」，取决于标准答案是怎么造的。这正是第 04、05 章要处理的问题。**本章只要求你会做这个「分段定位」的动作，不要求你判断绝对值。**

## 6. 自测

答不上就回去重读对应小节。

**Q1.** 你的 RAG 最终答案质量很差。只给你一个端到端分数，你能不能知道该改 prompt 还是该改 embedding？为什么？

<details><summary>答案</summary>

不能。端到端分数把检索失败和生成失败混在一个数字里。必须分段看：如果检索指标低而生成指标高，病在检索；反之病在生成。（§ 4.1）
</details>

**Q2.** 为什么检索段的评估不需要 LLM，生成段就必须要？

<details><summary>答案</summary>

检索段的判断是「这个 chunk ID 在不在标准答案列表里」—— 字符串比对，确定性的。生成段是开放式文本，同一个意思有无数种说法，没有唯一正确字符串可比对，只能让一个理解语义的模型来判断。（§ 4.2）
</details>

**Q3.** 「造一个比人便宜、比人一致、但一定比人差的裁判」—— 这句话里的「比人差」在实践中会以哪几种形式冒出来？举两个。

<details><summary>答案</summary>

任选两个：① 裁判只比对 ID，不理解语义 —— 换个说法表达同一意思会被判不相关；② LLM 裁判有位置/长度/自我偏好；③ 标准答案本身是机器造的，可能就是错的；④ 造标准答案的方法自带立场，会偏袒某个检索器。（§ 2）
</details>

**Q4.** 离线评估分数提升了 10%，能不能说用户体验一定变好了？

<details><summary>答案</summary>

不能。测试集不等于真实用户问题分布。这是离线评估的固有天花板，要靠在线 A/B 才能回答。（§ 3.1）
</details>

**Q5.** `custom__recall` 和 `ragas__context_recall` 名字很像，它们量的是同一件事吗？

<details><summary>答案</summary>

不是。前者在检索段（比对 chunk ID 的重合比例，纯数学），后者在中间地带（LLM 判断捞上来的上下文实际支撑了答案的多少）。第 02 章会用真实数字展示两者的差距有多大。（§ 4.3、§ 5）
</details>

## 本章小结

| 问题 | 答案 |
|---|---|
| 评估要解决什么 | 把主观感觉变成**可重复、可对比、可归因**的数字 |
| 评估的本质 | 造一个比人便宜、比人一致、**但一定比人差**的裁判 |
| 「比人差」会怎么冒出来 | 只比 ID / judge 有偏好 / 标准答案是机器造的 / 造法自带立场 —— 分别在 02·03·04·05 章处理 |
| 最重要的一个动作 | **拆两段**：检索段和生成段独立失败，药完全不相干 |
| 两段怎么评 | 检索段比对 ID（纯数学、确定）；生成段让 LLM 读（会漂、会失败） |
| 本章不要求你做的事 | **判断绝对值高低** —— 那取决于金标怎么造的（04·05 章） |
