## 1. 最常用的 9 个词（先记这些）

| 词 | 用人话说 | 打个比方 |
|---|---|---|
| **chunk（片段）** | 一份文档被切碎后的一小段，检索的最小单位 | 书里的**一页** |
| **chunk_id** | 每个片段的身份证号 | 页码 |
| **金标**（golden test set） | 出题人准备好的考卷：题目 + 参考答案 | 卷子 |
| **case** | 考卷上的**一道题** | 第 3 题 |
| **ground_truth** | 参考答案的**文字**版 | 「标准答案：因为会锁表」 |
| **expected_chunk_ids** | 参考答案的**页码**版：该翻到哪几页 | 「见第 12、37 页」 |
| **judge（裁判）** | 专门用来打分的那个 AI，它不参与答题 | 改卷老师 |
| **指标**（metric） | 把「好不好」算成一个 0~1 的数的某种算法 | 某种给分规则 |
| **降级**（degradation） | 裁判没能给出分数，这道题的这一项作废 | 这题没批，空着 |

详细讲解在 [00 章](00-prerequisites.md)。

## 2. 英文缩写逐词拆解 ⭐

**看不懂缩写不是你的问题** —— 它们全是英文短语的首字母，拆开就好懂了。

### 2.1 指标名

| 缩写 | 全称 | 逐词是什么意思 | 所以它在算什么 |
|---|---|---|---|
| **MRR** | **M**ean **R**eciprocal **R**ank | 平均 · 倒数 · 排名 | 「第一个对的排第几」→ 取**倒数**（排第 2 → 1/2 = 0.5）→ 所有题**取平均** |
| **DCG** | **D**iscounted **C**umulative **G**ain | 打折的 · 累加的 · 收益 | 每个命中按「排得多后面」**打折**，然后**加起来** |
| **IDCG** | **I**deal **DCG** | **理想**情况的 DCG | 假设所有该翻的页都挤在最前面，能拿多少分 |
| **nDCG** | **n**ormalized **DCG** | **归一化**的 DCG | `DCG ÷ IDCG` —— 除一下才能跨题比较 |
| **Hit Rate** | （不是缩写） | 命中率 | 前 k 条里**只要有一条**对的就记 1 分 |
| **MAP** | **M**ean **A**verage **P**recision | 平均 · 平均 · 精确率 | 每个命中位置算一次精确率再平均（`context_precision` 的内核） |

> 💡 **这类缩写要「从右往左」读，才是操作顺序**：
>
> - `MRR` → 先有 **R**ank（排第几），再取 **R**eciprocal（倒数），最后求 **M**ean（平均）
> - `DCG` → 先有 **G**ain（收益），再 **D**iscounted（打折），最后 **C**umulative（累加）
>
> **`RR` 和 `MRR` 别搞混**：RR 是**单独一道题**的分，MRR 是**整套卷子**的平均。报告里的 `custom__mrr` 是后者；单条 case 的 `reciprocal_rank` 字段才是前者。

> 💡 **为什么 MRR 要取倒数？** 因为「排第 1」和「排第 2」的差距，应该远大于「排第 9」和「排第 10」的差距。倒数正好有这个性质：1.0 / 0.5 / 0.33 / 0.25 …… 衰减很陡。
>
> **为什么 nDCG 要除以理想值？** 因为不同题目的相关页数不同（有的题该翻 2 页，有的该翻 8 页），原始 DCG 没法互相比较，各自除以自己的满分才能平均。

完整手算见 [02 章 § 3](02-retrieval-metrics.md)。

### 2.2 检索与生成方法

| 缩写 | 全称 | 人话 |
|---|---|---|
| **RAG** | **R**etrieval-**A**ugmented **G**eneration | 检索增强生成 —— 先查资料，再让 AI 照着资料回答 |
| **RAGAS** | **RAG** **A**ssessment | 一个专门评估 RAG 的第三方库，靠 AI 判分 |
| **BM25** | **B**est **M**atching，第 25 号公式 | 一个**按关键词**匹配的经典算法（1994 年，至今没被淘汰） |
| **RRF** | **R**eciprocal **R**ank **F**usion | 倒数排名融合 —— 把多路检索结果**合并成一个排序**的算法 |
| **HyDE** | **Hy**pothetical **D**ocument **E**mbeddings | 假想文档嵌入 —— 先让 AI **编一个假答案**，再拿这个假答案去检索 |
| **NLI** | **N**atural **L**anguage **I**nference | 自然语言推理 —— 判断「这段材料能不能推出这句话」 |
| **LLM** | **L**arge **L**anguage **M**odel | 大语言模型 |
| **IR** | **I**nformation **R**etrieval | 信息检索 —— 搜索引擎那个领域，本专题 02 章的指标全来自这里 |
| **TREC** | **T**ext **RE**trieval **C**onference | 信息检索的老牌评测会议，`pooling` 做法来自它 |
| **API** | **A**pplication **P**rogramming **I**nterface | 程序之间互相调用的接口 |

## 3. 检索相关的英文词（正文用得很多，但容易懵）

| 词 | 人话 | 打个比方 |
|---|---|---|
| **embedding（嵌入 / 向量）** | 把一段文字变成一串数字，意思相近的文字数字也相近 | 给每段话一个「语义坐标」 |
| **dense（稠密检索）** | **按意思找** —— 用 embedding 算相似度。换个说法也能找到 | 按「大概讲什么」找书页 |
| **sparse（稀疏检索）** | **按词找** —— BM25 那一路。词对不上就找不到 | 按「出现了哪些字」找书页 |
| **hybrid（混合检索）** | dense + sparse 两路都跑，再用 RRF 合并 | 两种找法都用，结果合起来 |
| **rerank（重排）** | 第一轮粗筛出几十条后，用一个更慢更准的模型**重新排序** | 先粗选 40 页，再仔细挑出最相关的 |
| **cross-encoder** | 重排用的那种模型：把「问题 + 候选片段」一起读，输出一个相关度分 | 挨个仔细读，慢但准 |
| **top-k / `top_k` / top-5** | 只取排名最前的 k 条。`top-5` 就是前 5 条 | 只看前 5 页 |
| **collection（集合）** | 向量库里的一个「库」，装着一批切好的片段 | 一个书架 |
| **dense-anchored** | **本项目自造的词**：指某个指标的标准答案是纯 dense 检索产出的，所以它天然偏袒 dense | 「尺子是按 dense 的口味刻的」 |
| **prompt（提示词）** | 发给 AI 的那段指令文字 | 给它的任务说明 |

> ⚠️ **`dense` / `sparse` 这对词在专题里出现几十次**，是理解 [05 章](05-meta-evaluation.md) 的关键。记住一句话就够：**dense 按意思找，sparse 按词找。**

## 4. 最容易搞混的：「召回率」有三种意思

| 出现形式 | 在哪一层 | 量的是什么 | 要不要 AI |
|---|---|---|---|
| `custom__recall` | 检索段 | 捞到的片段 **ID** 与金标 ID 的重合比例 | ❌ |
| `ragas__context_recall` | 中间地带 | **参考答案里的每句话**能否在检索到的文本里找到出处 | ✅ |
| 教科书的 Recall@k | 检索段 | 同 `custom__recall`（本项目实现有细微差异，见 [02 章 § 6.1](02-retrieval-metrics.md)） | ❌ |
| `ragas__context_precision` | 中间地带 | 检索到的每条**有没有用**，且有用的排没排在前面 | ✅ |
| 教科书的 Precision@k | 检索段 | 前 k 条里相关的比例（**本项目未实现**） | ❌ |

### 两个词本身是什么意思

| | 中文 | 字面在说什么 | 分母是谁给的 | 担心的事 | 别名 |
|---|---|---|---|---|---|
| **Recall** | 召回率 | 该「**召**」回来的都叫**回**来了吗 | **出题人**（该捞的） | **漏**了什么 | 查全率、`sensitivity`（灵敏度） |
| **Precision** | 精确率 | 交上来的东西**精**不精 | **你自己**（实际捞的） | **混**进了什么垃圾 | 查准率 |

**一句话记法：一个看「漏」，一个看「混」。** 分子一样，只有分母换了 —— 换分母就是换视角。

⚠️ **它俩天生此消彼长**：捞得越多，漏得越少（Recall 涨）但垃圾越多（Precision 跌）。所以单看一个能被轻易刷分。完整讲解见 [02 章 § 3 开头](02-retrieval-metrics.md)。

### 两个翻译陷阱：precision ≠ 精密，faithfulness ≠ 真实

**① `precision` 在英文里有两个不相干的义项，这里用的是检索义：**

| 义项 | 中文 | 意思 | 是不是这里的意思 |
|---|---|---|---|
| 日常/工程义 | 精确、精密 | 测量得多细、误差多小（「精确到小数点后三位」） | ❌ 完全无关 |
| 信息检索义 | **查准率** | **捞回来的东西里，有用的占多少** | ✅ 就是这个 |

用渔网打比方：**precision 问「网里的东西有多少是鱼」，recall 问「海里的鱼有多少进了网」。** 拖大网 → recall 高 precision 低；只叉最有把握的一条 → 反过来。

**② `faithfulness` 译作「忠实度」，关键是想清楚忠实是「对谁」忠实。** faithful 的本义是「忠诚的」，它天然要求一个宾语 —— 这个指标的宾语是 **`contexts`（检索到的材料）**，不是事实、不是标准答案：

> faithfulness = 答案**忠于材料**的程度 = 开卷考试的「**照书作答率**」

老师不管你答得对不对，只查你写的每句话能不能在你翻开的那几页里找到依据。所以**材料本身是错的、你照抄，忠实度照样满分**。千万别把它读成「真实性」「准确性」—— 那两个词暗示「和事实比对」，而它从头到尾没碰过 `ground_truth`。

**③ 一个帮记忆的巧合：faithfulness 本质上就是一种查准率** —— 拆开「你写的话」逐句问「有出处吗」，和 `context_precision` 拆开「你捞的页」逐条问「有用吗」是同一个查准结构，只是查的对象不同。查全结构只有一个：`context_recall`。展开见 [03 章 § 2.2](03-generation-metrics.md) 的警告块。

**④ 为什么这四个指标命名风格如此分裂**：它们借自两个研究社区 —— `context_precision` / `context_recall` 来自信息检索（IR）的经典行话，`faithfulness` / `answer_relevancy` 来自 NLG / 摘要评估的行话【文献】，RAGAS 把两族词拼进同一份报告，从没做过统一重命名。**推论：指标名是历史沉积物，不是接口文档，别从名字反推算法**（`context_precision` 的名字里看不出它读 `ground_truth`）。来龙去脉见 [03 章 § 3.6](03-generation-metrics.md)。

> 💡 **一秒判别的窍门**：看它读的是 **ID** 还是**文本**。
>
> - 读 **ID** → 纯算术，不花钱，永远算得出来
> - 读 **文本** → 必须请 AI 判，会花钱、会波动、**会失败**
>
> 实测同一批检索结果，`custom__recall` = 0.30 而 `ragas__context_recall` = 0.83 —— **两个都是对的**，因为它们问的根本不是同一个问题。

## 5. 三种「答案」

| 名字 | 是什么 | 谁造的 |
|---|---|---|
| `query` | **题目**（用户的问题） | 出卷时生成 |
| `ground_truth` | 参考答案**文本** | 合成时由 AI 写，人工精修过 |
| `expected_chunk_ids` | 期望捞到的**片段 ID 列表** | 由标注脚本产出（**两代做法不同**，见 [04 章 § 5](04-golden-set.md)） |
| `answer` | 系统**本次实际生成**的回答 | 评估运行时现场生成 |
| `contexts` | 本次**检索到的片段原文**（不是 ID，是文本） | 评估运行时现场检索 |

「**金标**（golden test set）」是包含前三者的那份 JSON 文件的统称。

> ⚠️ `contexts` **必须是文本，不能是 ID**。传 ID 进去不会报错，AI 会老老实实把 `...chm_2835_610f192b` 当成一段话去判断，然后给你一个看起来正常的低分 —— 这是一类**静默失败**。

## 6. 三个长得像版本号、但互不联动的字段

| 字段 | 指什么 |
|---|---|
| `_schema_version` | 金标 **JSON 结构**的版本（字段增删） |
| `version` | 这份金标**内容**的版本（`v1.0` / `v2.0` / `v0.1-partial`） |
| `_labeling_method` | `expected_chunk_ids` **怎么挑出来的**（`dense-top-k` / `pooled-llm-judged`） |

⚠️ **它们不联动。** 本项目就有 `version` 写着 `v1.0`、但标注方法已经换代的实例。

> **判断「两份报告的分数能不能比」时，看 `_labeling_method`，不要看 `version`。** 完整实例见深文 [golden-test-set-explained.md § 8](../golden-test-set-explained.md)。

两代标注方法的名字也拆一下：

| 值 | 逐词 | 人话 |
|---|---|---|
| `dense-top-k` | dense（按意思找）+ top-k（前 k 条） | 拿参考答案去按意思搜，前 5 条就算标准答案 |
| `pooled-llm-judged` | pooled（汇集）+ llm-judged（AI 判定） | 多路检索结果**汇总成一池**，再让 AI 逐条判相关度 |

## 7. 报告 JSON 里的字段名

跑完评估会得到 `logs/evaluation_reports/<run_id>.json`。里面的字段：

| 字段 | 人话 |
|---|---|
| `run_id` | 这次运行的编号（一长串随机字符，正文里用前 8 位指代，如 `80a82405`） |
| `total_cases` | 这次考了几道题 |
| `aggregate_metrics` | **8 个指标的平均分** —— 大家最先看的就是这里 |
| **`metric_integrity`** | **每个指标各自算了多少条样本** ⭐ 看分数前先看它 |
| ├ `valid_count` | 这个指标**实际算成功**了几条（真正的分母） |
| ├ `degraded_count` | 这个指标**算失败**了几条 |
| └ `reasons` | 失败原因的分布 |
| `degraded_case_count` | 有多少道题**至少有一项**没批出来 |
| `degradation_reasons` | 单道题里，哪几项失败了、为什么 |
| `acceptance_status` | `pass` / `fail` —— 8 项是否都过阈 **且** 降级率 ≤ 5% |
| `acceptance_thresholds_snapshot` | 判定当时用的阈值（存快照，以后改了阈值也能追溯） |
| `case_results` | **每道题的完整原始数据**（题目 / 答案 / 检索到的材料 / 参考答案） |
| `baseline_id` | 跟哪一次运行做对比 |
| `delta_*` | 与那次的**分数差**（delta 就是「差值」） |
| `delta_comparable` | 工具判断这个差值能不能比（**它只查了一维，别全信**） |
| `delta_incomparable_metrics` | 逐项说明哪个指标不可比、为什么 |
| `judge_llm_identifier` | 这次用的裁判是谁（如 `glm:minimax/minimax-m2.7`） |
| `embedding_identifier` | 这次用的向量模型是谁 |
| `aggregate_metrics_by_tag` | 按题目类型 / 难度切片后的分数 |
| `per_tag_delta` | 上一行那些切片**各自相对基线的差值**（「总分没变但难题掉了」只能从这里看出来） |
| `labeling_method` | 这份卷子的标准答案是怎么标的（见 § 6） |
| `null` | JSON 里表示「**这里没有值**」（不是 0，是「空」） |

### 降级原因的五个取值

| 值 | 人话 |
|---|---|
| `unparseable` | 裁判回答了，但格式不对、**解析不出分数**（最常见的一种） |
| `empty_response` | 裁判**啥也没回**（空字符串） |
| `timeout` | 裁判**超时**了 |
| `upstream_error` | 上游拒绝服务：**没额度 / 被限流 / 模型下架** |
| `unknown` | 归不进上面任何一类。**它的占比本身就是个警报** |

| 词 | 含义 |
|---|---|
| **judge_llm** | 打分用的模型 |
| **screening_llm** | 金标精修时**预筛**用的模型 |
| **labeling_llm** | 标注「该翻哪几页」用的模型 |

## 9. 统计与实验方法

| 词 | 人话 |
|---|---|
| **baseline（基线）** | 被指定当参照系的某一次历史运行 |
| **delta** | 差值。`delta_mrr = +0.08` 就是「MRR 比基线高 0.08」 |
| **NaN** | **N**ot **a** **N**umber，「这儿不是一个数」。算不出来时放的占位值，**它会退出平均值的分母** |
| **分母收缩** | 因为降级，某个指标的平均值实际只算了一部分题 —— 而平均值本身看不出来 |
| **幸存者偏差** | 只统计「活下来的样本」导致结论偏乐观。这里指：**判不出来的往往是答得烂的那些** |
| **锚定偏差** | 用检索器 X 造标准答案，再用它评检索器 Y —— 测出来的是「Y 有多像 X」 |
| **元评估**（meta-evaluation） | **对「评估」本身的评估** —— 不问系统答得好不好，问「这把尺子准不准、量的是不是你以为的那件事」。构词法同「数据 / 元数据」。它只有两个动作：**换参照物**（拿答案已知正确的东西去量）、**换条件**（冻结其余只改一个再量）。见 [05 章](05-meta-evaluation.md) |
| **系统性偏差**（bias） | **总是往同一个方向偏**。⚠️ 加大样本、多跑几次**都消不掉**，只会把错的数测得更精确 |
| **随机噪声** | 有时偏高有时偏低。多测几次取平均**能**抵消 —— 和上一条是本专题最容易混的一对 |
| **同源污染** | 用 A 造的东西再用 A 来验，验不出 A 的盲点。所以本项目强制三处**异源** |
| **消融（ablation）** | 一次**只改一个变量**，否则分数变了也不知道是谁的功劳 |
| **配对（paired）比较** | 逐条算差值再看这串差值，而不是两组各自平均再相减。**前提是两次的输入必须完全相同** —— 所以做 judge 对照要冻结元组，不能重跑整条链路 |
| **p 值** | 统计检验的结果。**越小越说明「这个差异不像是碰巧」**。习惯上 p < 0.05 才算显著 |
| **Jaccard** | 两个集合的重合度：`交集 ÷ 并集`。0 = 完全不重合，1 = 完全一样 |
| **qrels** | query relevance judgments，「哪个 query 对应哪些 doc、相关到什么程度」的标注集。MTEB / BEIR / TREC 的基础 |
| **MTEB / BEIR** | 公开的 embedding / 检索评测榜单，**全部建立在 qrels 上**，主指标 `nDCG@10`。挑 embedding 模型就是在看它们 |
| **ID 键 / 文本键** | 判断「捞的片段对不对」时用什么做比对：ID 精确但不可跨系统；文本可移植但要 LLM 判。见 [07 章 § 对标业界](07-this-project.md) |
| **pooling（池化）** | 把多个检索路径的前 N 条结果**并起来**，只标这个池子。TREC 几十年的标准做法 |
| **pooling bias**（池化偏差） | 上一条的代价：**没参加过池化的系统会被系统性低估**（它捞的好片段根本不在标注范围内）。本项目的「池」只有 dense 一个成员，所以这就是 05 章的**锚定偏差** |
| **oracle** | 「先知」—— 指某种假想的完美结果，用来当上限参照 |
| **离线评估** | 拿固定测试集跑分（**本专题讲的全是这个**） |
| **在线评估** | 用真实用户流量做 A/B 对比（本专题**不涉及**） |
| **A/B** | 同时跑两个版本对比效果 |
| **LLM-as-judge** | 「让大模型当裁判」这个范式的正式叫法 |
| **statements** | RAGAS 把一段答案拆成的**一句句原子陈述**，`faithfulness` 逐句判定的单位 |
| **cross_judge_agreement_rate** | **两个 AI** 判定结果的一致率（本项目 v2 金标是 95.8%） |
| **human_agreement_rate** | **人工**抽检与 AI 判定的一致率。⚠️ 本项目至今是 `null`（还没做） |
| **train-eval skew** | 建索引和评估用了**不同的** embedding 模型，导致结果失真 |
| **grade** | 分级相关度，0~3 分（0 无关 / 1 沾边 / 2 部分支撑 / 3 直接回答） |
| **`rel` / `rel_i`** | **rel**evance（相关度）的缩写，`i` 是下标。DCG 公式的**分子** —— 「第 i 条**有多**相关」。⚠️ 本项目**硬编码为 1**（二元），v2 金标的 0~3 分级没被用上 |
| **二元标注**（binary） | `rel` 只能是 0 或 1：相关 / 不相关 |
| **分级标注**（graded） | `rel` 可以是 0/1/2/3。**只有 nDCG 用得上**，是它相对其他四个指标的唯一独有能力 |
| **fixture** | 测试用的固定数据文件。本项目的金标都放在 `tests/fixtures/` |

## 10. 脚本名（`scripts/` 下那一堆 .py）

正文经常提到脚本名。它们按「造卷子 → 考试」的顺序排：

| 脚本 | 名字逐词 | 干什么 |
|---|---|---|
| `synthesize_testset.py` | synthesize（合成）+ testset（测试集） | **第 1 步造卷子**：让 AI 从资料里生成候选题目 + 参考答案 |
| `refine_testset.py` | refine（精修） | **第 2 步筛卷子**：把烂题挑掉（`--auto-mode` = 让 AI 先预筛，只让人看存疑的） |
| `backfill_chunk_ids.py` | backfill（回填）+ chunk_ids（片段号） | **第 3 步标页码 · 第一代**：拿参考答案按意思搜，前 5 条就算标准答案 |
| `label_golden_chunks.py` | label（标注）+ golden chunks（金标片段） | **第 3 步标页码 · 第二代**：多路检索汇总成池，让 AI 逐条判 0~3 分 |
| `evaluate.py` | evaluate（评估） | **考试**：跑一遍，出报告 |
| `calibrate_fusion_weights.py` | calibrate（校准）+ fusion weights（融合权重） | 调 dense / sparse 两路的相对分量 |
| `start_dashboard.py` | dashboard（仪表盘） | 打开网页界面看趋势 |

### 命令行参数（CLI flag）

| 参数 | 意思 |
|---|---|
| `--pretty` | 输出排版好看一点 |
| `--collection <名字>` | 指定用哪个「书架」 |
| `--auto-mode` | 精修时启用 AI 预筛 |
| `--allow-same-source` | **强行放过**「无法确认两个模型是否异源」的检查（⚠️ 只豁免「无法确认」，不豁免已确认同源） |
| `--dry-run` | 空跑一遍，不真的调 AI（零成本试验） |
| `-u` | Python 参数，**不缓冲输出**。不加会看到空白误以为卡死 |

## 11. `settings.yaml` 里的配置项名

| 配置项 | 人话 |
|---|---|
| `top_k_final` | 最终返回几条片段给 AI 读（本项目默认 **10**）。02 章所有指标都隐含 `@10` |
| `fusion_weights` | dense / sparse 两路在合并时的**相对分量**。只有比例有意义 |
| `rrf_k` | RRF 合并算法的平滑参数 |
| `rerank.backend` | 用哪种重排（`none` = **不开**，本项目默认；`cross_encoder` = 本地模型） |
| `chunk_id_validation` | 开关：跑评估前**先检查金标里的页码还存不存在** |
| `acceptance_thresholds` | 8 个指标各自的及格线 |
| `degradation.max_ratio` | 降级率上限（默认 **0.05**，超了直接判 fail） |
| `keep_threshold` / `drop_threshold` | 精修预筛的置信度门槛（≥ 就自动保留 / 自动丢弃） |
| `relevance_threshold` | 标注时相关度 ≥ 几分才算「该翻的页」（默认 **2**） |
| `adapt_language_ratio_min` | 校验 RAGAS 的中文翻译**真的翻了** —— 目标语言字符占比下限 |
| `tag_slice_min_samples` | 按类型切片时，样本少于这个数就不出分（默认 5） |
| `collection_name` | 用哪个「书架」。**dense 和 sparse 两路共用这一个值** |

> 💡 **一条通用规律**：`settings.yaml` 里任何数值阈值，如果旁边配了一个模型名，那么**这两者是捆绑的** —— 换模型不重新校准阈值，等于换了温度计不换刻度。这在专题里出现了四次（[05 章 § 7](05-meta-evaluation.md)）。

## 13. 八项指标一览

本项目默认输出的 8 个数，按「读 ID 还是读文本」分成两组：

| 指标 | 组 | 一句话 | 会降级吗 |
|---|---|---|---|
| `custom__hit_rate` | 读 ID | 至少捞到一条对的了吗 | ❌ 从不 |
| `custom__mrr` | 读 ID | 第一条对的排第几 | ❌ |
| `custom__recall` | 读 ID | 该捞的捞回了几成 | ❌ |
| `custom__ndcg` | 读 ID | 整体排序质量 | ❌ |
| `ragas__context_recall` | 读文本 | 参考答案的每句话都有出处吗 | ✅ 会 |
| `ragas__context_precision` | 读文本 | 捞上来的干不干净、排序对不对 | ✅ |
| `ragas__faithfulness` | 读文本 | 答案有没有编（**不判对错**，只判有没有出处） | ✅ |
| `ragas__answer_relevancy` | 读文本 | 有没有答到点上 | ✅ |

**名字怎么读**：双下划线只是分隔符，前缀是「谁算的」——

- `custom__` = **本项目自己写的代码**，纯算术，免费，永远算得出来
- `ragas__` = **第三方库 RAGAS**，靠 AI 判，花钱，**会失败**

**前四项零成本、永远算得出来；后四项要花钱、会波动、会失败。** 这个分界贯穿整个专题。
