## 先说清 `custom__` 这个前缀是怎么回事

打开报告会看到 `custom__hit_rate`、`custom__mrr` 这种名字。**很多人第一反应是「这是某种特殊的、定制版的 Hit Rate 吗？」—— 不是。**

### 结论先给：它就是本章讲的那个 Hit Rate

```
custom__hit_rate   =   02 章 § 3.1 讲的那个 Hit Rate
└────┘└┘└──────┘
  ↑    ↑    ↑
谁算的 分隔符 指标本身
```

**前缀不是指标的一部分，是一个「谁算的」标签。** 公式一模一样（除了本章末尾那四处实现差异）。

### `custom` 是**后端的名字**，不是「定制」的意思

本项目的评估是**可插拔**的，可以同时启用多个「评估后端」：

| 后端 | 是什么 | 产出哪几项 |
|---|---|---|
| **`custom`** | **本项目自研的评估器**（`CustomEvaluator` 类） | hit_rate / mrr / recall / ndcg |
| **`ragas`** | **第三方开源库** RAGAS | faithfulness / answer_relevancy / context_precision / context_recall |

所以 `custom` 读作「**自研后端**」，和 `ragas` 是并列关系 —— 一个是自己写的，一个是外部库。**不是「定制版 vs 标准版」的意思。**

### 为什么非要加前缀：名字会撞车

两个后端都会产出叫 `recall`、`precision` 的指标：

```
不加前缀会变成 ——
  custom 的 recall  ──┐
                      ├──> 都叫 "recall"，覆盖掉一个 ❌
  ragas  的 recall  ──┘

加了前缀 ——
  custom__recall          ← 比对 chunk ID，纯算术
  ragas__context_recall   ← LLM 判断内容够不够
```

而这两个 recall **量的根本不是同一件事**（实测能差到 0.30 vs 0.83）。**前缀就是防止你把它们看成一个东西。**

> `__` 是**双下划线**，纯粹当分隔符用 —— 因为指标名自己带单下划线（`hit_rate`），用双下划线才能一眼看出哪里是分界。

### 一个有意思的实现细节：前缀是**条件加**的

【代码】只有**同时启用多个后端**时才加前缀（[composite_evaluator.py:77](../../../src/observability/evaluation/composite_evaluator.py#L77)）：

```python
# 仅当组合多个评估器时才添加 prefix，避免与历史 baseline 的无前缀 key 失配。
apply_prefix = len(self._evaluators) > 1
```

**所以如果你把 `settings.yaml` 的 `evaluation.backends` 改成只留 `[custom]`，报告里的 key 会变成 `hit_rate` 而不是 `custom__hit_rate`。**

这是为了**向后兼容** —— 早期项目只有 custom 一个后端，历史报告和基线里存的都是无前缀的 key。无条件加前缀会让新报告和旧基线对不上，delta 全部算不出来。

> ⚠️ **实用后果**：看到一份报告里是 `hit_rate` 而不是 `custom__hit_rate`，说明那次运行**只启用了 custom 后端**（没跑 RAGAS）。这是个能一眼看出来的信号。

### 两组的真正区别不在名字，在实现

| | `custom__*`（四项） | `ragas__*`（四项） |
|---|---|---|
| 谁写的 | 本项目自己的代码 | 第三方库 RAGAS |
| 读什么 | **chunk ID**（比对列表） | **文本**（让 LLM 读） |
| 要花钱吗 | ❌ 零成本 | 💰 每条 case 十几次 LLM 调用 |
| 结果稳定吗 | ✅ 完全确定，跑两次一模一样 | ⚠️ 会波动，换 judge 会漂 |
| 会算不出来吗 | ❌ 永远算得出来 | ⚠️ **会失败**（降级） |
| 本章讲的是 | ✅ 这四项 | 03 章讲 |

**记住这一条就够用了：看到 `custom__` 前缀 = 纯算术、免费、铁打的；看到 `ragas__` = AI 判的、花钱、会失败。**

### 那为什么两组都要？RAGAS 不是也评检索吗

**这是个很自然的疑问，而且它戳中了一个容易含糊过去的地方。**

RAGAS 确实有两项是评检索的（`context_recall` / `context_precision`）。既然如此，为什么还要自己再写四个？

**答案在一个可以直接去代码里核实的事实上：**

> ### ⭐ RAGAS **从来看不到** `expected_chunk_ids`

【代码】喂给 RAGAS 的数据集只有**四个字段**（[ragas_evaluator.py:295-301](../../../src/observability/evaluation/ragas_evaluator.py#L295)）：

```python
dataset = Dataset.from_dict({
    "question":     [query],           # 问题
    "answer":       [answer],          # 系统生成的回答
    "contexts":     [list(contexts)],  # 检索到的片段【原文】
    "ground_truth": [ground_truth],    # 参考答案【文字】
})
```

**注意这个数据集里没有 chunk ID。**

严格说，`golden_ids` 确实出现在 `RagasEvaluator.evaluate()` 的**参数签名**里，还做了非空校验 —— 但那只是为了**和其他评估器保持同一个接口**。代码注释把这件事说得很直白【代码】（[ragas_evaluator.py:138-140](../../../src/observability/evaluation/ragas_evaluator.py#L138)）：

```python
retrieved_ids: Ranked retrieved chunk IDs（仅用于与检索类指标接口统一，
    RAGAS 本身不使用 ID）。
golden_ids: Expected golden chunk IDs（同上）。
```

> **收到了，但一个字都没用。** 四项 RAGAS 指标的计算完全建立在上面那四个文本字段上 —— 它**不知道「本该捞哪几页」**。

它只能看着「捞回来的这堆文字」和「参考答案这段文字」，判断内容够不够、干不干净。

**这不是实现疏忽，是 RAGAS 的设计** —— 它面向的是「没有 chunk 级标注也能评」的场景（这也正是 `faithfulness` / `answer_relevancy` 能在线上流量跑的原因）。

### 于是有三类问题，RAGAS 在结构上答不了

| 问题 | 谁能答 | 为什么 RAGAS 不能 |
|---|---|---|
| **有多少比例的题，一条正确片段都没捞到？** | `custom__hit_rate` | 它不知道哪些片段算「正确」 |
| **第一条正确片段排在第几位？** | `custom__mrr` | 同上 —— 没有 ID 就没有「第几个是对的」 |
| **该捞的 5 条，捞回了几条？** | `custom__recall` | 它连「该捞 5 条」这件事都不知道 |

**注意这三个问题的共同点：它们都需要一份「正确答案清单」。** 而那份清单（`expected_chunk_ids`）只交给了 custom 这一路。

> 💡 **所以两组的分界不是「检索 vs 生成」，是「有没有 chunk 级标准答案」**：
>
> - `custom__*` ← 拿到 **ID 清单**，能回答「捞对了哪几个、排第几」
> - `ragas__*` ← 拿到 **文本**，能回答「内容够不够、有没有编」
>
> ⚠️ 我在 [03 章 § 2](03-generation-metrics.md) 把 `context_recall` / `context_precision` 归为「评检索」—— 那是按**它们关心哪一段**分的，没错，但**别据此以为它们能替代 custom 四项**。两种分法看的是不同维度。

**Q：可就算这样，为什么不能只用 RAGAS 那两项凑合？**

因为它有四个致命的日常缺陷：

| 问题 | 实测 |
|---|---|
| **贵** | 每条 case 十几次 LLM 调用，42 条一轮约 **595 次**【实测】 |
| **慢** | 判定是串行 LLM 调用，一轮几十分钟 |
| **会失败** | run `80a82405` 降级率 **54.8%**【实测】—— 一半以上的题判不出来 |
| **会漂** | 换个 judge 模型，`context_precision` 能差 **0.08~0.11**【实测】 |

**这四条加起来，意味着它进不了 CI** —— 你没法每改一行代码就烧几百次调用、等半小时、然后得到一个可能因为限流而变化的分数。

> **这一条其实比「能不能测同一件事」更决定性**：哪怕 RAGAS 在能力上完全覆盖了 custom，你**仍然需要**一组能每次提交都跑的探针。而那组探针必须是零成本、秒级、结果确定的 —— **只有纯算术能做到**。

**还有一层：RAGAS 会失败，custom 是兜底**

run `80a82405` 的降级率 **54.8%**【实测】—— 那次运行里 RAGAS 四项有一半以上判不出来。

**但同一份报告里，四项 `custom__*` 的分母是满的（42/42），一条没丢。**

【代码】原因很直白：custom 不调 LLM，**它没有「失败」这个概念**。如果没有这一组，那次评估等于全废。

**Q：那反过来，为什么不只用 custom？它免费又确定**

因为它**完全不理解语义**，只会比对 ID：

- 换个说法表达同一个意思 → 它判为「不相关」
- 捞到了一条内容等价的**另一个** chunk → 它判 0 分
- 答案编没编、答没答到点 → **它一无所知**（那是生成段，它管不着）

而且它依赖的 `expected_chunk_ids` 本身就有偏（[05 章](05-meta-evaluation.md) 整章在讲这件事）。

### 一个真实例子：两个都看才能发现真相

回到 [00 章 § 2.3](00-prerequisites.md#23-一条真实-case-的完整数据) 那条 case【实测】（run `5efa34ab`）：

```
custom__hit_rate        1.0     ← 捞到了
custom__mrr             1.0     ← 而且排第 1
custom__recall          0.2     ← 但金标 5 条只捞到 1 条 ⚠️
ragas__context_recall   1.0     ← 内容完全支撑了参考答案 ⚠️
```

**这两个 ⚠️ 放在一起才有意义**：

| 只看谁 | 会得出什么结论 |
|---|---|
| 只看 `custom__recall = 0.2` | 「检索很差，漏了 80%」→ **误判** |
| 只看 `ragas__context_recall = 1.0` | 「检索完美」→ **看不到金标可能有问题** |
| **两个一起看** | 「内容够了，但和金标列的 ID 对不上」→ **金标那 5 条里至少 4 条不是必需品** ✅ |

**第三行那个结论，任何单独一组指标都得不出来。** 这就是为什么两组都要。

### 所以是分工，不是冗余

| | `custom__*` | `ragas__*` |
|---|---|---|
| **定位** | **回归探针** | **质量体检** |
| 什么时候跑 | **每次改代码都跑**（零成本、秒级） | 改了策略、阶段性验收才跑 |
| 回答什么 | 「有没有改坏」 | 「好在哪、坏在哪」 |

> 【推断】把 `ragas` 塞进每次 CI 是浪费；把 `custom` 当成质量的最终裁判是误用。

### ⚠️ 这个名字有误导性：成熟度其实是反过来的

**「custom」听起来像「自创的、非标准的、凑合用的」，「ragas」听起来像「正规的、库提供的、权威的」。**

**实际情况正好相反：**

| | `custom__*` 四项 | `ragas__*` 四项 |
|---|---|---|
| 出现时间 | **1960~90 年代**，信息检索经典【文献】 | **2023 年之后**（RAGAS 论文 arXiv:2309.15217） |
| 成熟度 | **教科书级**，公式全球统一、无方言 | **仍在快速演进**，0.1 → 0.2 就破坏性重构过 |
| 结果确定性 | 完全确定 | 换 judge 就漂 |
| 业界共识 | 高，任何认真的检索评估都会用 | **LLM-as-judge 本身仍有大量争议** |

> **真正「新、需要小心」的那一组是 `ragas__`，不是 `custom__`。**
>
> `custom` 在这里只表示「**本仓库自己实现的**」，**不表示「自己发明的」** —— 四个公式是照教科书写的，加起来三十来行代码。

**这四个指标是不是业界最佳实践？** 是 —— `Hit Rate` / `Recall` / `MRR` / `nDCG` 是 IR 领域几十年的标准，搜索引擎、推荐系统、RAG 通用。**只有 `custom__` 这个前缀是本项目的命名**，别的项目可能叫 `ir__`、`retrieval__`，或者干脆不加。

【推断】自己实现 vs 用现成 IR 评测库（如 `pytrec_eval`、`ranx`）两种都常见。自己写的代价是**容易和教科书产生细微偏差** —— 本项目就有四处，见下面 § 实现与教科书的四处差异。

### 「不经过 LLM」是特性，不是缺陷

看到「不用 LLM」很容易觉得它低级。**恰恰相反 —— 不用 LLM 正是它全部价值的来源。**

回到改卷子的比喻：

> **选择题用答题卡机器批**（确定、免费、秒出）；**作文才需要人工阅卷**。
>
> 你不会因为「答题卡机器不理解语义」就说它没价值 —— **因为选择题本来就不需要理解语义。**

`custom__*` 测的正是一个**有确定答案的问题**：「捞到的这个 ID，在不在标准答案清单里？」

这个问题**不需要理解语义就能回答**。用 LLM 去做等于杀鸡用牛刀，还白白引入不确定性。

> **用 LLM 不是优点，是成本。** 只有当问题本身**没有确定答案**时（比如「这段话有没有编」），才不得不请 LLM。

不用 LLM 换来的四个能力，每一个都是 RAGAS 给不了的：

| 能力 | 为什么重要 |
|---|---|
| **可重复** | 同样输入永远同样输出。分数变了 → **一定是系统变了**，不可能是裁判抽风 |
| **可归因** | 没有第二个变量。RAGAS 分数变了，你分不清是检索变了还是 judge 漂了 |
| **不会失败** | run `80a82405` 降级 54.8% 时，四项 custom 分母仍是满的 42/42【实测】 |
| **可手算复核** | 出了怪结果你能自己验算（§ 7 的练习就是干这个）。LLM 判的你验不了 |

### 什么时候用哪一组

| 场景 | 用哪个 | 为什么 |
|---|---|---|
| **每次提交 / CI 回归** | **只用 custom** | 零成本秒级，唯一跑得起的 |
| **调 embedding / 切分 / 融合权重 / `top_k`** | **custom 为主** | 这些改动直接改变「捞到哪些 ID」，正是它测的 |
| **怀疑「是不是彻底抓瞎」** | **`custom__hit_rate`** | 唯一能回答这个问题的指标 |
| **改了 prompt / 换了生成模型** | **必须上 ragas** | custom 对生成段一无所知 |
| **阶段性验收 / 发版前** | **两组都跑** | 一组测「捞对没」，一组测「答好没」 |
| **判断重排好坏** | ⚠️ **两组都不能单独信** | 见 [05 章 § 2.2](05-meta-evaluation.md) |
| **线上生产流量** | **只能用 ragas 的两项** | 线上没有 chunk 级标注 |
| **没有 chunk 级金标** | **custom 用不了** | 它的输入就是 `expected_chunk_ids` |

> 💡 **最后一行是 custom 的硬前提**：它依赖一份标好「该捞哪几个片段」的金标。**没有这份清单，这四个指标一个都算不出来** —— 而造这份清单本身就是 [04 章](04-golden-set.md) 那一整章的工作量。
>
> 这也是 RAGAS 那两个 `context_*` 存在的意义：**在没有 chunk 级标注的场景下，它们是唯一能评检索的东西。**

### 顺带：这是个可插拔架构，不止两种

`evaluation.backends` 是**配置项**，不是写死的两个【代码】：

```yaml
evaluation:
  backends:
    - custom     # 想省钱就只留这个
    - ragas      # 想看语义质量就加上
```

本项目的设计原则之一是**评估后端可插拔** —— 将来接第三方库（如 DeepEval）只需注册 + 改配置，不改业务代码。所以「两种」是**当前启用了两个**，不是架构上只支持两个。

## 实现与教科书的四处差异

读代码之前先知道这些，能避免「怎么跟公式对不上」的困惑【代码】（[custom_evaluator.py:114-145](../../../src/libs/evaluator/custom_evaluator.py#L114)）：

| # | 差异 | 影响 |
|---|---|---|
| 1 | **nDCG 用二元增益**（`rel` 恒为 1），不是分级增益 | v2 金标里 0-3 的 grade **没有进入计算** —— 见下一节 |
| 2 | **IDCG 的理想命中数 = `min(|golden|, |retrieved|)`** | 当金标条数 > 返回条数时，IDCG 按返回条数封顶，nDCG 不会被结构性压低 |
| 3 | **Recall 的分母是金标全集**，不做 @k 二次截断 | 因为检索已在 top_k 处截断，效果上等于 Recall@10 |
| 4 | **没有 Precision** | 噪声侧由 `ragas__context_precision` 覆盖 |

## 一个可以自己去核实的发现

v2 金标（`golden_test_set_zh_v2.json`）每条 case 里，`_chunk_labels` 存了 LLM 判定的 **0-3 分级相关度**【代码】：

```json
{ "chunk_id": "...MetaTrader5SDK_Chinese.chm_2835_610f192b",
  "grade": 3,
  "reason": "The passage directly states that only applications running on the main server can...",
  "contributed_by": ["dense", "sparse", "rerank"] }
```

但被接受的 chunk 会**平铺**进 `expected_chunk_ids` 这个扁平列表，而 `custom_evaluator` 只收到这个列表 —— **grade 信息在计算时被丢弃了**，grade=3 和 grade=1 的 chunk 在 nDCG 里贡献完全相同。

【推断】这是 nDCG 唯一相对其他指标的独有能力（§ 1 分级标注）目前没被用上。金标已经具备分级数据，是计算侧没接。是否值得接是另一个问题 —— 但至少你现在知道，**看到 `custom__ndcg` 时不要以为它用上了 LLM 的精细判定**。

## 用真实数字练一遍

两份真实报告【实测】：

| | run `80a82405`（英文，42 条） | run `0798cc98`（中文，6 条） |
|---|---|---|
| `custom__hit_rate` | 0.619 | 0.6667 |
| `custom__mrr` | 0.5016 | 0.6667 |
| `custom__recall` | 0.4238 | **0.30** |
| `custom__ndcg` | 0.4012 | 0.3645 |
| `ragas__context_recall` | 0.8333 | **0.8333** |

**先用 § 4 的读法解释英文那列**：hit_rate 0.619 说明约 38% 的问题一条相关材料都没捞到（这是主要矛盾）；recall 0.4238 说明捞到的问题里也只找回了不到一半的相关材料；mrr 0.5016 说明平均而言第一条正确材料排在第 2 位左右 —— **排序不算差，覆盖面才是短板**。

**再看中文那列的 0.30 和 0.8333**。这两个名字里都有 recall 的指标，差了将近 3 倍。原因在 01 章 § 4.3 说过：

- `custom__recall` = 0.30 —— 「检索到的 chunk ID，和金标列出的那些，重合了 30%」，纯集合运算
- `ragas__context_recall` = 0.8333 —— 「检索到的上下文，实际支撑了参考答案里 83% 的内容」，LLM 判断

**它们可以同时是对的**：捞到的 chunk 和金标列表对不上，但内容上确实覆盖了答案 —— 说明金标列的那几个 ID 未必是唯一能回答问题的 chunk。

> ⚠️ 这个观察直接通向第 04、05 章：**金标的 `expected_chunk_ids` 是怎么挑出来的？凭什么认为它是「唯一正确答案」？** 本项目有两代不同的挑法，导致的偏差是理解「重排指标为什么会跌」的关键。学完本章后请读 [golden-test-set-explained.md](../golden-test-set-explained.md)。
