## 0. 前置知识

这一节不讲结构化输出，只把后面会反复用到的概念先立起来。**每小节末尾标注它为哪一节铺垫**，你可以按需读。

### 0.1 LLM 是怎么生成文字的

这是理解 §4「约束解码」的**唯一前提**。只需要搞清四个词。

**token（词元）**：文本被切成的最小单位，**不等于字或词**。粗略地说，中文常 1–2 个字一个 token，英文常一个词或词根一个 token。`{"decision":` 这样的片段可能被切成 `{"`、`decision`、`":` 三个 token。

**词表（vocabulary）**：模型认识的**全部** token 的固定集合，通常几万到几十万个。模型永远只能从这个集合里挑，一个都不能多。

**logits**：模型的**唯一输出**。给定已有文本，它为词表里**每一个** token 打一个原始分数。

**采样（sampling）**：从这些分数里**挑一个** token 出来。

一次完整的生成是这样循环的：

```
输入: 已有的 token 序列   {"decision"
   │
   ▼
① 模型前向传播 ──▶ logits：给词表里每个 token 打分
                    ":"→3.2   " "→2.9   "keep"→1.1   "{"→-4.0  ...
   │
   ▼
② 采样：从这张分数表里挑一个                    ← temperature / top_p 在这里起作用
   │
   ▼
③ 挑中 ":"，拼回序列 → {"decision":
   │
   └──────── 回到 ①，再算一次 ────────
```

三个必须记住的推论：

1. **一次前向传播只产生一个 token。** 生成 100 个 token 就是跑 100 次。
2. **模型自己不「挑词」。** 它只产出分数表，挑词是第 ② 步做的——**而第 ② 步不在模型里**（§0.2 会看到这个分工的意义）。
3. **这个过程叫「自回归」**（autoregressive）：每一步的输出都被拼回输入，作为下一步的上下文。所以**先生成的内容会影响后生成的内容，反过来不成立**。

> **`temperature` 在机制上做了什么**：它在第 ② 步缩放分数表。`temperature=0` → 永远挑分最高的那个（确定性最强）；数值越大 → 分数表被「拉平」，低分 token 也有机会被选中（更随机）。
>
> 记住这一点：**`temperature` 不在模型里，它是采样阶段的参数。** §4 的约束解码跟它是**同一个位置的邻居**。

📎 **为 §4（约束解码原理）、§6.1（字段顺序）铺垫。**

### 0.2 一次 API 调用长什么样

本文所有代码都是 OpenAI 兼容格式（你项目的 `glm` provider 也是）。先把请求和响应的字段认全。

**请求**：

```python
resp = client.chat.completions.create(
    model="z-ai/glm-5.2",
    messages=[{"role": "user", "content": "..."}],   # 对话内容
    temperature=0.0,          # 采样温度，见 §0.1
    max_tokens=3000,          # 最多生成多少 token（★ 后面会反复出现）
    # ↓ 下面三个是「结构化输出」用的，本文主角
    response_format={...},    # §3.2 / §3.4
    tools=[...],              # §3.3
    tool_choice={...},        # §3.3.1
)
```

**响应**：

```python
resp.choices[0].message.content      # 模型说的话（字符串）
resp.choices[0].message.tool_calls   # 模型想调用的「函数」（§3.3）；没有时是 None
resp.choices[0].finish_reason        # 为什么停下来 ★
resp.usage.completion_tokens         # 这次生成了多少 token ★
```

**`finish_reason` 的取值**——这是全文最重要的**归因字段**：

| 取值 | 含义 | 意味着 |
|---|---|---|
| `stop` | 正常说完了 | 内容完整 |
| `length` | **撞到 `max_tokens` 上限被截断** | 内容**写了一半**，JSON 一定非法 |
| `tool_calls` | 通过 `tool_calls` 返回，不是普通文本 | §3.3 生效了 |
| `content_filter` | 被内容审查拦了 | — |

> ⚠️ **`content` 与 `tool_calls` 是二选一的。** 走了 tools 通道，`content` 通常是空的，数据在 `tool_calls[0].function.arguments` 里（**注意它是字符串，还要再 `json.loads` 一次**）。
>
> 反过来——**说好了走 tools 却发现 `tool_calls` 是 `None`**，就是 §3.3.1 那个「参数被静默忽略」的失效。

📎 **为 §3 全节、§8.6（探针）铺垫。不认识这几个字段，后面的代码和实测表都读不懂。**

### 0.3 pydantic 与 JSON Schema

**JSON Schema** 是一个标准：**用 JSON 来描述「一份 JSON 应该长什么样」**。它本身不是数据，是**对数据的规格说明**。

```json
{
  "type": "object",
  "properties": {
    "decision":   {"type": "string", "enum": ["keep", "drop", "borderline"]},
    "confidence": {"type": "number"}
  },
  "required": ["decision", "confidence"],
  "additionalProperties": false
}
```

读法：这是个对象；有 `decision`（字符串，只能是那三个值之一）和 `confidence`（数字）；两个都必填；不许有别的字段。

**pydantic** 是 Python 库，让你用类来写同一件事，并**自动互转**：

```python
from typing import Literal
from pydantic import BaseModel

class ScreeningVerdict(BaseModel):
    decision: Literal["keep", "drop", "borderline"]
    confidence: float

# 方向一：类 → JSON Schema（发给 API 用）
ScreeningVerdict.model_json_schema()     # 得到上面那段 JSON

# 方向二：dict → 对象（收到响应后用）
args = {"decision": "keep", "confidence": 0.95}
v = ScreeningVerdict(**args)
v.decision      # "keep"，且已校验合法
```

**关于 `**args`** —— 这是 Python 的**字典解包**语法，不是什么特殊魔法：

```python
args = {"decision": "keep", "confidence": 0.95}
ScreeningVerdict(**args)
# 完全等价于手写：
ScreeningVerdict(decision="keep", confidence=0.95)
```

`**` 把字典拆成关键字参数。所以 `ScreeningVerdict(**args)` 就是**造一个对象**——纯本地操作，不联网、不调模型。

它做两件事：① 你能用 `v.decision` 而不是 `args["decision"]`；② **校验**——`confidence` 传了字符串、或 `decision` 不在三个值里，**当场抛异常**，脏数据进不了下游。

📎 **为 §3.3、§3.4、§7 的所有代码示例铺垫。**

### 0.4 推理模型与推理 token

近年的模型很多是**推理模型**（reasoning model）：正式作答前，先在内部生成一大段「思考过程」。

关键在于这段思考的计费与配额：

```
        你设的 max_tokens = 800
   ┌──────────────────────────────────────┐
   │████████████████████████████░░░░░░░░░░│
   │  推理段（你看不见）         可见内容  │
   │  ~700 token                 ~100     │
   └──────────────────────────────────────┘
     ↑ 照样占额度、照样计费
```

- 推理段**占用 `max_tokens` 配额**
- 推理段**照常计费**
- 但它**通常不出现在 `content` 里**——你看不到它

于是会出现一个极其反直觉的现象：

> **`content` 是空字符串，但 `completion_tokens` 是 800。**
>
> 模型烧光了预算却一个可见的字都没给你。这**看起来像「模型不听话」，实际是预算问题**。

【实测】本项目在用的三个模型**全是推理型**，推理段占 completion token 的 **85–90%**（§8.2 有数据表）。这直接解释了项目历史上 `max_tokens=200` 导致「空响应」的那次误诊。

📎 **为 §8.2、§8.6、§9.2 第 1 条铺垫。这是全文最实用的一条前置知识。**

## 1. 问题的起点：LLM 只会吐字符串

先认清一个物理事实：

> **LLM 只会做一件事——预测下一个 token。它的输出，本质上永远是一串字符。**

而调用方的程序需要的是**有类型、能直接参与运算的值**。举个具体例子（本项目预筛判定的形状，见 §8）：

```python
decision: Literal["keep", "drop", "borderline"]   # 要拿去做分支
confidence: float                                  # 要跟阈值 0.80 比大小
reason: str
```

> ⚠️ **这只是一个例子，不是什么通用格式。** schema 的形状完全由任务决定：情感分类可能只要一个枚举值，实体抽取要的是 `list[Entity]`，意图路由要的是一个受限字符串。**普适的不是字段名，是「值有类型、无需解析即可使用」这件事。**

这中间有一道鸿沟。**「结构化输出」就是架在这道鸿沟上的桥**——让本质是字符串的东西，可靠地变成有类型、有字段、可校验的对象。

注意关键词是**可靠**。「让模型吐 JSON」谁都会写，难的是「保证每一次都吐得出来、且吐对」。整个话题的全部技术含量都在「可靠」这两个字上。

### 1.1 什么时候**不**需要结构化输出

先划清边界，免得到处滥用。判据只有一条：

> **输出是给人看的，还是给代码看的？**

| | 下游 | 要不要结构化 |
|---|---|---|
| 聊天、摘要、翻译、改写 | 人 | **不要**。字符串就是最终产物 |
| 分类、抽取、评分、路由 | 代码 | **要**。字符串是障碍 |

本项目里的两条路径正好是对照：

- **`response_builder` 生成带引用的答案** → 给人读的，字符串**就是**产物。强行套 schema 只会削弱表达力，还会触发 §6.1 的推理空间损失。
- **`testset_screener` 的判定** → 要跟 `keep_threshold` 比大小、决定路由。这里必须结构化。

还有个**中间态**：一部分给人看、一部分给代码看。比如「答案正文 + 引用 chunk_id 列表」——这时照样用结构化输出，schema 里就是一个长文本字段 + 一个 id 数组。**字段内部可以装自然语言，两者不冲突。**

## 2. 三层可靠性：先把「结构化输出」拆开

这是理解后面所有内容的前提。「输出是对的」其实包含三件独立的事，越往下越难：

| 层次 | 要求 | 失败长什么样 | 谁能保证 |
|---|---|---|---|
| **① 语法合法** | 能被 `json.loads` 解析 | 少个括号 / 引号没转义 / 被截断 | **约束解码可 100% 保证** |
| **② 结构符合** | 字段齐全、类型正确、枚举值合法 | 返回 `{"结果": "相关"}`，字段名对不上 | 严格模式 Structured Outputs 可保证 |
| **③ 语义正确** | 这个判断本身是对的 | `decision="keep"` 但实际该 drop | **没有任何机制能保证** |

**所有实现方法之间的差异，只发生在 ① 和 ②。③ 永远是模型能力问题。**

这个划分的实用价值在于**归因**。当你看到「judge 失败率 55%」时，它其实混着两类完全不同的原因：

- 落在 ① / ② 的部分 → **是工程缺陷，可以被机制彻底清零**
- 落在 ③ 的部分 → 是模型或输入的问题，换实现方法一点用没有

分不清这两者，就会出现「换了个更强的模型，失败率降了，于是以为模型更聪明」——实际可能只是新模型**更自觉地遵守格式**而已，判断力并没有变。

## 3. 四种实现方法

> **前置**：这一节全程用 §0.2 的 API 字段和 §0.3 的 pydantic 写法。不熟就先回去看一眼。
>
> **本节路线图**：四种方法按可靠性从低到高排，**每一种都在补上一种的缺口**——
>
> ```
>  3.1 提示词请求      → 零强制力，全靠模型自觉        ┐
>  3.2 JSON Mode       → 保证是 JSON，但字段可能全错   │ 缺口逐层收窄
>  3.3 Function Calling→ 借 tools 通道，schema 真生效  │
>  3.4 约束解码        → 物理上无法违规               ┘
> ```

按可靠性从低到高。

### 3.1 提示词 + 解析（prompt + OutputParser）

**机制**：在提示词里写「请输出 JSON，格式为……」，模型自由生成，你自己 `json.loads`。

```python
prompt = """判定这条金标用例，只输出 JSON，不要有其他文字：
{"decision": "keep|drop|borderline", "confidence": <0-1的小数>, "reason": "<理由>"}"""
raw = llm.generate(prompt)
data = json.loads(raw)   # 🙏
```

**本质**：**纯粹的请求，零强制力。**

模型完全可以回你：

````text
好的，这是判定结果：

```json
{"decision": "keep", ...}
```

希望对你有帮助！
````

它没做错任何事——你只是「请求」了它，没有任何机制阻止它说人话。承受后果的是你的解析器。

**典型失效模式**（后面会看到本项目全中）：

| 失效 | 原因 | 属于哪层 |
|---|---|---|
| markdown 代码围栏包裹 | 模型觉得这样更好读 | ① |
| 前后夹带解释文字 | 模型的对话本能 | ① |
| 字符串内引号/换行未转义 | 生成内容与转义是两个任务 | ① |
| 输出被 `max_tokens` 截断 | JSON 写一半 = 语法非法 | ① |
| 字段名用了中文或同义词 | 提示词只是建议 | ② |

**它唯一的优点是普适**——任何模型、任何端点都能用，不依赖任何 API 能力。所以它永远是最后的兜底方案。

### 3.2 JSON Mode

**机制**：API 参数 `response_format={"type": "json_object"}`，服务端保证返回**合法 JSON**。【文献】

```python
resp = client.chat.completions.create(
    model="...", messages=[...],
    response_format={"type": "json_object"},
)
json.loads(resp.choices[0].message.content)   # 这行不会炸
```

**⚠️ 最容易误解的一点**：它只保证**是 JSON**，**完全不保证符合你的 schema**。它可能给你：

```json
{"结果": "相关", "备注": "这段讲的是配置"}
```

合法 JSON，你要的字段一个都没有。

> **JSON Mode 解决了 ①，完全没碰 ②。** schema 依然只能写在提示词里，模型看不看是它的事。

另有一个实践约束【文献】：多数实现要求**提示词里必须出现 "JSON" 字样**，否则 API 直接报错——这是为了防止模型陷入无限空白生成。

### 3.3 Function Calling（函数调用）

**机制**：把 schema 转成 JSON Schema 塞进 `tools` 参数，用 `tool_choice` **强制**模型「调用」它，再把参数捡走。

> **关于 `ScreeningVerdict`**：它是本项目真实存在的类（[`testset_screener.py:115`](../../src/observability/evaluation/testset_screener.py#L115)，字段 `case_index`/`decision`/`confidence`/`reason`），全文示例做了简化并统一用它。探针脚本里对应的 tool name 是 `screening_verdict`。
>
> 但要分清：**发给 API 的 `"name"` 只是个字符串标签**，与本地类无绑定，改成 `"abc123"` 照样能跑（§3.3.2 第 3 条）。**类是真的，标签是任意的。**

```python
resp = client.chat.completions.create(
    model="...", messages=[...],
    tools=[{
        "type": "function",
        "function": {
            "name": "ScreeningVerdict",                        # ← 假函数，永不执行
            "parameters": ScreeningVerdict.model_json_schema(), # ← schema 走正式通道
        }
    }],
    tool_choice={"type": "function",
                 "function": {"name": "ScreeningVerdict"}},     # ← 强制，不给它说人话的退路
)
args = json.loads(resp.choices[0].message.tool_calls[0].function.arguments)
ScreeningVerdict(**args)   # pydantic 二次校验
```

**为什么比前两种可靠**，两个独立原因：

1. **schema 走的是结构化通道，不是提示词。** 模型在训练时见过海量「给你 JSON Schema，产出对应参数」的样本，这是被专门训练过的技能，不是靠临场理解自然语言指令。
2. **`tool_choice` 强制**掐死了「模型决定用大白话回答」这条退路。

**但它不保证 100% 合规**——多数实现下模型仍是自由生成参数，只是极大概率对。这是「工程上够用」和「数学上保证」的区别。

#### 3.3.1 `tools` 与 `tool_choice`：清单与策略

两个正交的维度，缺一不可：

```python
tools=[...]        # 「你有哪些表格可以填」  —— 供给（清单）
tool_choice=...    # 「这次你必须填哪张」    —— 策略
```

**`tools` 只是告知，不构成任何要求。** 只传 `tools` 不传 `tool_choice`，模型完全可以看一眼说「我不用，我直接说」——这对 agent 是**正确行为**，对结构化输出是灾难。

类比：`tools` 是**菜单**（店里有什么菜），`tool_choice` 是**今天怎么点**。菜单不决定你吃什么。

`tool_choice` 的四档【文献】：

| 取值 | 含义 | 典型场景 |
|---|---|---|
| `"auto"` | 模型自己决定调不调、调哪个（**有 tools 时的默认值**） | **agent loop**——该查资料就查，够了就回答 |
| `"none"` | 不许调，正常说话 | 临时禁用工具但不想改 `tools` 列表 |
| `"required"` | 必须调一个，但调哪个由模型选 | 「要么给答案，要么给澄清问题」这种多选一 |
| `{"type":"function","function":{"name":"X"}}` | 必须调 **X** | **结构化输出**——本文用的就是这个 |

**为什么不能合并成一个字段**，三个理由：

1. **主要用途本来就是「模型自己选」。** function calling 的本职是 agent——给 5 个工具让它自己判断。若「给了工具就必须调」，核心场景直接没了。
2. **生命周期不同。** `tools` 是静态的（定义一次、每轮原样重发），`tool_choice` 是每轮可变的。agent loop 里很常见：前几轮 `"auto"` 让它自由探索，探索够了切成强制 `final_answer` 逼它交卷。合并了就得每轮重建整个列表。
3. **`"none"` 无处安放。** 想临时禁用，合并后只能传空 `tools`——但那样模型**看不到工具定义了**，跟「看得到但这次别用」不是一回事（对提示缓存也不友好）。

> ⚠️【实测】**`tool_choice` 是你的请求，不是保证。** 探针首轮有一条：明明传了强制，`z-ai/glm-5.2-free` 仍返回一段散文，`tool_calls` 为 `None`，HTTP 200 无报错。第二轮同一条又通过了——**间歇性静默失效，比彻底不支持更危险**。
>
> 所以调用方**必须检查 `tool_calls` 是否为空**，且能力探测**不能只测一次**。

#### 3.3.2 「假函数」是什么意思

先纠正一个几乎人人都有的误解：**模型从来没有执行过任何函数**，即使在真正的工具调用场景里也一样。

你发给 API 的从来不是代码，只是一段**描述**（name + 参数的 JSON Schema）。模型看不到你的代码，也没有运行时。它做的唯一一件事是生成一段文本，表示「我想调用 X，参数是 Y」。

> **「函数调用」这个名字本身就有误导性。模型产出的是调用意图，不是调用行为。真正执行的永远是你。**

所以真函数和假函数的差别，**只在你收到响应之后**：

```
                    真工具调用                          结构化输出
                    ─────────                          ─────────
  你的代码里     def get_weather(city):              class ScreeningVerdict(BaseModel):
                     return requests.get(...)             decision: str
                 ↑ 真实存在、能跑                     ↑ 只是数据定义，不可执行

  发给 API       {"name": "get_weather",             {"name": "ScreeningVerdict",
                  "parameters": {...}}                "parameters": {...}}
                 ↑ ────────── 这两行完全同构 ──────────↑

  模型返回       tool_calls[0].arguments             tool_calls[0].arguments
                 = {"city": "北京"}                   = {"decision": "keep", ...}
                 ↑ ────────── 这两行也完全同构 ────────↑

  你接下来做     result = get_weather("北京")        ScreeningVerdict(**args)
                 ↓ 结果塞回消息，再请求一次           ↓ 结束。就这样。
                 → 第二轮调用模型（agent loop）      没有第二轮
                 ↑ ═══════ 差别只在这里 ═══════↑
```

「假」具体假在：

1. **全项目搜不到 `def ScreeningVerdict(...)`** —— 项目里那个是 `@dataclass class`，**不是函数，不可调用**
2. 传进去的甚至是个 **pydantic class**，不是函数。API 那个 `"function"` 字段名纯粹是历史包袱
3. **`name` 完全是个标签**，叫什么都行——它只用于在多个 tool 间区分，而你只有一个且强制调用
4. `tool_choice` 强制后模型只有这一条路，**这才是可靠的来源**

> **API 里那个「函数形状的槽位」，是当时唯一被专门训练过的「按 schema 产出数据」通道。** 结构化输出去借用它，不为调用什么，只为蹭这条通道的可靠性。**函数只是外壳，schema 才是内容。**

⚠️ 精确性补充：确实存在少数由服务端执行的内置工具（代码执行、网页搜索类）。那是独立的产品能力，与这里讨论的「你自己定义的 tools」是两回事——后者永远由你执行。

##### 「它什么都不干，那要它干嘛」

这是最常见的卡点，值得单独回答：**对，它确实什么都不干。它的作用不是「做事」，是「规定答案长什么样」。**

想象你要考 100 个学生同一道题：

- **方式 A（问答题）**：「请判断这条用例该保留还是丢弃，说明理由。」学生答：*「我认为应该保留。理由是问题清晰、上下文支持……希望我的分析对您有帮助！」*
- **方式 B（答题卡）**：递一张表格，必须填：`【判定】□keep □drop □borderline  【置信度】___  【理由】___`

三个问题：答题卡本身「干」了什么事吗？**没有，它只是张纸。** 学生的思考变了吗？**没有。** 那它的意义在哪？**你能用机器批卷了。**

**假函数就是那张答题卡**：`tools` = 把表格递过去，`tool_choice` 强制 = 「必须填表，不许口头作答」。

**同一个模型、同一个问题、同一个判断结果**，只差「递没递表格」【实测】：

| | 不用假函数（baseline） | 用假函数（tools） |
|---|---|---|
| 返回长什么样 | ` ```json ... ``` ` 外面裹着客套话 | `{"confidence":0.95,"decision":"keep",...}` |
| 6 次调用产出**纯 JSON** | **0 次** | **6 次** |
| minimax 耗时 | 14.9 秒 | **3.0 秒** |
| minimax 输出 token | 579 | **76** |

快 5 倍省 87% 的原因：不给表格时模型要先写一堆推理散文再挤出 JSON；给了表格它直接填格子（`finish_reason=tool_calls`，几乎不走推理段）。

> **那为什么非得长成「函数」的样子？** 因为你只有这一种信封。你真正想寄的是那份 schema，但 API 参数里能装 JSON Schema 的槽位只有 `tools`——它当初是为工具调用设计的，所以长成函数的样子。**你要送的是信，但邮局只卖一种信封。**

#### 3.3.3 外部工具与假函数：同一条通道，方向相反

它们不是并列的两个东西，是**同一个 `tools` 通道的两种用法**，解决的问题毫无交集：

| | 外部工具 | 假函数 |
|---|---|---|
| 模型缺什么 | 缺**信息/能力**（不知道天气、不能跑 SQL） | **什么都不缺**，它已经知道答案 |
| 缺的是谁的 | 模型的 | **你的**——你缺一个可被代码消费的格式 |
| 数据方向 | 外部 **→** 模型 | 模型 **→** 你的代码 |
| 要不要回到模型 | **必须**，否则结果没意义 | **不用**，参数本身就是终点 |
| 调用轮数 | ≥ 2 轮（agent loop） | 1 轮 |
| 那个函数 | 真实存在，会被执行 | 不存在，永不执行 |

> **外部工具解决「模型不知道」，假函数解决「模型知道，但说出来的形式我没法用」。** 前者是能力问题，后者是格式问题。互相替代不了。

以本项目预筛为例：没有任何外部工具能帮上忙——它不缺信息（contexts 已喂给它）、不缺算力（要的是主观判断）。缺的只是「怎么保证它吐 `confidence: 0.85` 而不是『我觉得大概八成能留』」。

**那为什么要挪用同一条通道？** 纯粹是历史（见 §6.3 时间线）：2023-06 到 2024-08 之间，`tools` 是唯一被训练过的 schema 通道，想拿结构化数据只能借道。**假函数是 workaround，不是设计。**

**挪用的代价是两者会打架**：

```python
tools=[{"function": {"name": "search_corpus", ...}},   # 真工具
       {"function": {"name": "ScreeningVerdict", ...}}]       # 假函数
tool_choice={"type": "function",
             "function": {"name": "ScreeningVerdict"}}        # ← 强制 → 真工具永远调不到
```

要么强制（拿到可靠格式，模型丧失用真工具的自由），要么不强制（模型可能选真工具，结构化输出落空）。**这就是 §6.2「占用 tools 通道」的具体来源。**

而 §3.4 的 `json_schema` 走的是 `response_format` 参数，与 `tools` 是**两条独立通道，可同时使用**——这是它相对 function calling 的一个实打实的优势。

**结论：假函数正在退役。**

| 场景 | 该用什么 |
|---|---|
| 模型需要外部能力 | **真工具**，function calling 的本职，不可替代 |
| 只要结构化数据，端点支持 `json_schema` | **走正路**，别用假函数 |
| 只要结构化数据，端点不支持 `json_schema` | 假函数仍是最好选择 |
| 两者都要 | `json_schema` + `tools` 并用 |

### 3.4 约束解码 / Structured Outputs（严格模式）

**机制**：`response_format={"type": "json_schema", "json_schema": {..., "strict": true}}`。【文献】

这是唯一**从数学上**保证 ① 和 ② 的方案。原理见 [§4](#4-约束解码原理为什么它能-100-保证)。

```python
resp = client.chat.completions.create(
    model="...", messages=[...],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "ScreeningVerdict",
            "schema": ScreeningVerdict.model_json_schema(),
            "strict": True,          # ← 关键。不加就退化成普通 json_mode
        },
    },
)
```

**代价**：见 [§6](#6-取舍为什么不是越新越好)，不是免费的。

### 3.5 四种方法对照

| 方法 | 保证 ① 语法 | 保证 ② 结构 | 依赖 | 普适性 |
|---|---|---|---|---|
| 提示词 + 解析 | ❌ | ❌ | 无 | **任何模型** |
| JSON Mode | ✅ | ❌ | API 支持 | 中 |
| Function Calling | 🔶 极大概率 | 🔶 极大概率 | 模型支持 tools | 中 |
| 约束解码严格模式 | ✅ **数学保证** | ✅ **数学保证** | 模型 + API 都支持 | 低 |

> **§3 小结**：四种方法的差别在于**「谁来保证格式」**——
>
> | | 谁在保证 |
> |---|---|
> | 3.1 | **模型自觉**（你只是请求） |
> | 3.2 | 服务端保证「是 JSON」，schema 仍靠自觉 |
> | 3.3 | 模型走**被专门训练过**的 tools 通道 |
> | 3.4 | **采样层强制**，物理上违反不了 |
>
> 从「求它」一路走到「它做不到不合规」。接下来 §4 解释最后一步的原理，§5 说清约束的边界，§6 说清代价。

## 4. 约束解码原理：为什么它能 100% 保证

这一节讲清楚了，前面所有结论就都站得住了。

> **前置**：需要 §0.1 的四个概念（token / 词表 / logits / 采样）。**没读过 §0.1 的话这一节会看不懂**，那里只有几分钟。

回顾 §0.1：每一步，模型在**整个词表**上算出一张分数表（logits），然后由**采样**从中挑一个 token。注意这个分工——**挑词的不是模型**。

约束解码就插在**模型算完、采样之前**的那个缝隙里：

```
                        ┌─────────────────────────────┐
   已生成前缀           │  模型前向传播               │
   {"confidence":  ───▶ │  → 全词表 logits            │
                        └──────────────┬──────────────┘
                                       │
                        ┌──────────────▼──────────────┐
                        │  语法状态机                  │   ← 约束解码在这里
                        │  「当前位置只能接数字」       │
                        │  → 把所有非数字 token        │
                        │     的概率强行置为 -inf      │
                        └──────────────┬──────────────┘
                                       │
                                  采样 ▼
                                只可能是 0-9
```

关键在于最后一句话：

> **模型不是「被要求」输出合法 JSON，而是它在物理上没有能力输出非法 JSON**——那些 token 根本不在候选集里，概率是 0。

这就是为什么它能给出**数学保证**，而不只是「概率很高」。提示词能被忽略，训练偏好会失效，但一个概率为 0 的 token 不可能被采样出来。

**推论**（很多困惑都能用它解开）：

- 截断（`max_tokens` 耗尽）**仍然会炸**。约束解码保证「生成出来的部分合法」，不保证「写得完」。**这一层永远要自己管。**
- ③ 语义层完全不受影响。约束能让模型必须输出 `0-3` 之间的整数，但**不能让它输出正确的那个**。

## 5. 「语法」不等于 JSON

上面一直拿 JSON 举例，但**约束解码这个机制跟 JSON 没有任何绑定关系**。这里的「语法」是形式语言意义上的 grammar。

### 5.1 约束表达力的光谱

约束解码真正需要的能力只有一个：**给定已生成的前缀，能回答「下一个 token 有哪些合法」**。任何能回答这个问题的形式化描述都能用：

| 约束形式 | 例子 | 典型实现【文献】 |
|---|---|---|
| **枚举 / 选择** | 只能是 `相关` / `不相关` / `部分相关` | 最简单，屏蔽所有偏离候选串的 token |
| **正则** | `^\d{4}-\d{2}-\d{2}$`、`^[0-3]$` | Outlines、vLLM `guided_regex` |
| **JSON Schema** | 你熟悉的那个 | 先编译成 CFG，是上一层的特例 |
| **任意上下文无关文法** | SQL、XML、Cypher、自定义 DSL | llama.cpp **GBNF**、XGrammar、guidance |

所以你完全可以约束模型：

- **只能输出合法 SQL**——给它 SQLite 文法 + 你的表名列名作为终结符，它连「查询不存在的列」都做不到
- **只能输出闭合的 XML**
- **只能输出 `0`/`1`/`2`/`3` 四个字符之一**——这时你连解析都不需要了

**JSON Schema 只是「把常用的一类 CFG 包了个标准化的壳」。** 厂商 API 为通用性只暴露这一层；本地推理（llama.cpp / vLLM / Outlines）能给你完整 CFG 表达力。

### 5.2 那为什么现实中几乎全是 JSON

1. **JSON Schema 是既成标准**，pydantic / TypeScript / OpenAPI 一键互转。写个 `BaseModel` 就免费得到 schema，这个生态优势压倒一切。
2. **文法极小、好编译**——嵌套靠一个栈就能跟踪，增量判断开销接近常数。
3. **训练数据里密度极高**，模型对它的先验最强。这条比想象中重要：约束解码保证形式，但如果模型对某格式极不熟悉，会被逼到概率很低的 token 上，**内容质量会崩**。
4. **厂商要选通用最大公约数**，JSON 是唯一答案。

### 5.3 两个必须知道的限制

**限制一：不是所有格式都能被完整约束。**

约束解码要求能在**任意前缀处**判断合法集。正则语言和大部分 CFG 没问题，但**上下文相关**的东西无能为力：

- **Python 缩进**（层级依赖上下文，不是 CFG）
- **YAML**（缩进敏感 + 大量隐式类型规则，臭名昭著地难约束）
- **「变量须先声明后使用」**——这压根不是语法问题，是语义问题

所以你会看到：保证「合法 JSON」的库很多，保证「合法 Python」的基本没有。

**限制二：字符 vs token 的错位。**

**文法定义在字符上，模型生成的是 token**，而一个 token 可能横跨语法边界。

比如词表里可能有个 token 就是 `":` （引号+冒号连在一起）。当状态机说「现在必须先来一个 `"` 结束字符串」时，这个 token 合不合法？合法的话它顺带把冒号也吐出来了，状态机得跟着跳两步。

处理这个叫 **token healing / token-grammar alignment**，是 XGrammar 这类库的核心工作量。用现成库时不用管，但它解释了为什么「约束解码」听起来简单、实现却自成一个技术领域。

---

## 6. 取舍：为什么不是「越新越好」

这节最反直觉，也最重要。**约束解码不是免费午餐。**

### 6.1 推理空间的损失（影响最大）

约束解码强迫模型**第一个 token 就是 `{`**。模型因此**失去了「先想一想再回答」的空间**。

而 LLM 的推理能力高度依赖于「把思考过程写出来」——这正是 CoT（Chain-of-Thought）有效的原因。不让它写，它就得凭直觉一步到位给出 `decision`。

**对 judge / 评分类任务，这个损失是实打实的**：判定相关度本来就需要先分析再打分。

**解法（这条可以直接用）**：把 reasoning 字段**放进 schema，并且放在最前面**。

```python
class ScreeningVerdict(BaseModel):
    reason: str                                        # ← 必须在最前
    decision: Literal["keep", "drop", "borderline"]    # ← 生成它时，reason 已在上下文里
    confidence: float
```

> **字段顺序在这里不是风格问题，是能力问题。**
>
> LLM 是自回归的、严格从左到右生成。
> - `reason` 在**前** = 模型在 JSON 内部完成了一次 CoT，`decision` 是基于分析得出的
> - `reason` 在**后** = `decision` 已经拍板了，`reason` 只是**事后编的理由**（post-hoc rationalization）
>
> 两者的字段完全一样，判断质量可能差很多。

⚠️ 注意：JSON 对象在规范上是无序的，但**生成顺序**有序。严格模式下多数实现按 schema 声明顺序生成，但这属于实现细节，换 provider 时值得确认。

> 🔴【实测】**这个技巧在本项目网关的 tools 通道上不可靠。** 探针里 schema 声明的顺序是 `reason` → `decision` → `confidence`，实际返回：
>
> | 模型 | 实际字段顺序 | 是否遵守声明顺序 |
> |---|---|---|
> | `z-ai/glm-5.2` | `reason` 在前 | ✅ |
> | `minimax/minimax-m2.7` | **`confidence` → `decision` → `reason`** | ❌ 完全颠倒 |
>
> minimax 把 `reason` 甩到了最后，也就是**退化成了事后编理由**——而它正是本项目的 judge。
>
> **结论：字段顺序技巧值得做（零成本），但必须验证它真被遵守，不能假定。** 验证方法就是看实际返回的键序。

### 6.2 其他取舍

| 取舍 | 说明 |
|---|---|
| **占用 tools 通道** | `function_calling` 方案下，如果场景本身要用真工具，两者会打架 |
| **schema 表达力受限** | 严格模式常要求所有字段 `required`、`additionalProperties: false`、限制嵌套深度、不支持部分字符串校验关键字【文献，以最新文档为准】。复杂 schema 可能根本用不了 |
| **首次调用编译开销** | schema 要编译成状态机/语法，首次有额外延迟 |
| **流式输出变复杂** | 流式场景下拿到的是不完整 JSON，需要增量解析（partial JSON parsing） |
| **格式熟悉度** | 见 §5.2 第 3 条，把模型逼进陌生格式会伤害内容质量 |

### 6.3 为什么会有这么多种方法

三个原因，都很现实：

**① 历史层积，不是设计出来的。**【文献】

```
2022       提示词 hack 是唯一选择（社区自己发明 OutputParser）
2023-06    OpenAI 推出 function calling  ← 为工具调用设计，被大家挪用来拿 JSON
2023-11    推出 JSON mode               ← 官方承认「原来大家只是想要 JSON」
2024-08    推出 Structured Outputs       ← 用约束解码彻底解决
```

每一代出来时上一代已有海量代码在跑，**不能删**。兼容层只能全都留着。

**② 供给侧是碎片的。**

| provider 类型 | 可用的路 |
|---|---|
| OpenAI 较新模型 | 四种全有 |
| Anthropic | tool use（≈function_calling），无 json_mode |
| 老模型 / 小模型 | 只有提示词 |
| **OpenAI 兼容端点**（如本项目的 `glm`） | **未知——文档说支持，实际透传与否要实测** |

**③ 真有取舍**，见 §6.1、§6.2。不是纯粹的「新的更好」。

## 7. LangChain 的 with_structured_output 在哪一层

```python
from typing import Literal
from pydantic import BaseModel, Field

class ScreeningVerdict(BaseModel):
    reason: str = Field(description="判定理由")
    decision: Literal["keep", "drop", "borderline"]
    confidence: float = Field(ge=0.0, le=1.0)

structured_llm = llm.with_structured_output(ScreeningVerdict)
result = structured_llm.invoke("query: ...\nchunk: ...")

result.decision     # 已校验的枚举值，不是随便一个字符串
result.confidence   # float，已被 pydantic 校验在 [0,1]
```

**关键认识**：`with_structured_output` 是一个**接口**，不是一种实现。它底层就是 §3 那四条路，靠 `method` 参数选：

| `method` 取值 | 对应 §3 的 |
|---|---|
| `"function_calling"` | §3.3（多数 provider 的默认） |
| `"json_mode"` | §3.2 |
| `"json_schema"` | §3.4 |
| （不支持时回落到 OutputParser） | §3.1 |

**它的价值是抹平 provider 差异**——OpenAI 用 `tools`、Anthropic 用 `tool_use`、Gemini 又不一样，`with_structured_output` 让你写一份代码。代价是抽象层厚、版本耦合紧。

一个实用参数【文献】：

```python
llm.with_structured_output(ScreeningVerdict, include_raw=True)
# 返回 {"raw": 原始消息, "parsed": 对象或 None, "parsing_error": 异常或 None}
# 解析失败时不抛异常 —— 生产环境需要做降级时用这个
```

**是否要为了它引入整个 LangChain？** 对本项目这种 provider 无关设计，更贴合的做法是在自家 `BaseLLM` 上加一个 `generate_structured(schema)` 抽象方法，各 provider 实现里各走各的原生通道——这符合硬约束「provider 无关」，且不引入 LangChain 的版本耦合。【推演】

## 8. 本项目现状核验

> **本节起开始涉及本项目背景。** 不熟悉的读者只需知道这几个词：
>
> | 词 | 在本节里的意思 |
> |---|---|
> | **chunk** | 文档被切开后的一小段文本，检索的最小单位 |
> | **金标（golden set）** | 人工/半自动标注的评估用例集，用来量检索与回答质量 |
> | **judge** | 一个专门用来给结果打分的 LLM（不是被评测的那个） |
> | **预筛 / 标注** | 两个用 LLM 批量做判定的离线流程，各自都要 LLM 返回结构化判定 |
> | **`degraded_case_count`** | judge 输出没解析成功、指标记为 NaN 的用例数。**它是本节的主角** |
>
> 通用读者可以只看 [§8.6](#86-实测网关到底支持哪一档)（探针方法与实测数据），那部分的方法论脱离本项目也成立。

### 8.1 四处 LLM 判定全走 §3.1（最脆弱的一条路）

【代码】全仓解析 LLM 输出的地方，**没有一处使用任何 API 级保证机制**：

| 位置 | 做法 |
|---|---|
| [`testset_screener.py:438`](../../src/observability/evaluation/testset_screener.py#L438) | 剥 markdown 围栏 → 截取 `{...}`。**写得最严谨的一处** |
| [`chunk_labeler.py:482`](../../src/observability/evaluation/chunk_labeler.py#L482) | 同上 **+ 裸数字正则兜底**（见下方风险） |
| [`_ragas_wrappers.py:112`](../../src/observability/evaluation/_ragas_wrappers.py#L112) | 交给 RAGAS 0.1.21 内部解析 |
| `testset_synthesizer.py` | `json.loads` |

**证据一**【代码】：[`testset_screener.py:438`](../../src/observability/evaluation/testset_screener.py#L438) 的 `_extract_json_object` 需要手工容忍 markdown 围栏和前后夹带文字。

> **这段容错代码存在本身，就是「没走 §3.2-3.4 任何一条通道」的证据**——走了的话，这些偏差在 API 层就不会发生。

**证据二**【代码】：[`config/prompts/testset_screening.txt`](../../config/prompts/testset_screening.txt) 里写的是

```text
Respond with STRICT JSON only — no markdown fences, no commentary before or after
```

提示词里的「STRICT」是**请求，不是约束**。真正的 strict 是 API 参数里那个 `"strict": true`。

**证据三**【代码】：[`_ragas_wrappers.py:112`](../../src/observability/evaluation/_ragas_wrappers.py#L112) 把项目 LLM 包成的是

```python
from langchain_core.language_models.llms import LLM as _LangChainLLM
```

这是 **文本补全型**（Completion）基类，只实现了 `_call(prompt) -> str`。这类基类**没有 `bind_tools` 方法**——也就是说，当前包装下 function calling 通道**在接口层就走不通**，不是「没选」，是「没得选」。要改必须先换成 Chat 模型基类。

**证据四（一处独立风险）**【代码】：[`chunk_labeler.py:474`](../../src/observability/evaluation/chunk_labeler.py#L474) 在 JSON 解析全部失败后还有一层兜底：

```python
# 裸数字兜底：取第一个 0-3 的独立数字
match = re.search(r"\b([0-3])\b", text)
```

**这不是「解析失败就降级」，是「猜」。** 模型回一句「这段和问题有 2 处关联，但相关度我判不了」——会被解析成 `grade=2`。

而 [`testset_screener.py:441`](../../src/observability/evaluation/testset_screener.py#L441) 的注释写的是相反的原则：

> 但**不**从数组内部挖对象 —— 宁可降级为 borderline 也不猜测其意图

**同一个项目里，两处对「拿不准怎么办」的态度是相反的。** screener 那条才是对的——猜出来的标注会静默污染金标，而金标是所有评估结论的地基。

### 8.2 已经付过的学费

【代码】[`_ragas_wrappers.py`](../../src/observability/evaluation/_ragas_wrappers.py) 的注释里记着：

> labeling 路径正因为这个参数给少了（硬编码 200）出现过「367 字符的 chunk 就返回空响应」—— 表现得像「模型不遵从 JSON 格式」，真实原因是没给它写完的余量。

这是 §4 那条推论的完美案例：**截断的 JSON 一定语法非法，而这个错误在解析层长得跟「模型不听话」一模一样，无法区分。** 归因错了，就会去调提示词（无效），而不是调 `max_tokens`（有效）。

【实测】§8.6 的探针把机制测精确了：**这三个模型全是推理型，`completion_tokens` 里 85–90% 是不可见的推理段。**

| 样本（2026-08-16 实测） | 总输出 token | 其中推理 | 可见内容 |
|---|---|---|---|
| `z-ai/glm-5.2` baseline | 500 | 429 | **71** |
| `z-ai/glm-5.2-free` json_object | 854 | 849 | **5** |
| `z-ai/glm-5.2-free` json_schema | 713 | 625 | 88 |

所以 `max_tokens=200` 的失效不是「余量不够写完」，而是**200 个 token 全被推理段吃光，一个字都没轮到可见内容**——所以返回的是彻底的空字符串，而不是半截 JSON。

> **推论：`max_tokens` 的安全值要按「推理段 + 可见内容」估，不能按可见内容估。** 对推理型模型，前者是后者的 5–10 倍。

### 8.3 `degraded_case_count` 的归因困境

CLAUDE.md 记录的 `degraded_case_count: 23/42 = 54.8%`，按 §2 的三层拆开看，混着两类原因：

| 原因 | 属于 | 能否消除 |
|---|---|---|
| judge 输出被截断 / 转义炸了 / 带了围栏 | ① 语法 | **能，且可清零** |
| judge 真的判不出来（英文问题产出中文答案等） | ③ 语义 | 不能，得治输入侧 |

**当前架构下这两者分不开**——`_extract_json_object` 返回 `None` 时不区分原因。

CLAUDE.md 里那条「换强 judge 后 `context_precision` 降级率 26% → 5%」的观察，顺着 §2 读会更准确：强模型可能只是**更自觉地吐合法 JSON**（① 层改善），而不是判断力提升（③ 层）。而 `faithfulness` 仍有 29% 判不出，说明那部分**主要落在 ③ 层**——这跟 CLAUDE.md 的结论（病因在输入侧）是一致的。【推演】

### 8.4 一个可立即验证的假设

【代码】提示词里的字段顺序是：

```json
{"decision": "keep|drop|borderline", "confidence": 0.0, "reason": "one short sentence naming the criterion that decided it"}
```

**`reason` 在最后。** 按 §6.1，这意味着模型**先拍板 decision，再编理由**——`reason` 是 post-hoc rationalization，对 decision 质量零贡献。

【推演】把顺序改成 `reason` → `decision` → `confidence`，让模型先写分析再下结论，判定质量可能改善。**这是零成本改动（只动提示词），但本文未做实验验证**，落地前应该跑一次对照。

> 注意这条属于 ③ 语义层的改进，跟换实现方法（① ② 层）是两件独立的事，可以分别做。

### 8.5 两条独立的改进路径

| 路径 | 改动量 | 解决什么 | 风险 |
|---|---|---|---|
| **A. 换格式**：JSON → XML 标签 | 小，只动 prompt + 解析函数 | 消灭转义类失败；支持**字段级降级**而非整条作废 | 低，不依赖网关能力 |
| **B. 换通道**：接 function calling / json_schema | 大，要动 `BaseLLM` 抽象 + ragas 包装层 | 从根上消灭 ① 层失败 | 需先确认网关是否真透传 `tools` |

**路径 A 的原理**：在**无约束**场景下，JSON 恰恰是最脆弱的格式之一，因为它要求字符串内部转义：

```json
{"decision": "keep", "reason": "文档里说 "北极星" 是..."}   ← 炸了，引号未转义
{"decision": "keep", "reason": "第一点...
第二点..."}                                        ← 炸了，裸换行非法
```

而 `reason` 是模型自由生成的中文长文本，出现引号、换行是常态。**模型必须一边思考内容、一边正确转义——这是两个任务，它经常只顾得上一个。**

标签式格式没有这个问题：

```xml
<reason>文档里说 "北极星" 是...
可以随便换行、随便打引号，没有任何字符需要转义</reason>
<decision>keep</decision>
<confidence>0.85</confidence>
```

用 `<decision>(.*?)</decision>` 挖，**不存在「解析全炸」**——某字段挖不出时其他字段照拿，可做**字段级降级**。而 `reason` 恰恰是三个字段里最不影响下游决策的那个。

> 顺带解释一个现象：Anthropic 早期一直建议用 XML 标签而非 JSON 组织输入输出。不是品味问题，是**无约束生成下标签格式的鲁棒性确实更好**。

**路径 B 的前置**：本项目 `glm` provider 走的是 OpenAI 兼容端点、路由到 minimax/claude 等模型，相关参数**未必被真实透传**。CLAUDE.md 里「模型下架是这个网关的常态」的经验说明，**这个网关的行为不能靠文档推定**，必须探针实测。

探针要测**两件事，且有优先级**（理由见 §3.3.3）：

| 优先级 | 测什么 | 怎么判断支持 |
|---|---|---|
| **1（首选）** | `response_format: {"type": "json_schema", ..., "strict": true}` | 返回内容严格符合 schema；不报参数错误 |
| 2（退路） | `tools` + `tool_choice` 强制 | 响应里真的出现 `tool_calls` 字段，而非退化成普通文本 |

本项目四处判定（预筛、标注、judge、合成）**全是纯格式问题，无一需要真工具**，所以 `json_schema` 是首选，假函数只是它不可用时的退路。

⚠️ 兼容端点的典型失效是**静默的**：参数被接受但被忽略，返回一段普通文本。所以探针不能只看「有没有报错」，必须校验**返回结构本身**。这与 CLAUDE.md 里记录的多次「静默失效」是同一类问题。

**探针已实现并跑过，结果见 §8.6。**

### 8.6 实测：网关到底支持哪一档

【实测】2026-08-16，脚本 [`scripts/dev/probe_structured_output.py`](../../scripts/dev/probe_structured_output.py)，明细 `logs/structured_output_probe/probe_results.json`。3 个模型 × 4 模式 × 2 提示词，跑了两轮。

#### 探针的两个设计要点

**① 必须用「诱导违规」的提示词做对照。** 单看一次成功的输出，无法区分「模型自愿遵守」和「被约束解码强制」。所以每种模式跑两个提示词：

- `neutral` —— 正常判定请求
- `adversarial` —— 额外要求「先用两三句散文解释思路，再给判定」

真正的约束解码在 adversarial 下**物理上吐不出散文**；只是自愿遵守的模型会破功。

**② 必须抓 `finish_reason` 和 `usage`。** 首轮探针没抓，于是满屏「空响应」**无法归因**——分不清是截断、是推理段吃光预算、还是真的返回空。这正是本文反复警告的那个错误，我在探针里原样犯了一遍。

> 同轮还有一个教训：一条 **429 限流**因为错误文本里碰巧含关键词，被字符串匹配误判成 `REJECTED`（「该模型不支持 json_schema」）。**把「网关现在忙」读成了「网关没这个能力」，结论完全相反。** 分类必须看 HTTP 状态码，不能匹配错误文本。

#### 结果

| 模型 | 用途 | baseline | json_object | json_schema | tools |
|---|---|---|---|---|---|
| `z-ai/glm-5.2` | 答案生成 | 围栏/夹带 | OK | **OK** | **OK** |
| `minimax/minimax-m2.7` | judge | 围栏/夹带 | OK | **429，无结论** | **OK** |
| `z-ai/glm-5.2-free` | 预筛 / 标注 | 围栏/夹带 | 返回 list | **OK** | **OK** |

**① baseline 六战六败。** 三模型 × 两提示词，**没有一次产出纯 JSON**——全是 markdown 围栏或前后夹带文字。项目当前路径**每一次调用都在靠 `_extract_json_object` 兜底**，不是偶发。这是 §3.1「零强制力」最直接的证据。

**② 这个网关上 `tools` 比 `json_schema` 更可靠**——与 §9.1 决策树的通用排序相反：

| 通道 | 覆盖 | 备注 |
|---|---|---|
| `tools` | **3/3 模型、6/6 次调用全过**，零限流 | |
| `json_schema` | 2/3 模型有结论 | judge 用的 minimax 三次尝试 1 成功 2 限流 |

而且 `tools` 在 minimax 上**又快又省**：3.0 秒 / 76 token，对比 json_object 的 14.9 秒 / 579 token——**快 5 倍、省 87%**。`finish_reason=tool_calls`，模型直接填参数，几乎不走推理段。

> 这正是 §5「能力住在服务层」那一课的实例：**上游模型支持什么，推不出你这条链路上什么最可靠。** 通用建议（json_schema 优先）在这个网关上被实测推翻——这不说明通用建议错，说明**必须实测**。

**③ 确证了 §3.2 那条警告。** `z-ai/glm-5.2-free` 在 json_object 模式下返回了**顶层 list**。「JSON Mode 只保证是 JSON、不保证符合 schema」——实测到了。

#### 由实测导出的待办

【代码】**`labeling_llm.max_tokens: 800` 余量偏薄。** [settings.yaml:319](../../config/settings.yaml#L319) 的注释说「800 下全部完整且解析成功」（2026-08-13 在真实 chunk 上测的），但探针在**同一模型**（`z-ai/glm-5.2-free`）的可比任务上，中性提示词就消耗了 **786** 个 completion token——98% 的利用率。

> ⚠️ 限定：786 来自「预筛一条金标用例」，prompt 比「给一个 chunk 打分」长；854 那个数来自**故意诱导写散文**的对抗提示词，不代表真实负载。所以这是**余量风险**，不是已发生的失效。`max_tokens` 是上限不是配额，调高不产生额外成本，建议提到 3000。

#### ⚠️ 一条被否证的假设（保留记录，避免重蹈）

本文早期版本曾把「给 `judge_llm` 配 `max_tokens`」列为优先级 1，理由是「推理段占 85–90%，judge 不传这个参数 → 可能截断 → 降级」。

**这条是错的，且项目此前已经否证过：**

- 【代码】[`_ragas_wrappers.py`](../../src/observability/evaluation/_ragas_wrappers.py) 的注释写着「judge 路径**刻意不传** max_tokens……T-3.1 归因否证了这条：**595 次成功判定调用零空响应**，最长响应 3378 字符，模型在自由书写」
- 【代码】`JudgeLLMSettings` 的字段是 `provider / model / api_key / base_url / temperature / request_timeout_sec`，**没有 `max_tokens`，是刻意省略**——加一个不解决任何问题的配置项就是下一个死配置
- CLAUDE.md 记着完整归因（42 条冻结元组）：14 条真实判定失败**全部**是「英文问题 + 中文答案」，语言一致的 14 条**零失败**。**病因在输入侧**

**教训**：探针测出「推理段占 85–90%」是真的，但**从「机制上可能」跳到「就是它」少了一步**——而那一步（judge 路径的实际归因）项目里早有结论。**新证据不自动作废旧归因**；先查已有结论，再提假设。

> 这恰好是本文 §2 讲的那个错误的实例：把 ① 层的一个**可能性**，误当成 ③ 层已知病因的替代解释。

## 9. 决策树与速查表

### 9.1 选型决策树

```
模型/端点支持 json_schema 严格模式？
  ├─ 是 → 用它。记得 reason 字段放最前面（§6.1）
  └─ 否 → 支持 function calling / tool use？
           ├─ 是 → 用 function_calling
           └─ 否 → 支持 json_mode？
                    ├─ 是 → json_mode + 提示词写 schema + pydantic 事后校验
                    └─ 否 → 提示词 + 容错解析
                            ├─ 优先考虑 XML 标签而非 JSON（§8.5）
                            └─ 必须准备「解析失败」的降级路径
```

> ⚠️ **这棵树给的是理论优先级，不是你端点上的实际优先级。** §8.6 实测：本项目网关上 `tools` 反而比 `json_schema` 更可靠（3/3 vs 2/3），而且快 5 倍、省 87%。
>
> **树只用来决定「先测哪个」，不能用来决定「用哪个」。** 顺序由实测定。

### 9.2 不管用哪种，都要做的四件事

1. **`max_tokens` 按「推理段 + 可见内容」给，不是按可见内容给。** 约束解码不防截断（§4 推论）。【实测】推理型模型的推理段占 completion token 的 **85–90%**（§8.2），所以安全值是你预期输出长度的 **5–10 倍**。这是最容易被误诊为「模型不听话」的失败。
2. **事后仍用 pydantic 校验。** ② 层保证不一定有；③ 层从来没有保证。
3. **准备降级路径。** 用 `include_raw=True` 或等价机制，让解析失败**不抛异常**，而是记录并降级。
4. **区分失败原因。** 至少把「空响应/截断」和「格式非法」分开记，否则永远无法归因（§8.3 的教训）。

> 这四条是**最低要求**。完整的八条运营纪律见 [§10.1 B](#101-生产上推荐什么)。

### 9.3 一句话速查

| 你想要 | 答案 |
|---|---|
| 结构化输出是什么 | 让 LLM 的字符串输出**可靠地**变成有类型的对象 |
| 和 function call 什么关系 | 借用 function call 通道传数据，**假函数永不执行** |
| 哪个最可靠 | 约束解码（json_schema strict），唯一有数学保证的 |
| 「语法」一定是 JSON 吗 | **不是**，任何 CFG 都行，JSON 只是生态最好的那个 |
| 为什么方法这么多 | 历史层积 + provider 碎片化 + 真有取舍 |
| 约束解码的代价 | 剥夺了模型「先想再答」的空间 → 把 reason 字段放最前 |
| 什么它保证不了 | **③ 语义层**——判断对不对，永远是模型能力问题 |
| 该信通用建议还是实测 | **实测**。§8.6 里通用排序被本项目网关推翻了 |

## 10. 生产实践清单与本项目差距

### 10.1 生产上推荐什么

分两层，**第二层才是「生产」二字的重点**，也是最常被跳过的。

**A. 通道选择（理论优先级）**

| 优先级 | 方式 | 什么时候用 |
|---|---|---|
| 1 | `json_schema` + `strict` | 端点支持就用它，唯一有数学保证 |
| 2 | `tools` + `tool_choice` 强制 | 没有 1，或需与真工具共存于 agent loop |
| 3 | `json_mode` + pydantic 校验 | 只剩它时。**记得它不保证 schema** |
| 4 | 提示词 + 容错解析 | 兜底。这时**优先 XML 标签而非 JSON**（§8.5） |

> ⚠️ 这个顺序只用来决定「**先测哪个**」。§8.6 实测已把它在本项目网关上推翻。**生产上的选择由探针定，不由文档定。**

**B. 运营纪律（与通道无关，更重要）**

| # | 纪律 | 为什么 |
|---|---|---|
| 1 | **永远做 pydantic 二次校验** | ② 层保证不一定有，③ 层从来没有 |
| 2 | **单条失败不炸整批** | 用 `include_raw=True` 或等价机制，记录 + 降级 |
| 3 | **失败必须可归因** | 记 `finish_reason` / `usage`，把「截断 / 格式非法 / 语义判不出」分开 |
| 4 | **`max_tokens` 按推理段估** | 推理型模型推理段占 85–90%，安全值 = 预期输出 × 5–10（§8.2） |
| 5 | **检查 `tool_calls` 是否为空** | `tool_choice` 是请求不是保证，会被静默吃掉（§3.3.1） |
| 6 | **能力探测纳入回归，不是一次性** | 实测到**间歇性**静默失效——测一次通过会漏 |
| 7 | **`reason` 放最前，且验证真被遵守** | 实测 minimax 在 tools 通道上不遵守声明顺序（§6.1） |
| 8 | **拿不准时降级，不要猜** | 猜出来的值会静默污染下游（§8.1 证据四） |

**第 3 条是最容易跳过、代价最大的一条**——不做它，后面所有优化都无法判断有没有效。

### 10.2 本项目符不符合

**通道选择：不符合。** 四处全在第 4 档，而实测证明至少两条更好的路可用（`tools` 三模型全过、`json_schema` 两模型可用）。

**运营纪律：一半符合，符合的那部分质量不错**——这点要给项目公道：

| 纪律 | 现状 |
|---|---|
| 1 二次校验 | ✅ `_coerce_confidence` 校验 [0,1] 且排除 bool |
| 2 不炸整批 | ✅ 降级 borderline / `judge_failed`，不抛异常 |
| 3 **失败可归因** | ❌ **最大缺口**。`_extract_json_object` 返回 `None` 时不区分原因 |
| 4 max_tokens | ⚠️ labeling 800，实测同模型中性提示词已用 786（98%）。judge 不传是**刻意且已否证**，不是缺口 |
| 5 检查 tool_calls | — 不适用（未走 tools） |
| 6 探测纳入回归 | ❌ 无 |
| 7 reason 放最前 | ❌ 提示词里 `reason` 在**最后** |
| 8 拿不准就降级 | ⚠️ screener ✅ / chunk_labeler ❌（裸数字兜底在猜） |

### 10.3 差距清单（按性价比排序）

| 优先级 | 动作 | 成本 | 收益 |
|---|---|---|---|
| **1** | `labeling_llm` 800 → 3000（judge **不要**动，见 §8.6 被否证的假设） | 改 1 行配置 | 消除标注路径的余量风险。**不影响 `evaluate.py`** |
| **2** | 判定失败时记录 `finish_reason` / `usage`，区分截断与格式非法 | 约 20 行 | **让后续所有优化可被验证** |
| 3 | 提示词字段顺序 `reason` 提到最前 | 改提示词 | ③ 层可能改善，需对照验证 |
| 4 | 去掉 `chunk_labeler` 裸数字兜底，改为显式 `judge_failed` | 删 3 行 | 消除静默错标 |
| 5 | 判定路径改走 `tools` 通道 | 需动 `BaseLLM` 抽象 | 消灭 ① 层失败，minimax 上省 87% token |
| 6 | 探针纳入定期回归 | 已有脚本 | 防间歇性静默失效 |

> **2 是这份清单里唯一的关键路径。**
>
> `degraded_case_count 54.8%` 的病因 CLAUDE.md 已归因清楚（输入侧的语言错乱），**不是 `max_tokens`、不是通道**。所以 1 和 5 都不会显著改善它——1 治的是标注路径的余量风险，5 治的是 ① 层失败与 token 成本。
>
> 而 2（失败可归因）是**唯一能让后续任何改动被验证**的前置。先做它。

## 附录：术语表

**基础概念**（§0 引入）：

| 术语 | 含义 |
|---|---|
| **token（词元）** | 文本被切成的最小单位，不等于字或词 |
| **词表（vocabulary）** | 模型认识的全部 token 的固定集合，几万到几十万个 |
| **logits** | 模型的唯一输出：给词表里每个 token 打的原始分数 |
| **采样（sampling）** | 从 logits 里挑一个 token。`temperature` / 约束解码都作用在这一步 |
| **自回归（autoregressive）** | 每步输出拼回输入作为下一步上下文。**先生成的影响后生成的，反之不成立** |
| **`finish_reason`** | 响应字段，说明为什么停下。`length` = 被 `max_tokens` 截断 |
| **推理模型 / reasoning token** | 作答前先生成一段内部思考。**占 `max_tokens`、照常计费、通常不可见** |
| **pydantic `BaseModel`** | Python 库，负责「类 ⇄ JSON Schema ⇄ 校验」互转 |
| **JSON Schema** | 用 JSON 描述「一份 JSON 该长什么样」的标准 |
| **`**args`** | Python 字典解包。`F(**{"a":1})` 等价于 `F(a=1)` |

**本文主题相关**：

| 术语 | 含义 |
|---|---|
| **Structured Output** | 结构化输出。泛指让 LLM 返回可直接使用的数据结构的一切手段 |
| **Function Calling / Tool Use** | 模型按给定 JSON Schema 生成函数调用参数的能力。被挪用作结构化输出通道 |
| **JSON Mode** | 只保证输出是合法 JSON、**不保证符合 schema** 的 API 模式 |
| **Structured Outputs（严格模式）** | OpenAI 对「JSON Schema + 约束解码」的产品命名，`strict: true` |
| **Constrained Decoding** | 约束解码。采样前把违反文法的 token 概率置零 |
| **Grammar-based Sampling** | 约束解码的另一说法，强调基于形式文法 |
| **CFG** | 上下文无关文法。约束解码能处理的主要文法类 |
| **GBNF** | llama.cpp 的文法描述格式，BNF 变体 |
| **Token Healing** | 处理「文法定义在字符上、生成发生在 token 上」错位的技术 |
| **OutputParser** | LangChain 里把模型文本解析成对象的组件，对应 §3.1 |
| **Post-hoc Rationalization** | 事后编理由。reason 字段放在结论之后时发生的现象 |
| **CoT** | Chain-of-Thought，让模型把推理过程写出来以提升准确率 |
