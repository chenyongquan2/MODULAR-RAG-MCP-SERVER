# 01 · 概念：结构化输出在解决什么问题

> **前置**：[00 · 前置知识](00-prerequisites.md)
> **本章目标**：搞清楚这件事的边界（什么时候需要、什么时候不需要），以及最重要的一个心智工具——**三层可靠性**。
> **预计**：15 min

---

## 1. 鸿沟在哪

§00 §1 讲过，模型只会预测下一个 token，**输出永远是一串字符**。

而你的程序需要的是能直接参与运算的值：

```python
decision: Literal["keep", "drop", "borderline"]   # 要拿去做分支
confidence: float                                  # 要跟阈值 0.80 比大小
reason: str
```

> ⚠️ **这只是一个例子**（取自本项目预筛判定的形状），不是通用格式。schema 完全由任务决定：情感分类可能只要一个枚举值，实体抽取要 `list[Entity]`，意图路由要一个受限字符串。
>
> **普适的不是字段名，是「值有类型、无需解析即可使用」这件事。**

**「结构化输出」就是架在这道鸿沟上的桥。**

注意关键词是**可靠**。「让模型吐 JSON」谁都会写——在提示词里加一句就行。难的是「保证每一次都吐得出来、且吐对」。**整个话题的全部技术含量都在这两个字上。**

---

## 2. 什么时候不需要

先划边界，免得到处滥用。判据只有一条：

> **输出是给人看的，还是给代码看的？**

| 场景 | 下游 | 要不要结构化 |
|---|---|---|
| 聊天、摘要、翻译、改写 | 人 | **不要**。字符串就是最终产物 |
| 分类、抽取、评分、路由 | 代码 | **要**。字符串是障碍 |

本项目里的两条路径正好是对照：

- **`response_builder` 生成带引用的答案** → 给人读的，字符串**就是**产物。强行套 schema 只会削弱表达力，还会付出 §04 章讲的推理空间代价。
- **`testset_screener` 的判定** → 要跟 `keep_threshold` 比大小、决定路由。**这里字符串是障碍。**

**中间态**也很常见：一部分给人看、一部分给代码看。比如「答案正文 + 引用 chunk_id 列表」——照样用结构化输出，schema 里就是一个长文本字段 + 一个 id 数组。**字段内部可以装自然语言，两者不冲突。**

---

## 3. 三层可靠性（本章核心）

这是全专题最有用的一个心智工具。

「输出是对的」其实包含**三件独立的事**，越往下越难：

| 层次 | 要求 | 失败长什么样 | 谁能保证 |
|---|---|---|---|
| **① 语法合法** | 能被 `json.loads` 解析 | 少个括号 / 引号没转义 / 被截断 | **约束解码可 100% 保证** |
| **② 结构符合** | 字段齐全、类型正确、枚举值合法 | 返回 `{"结果": "相关"}`，字段名对不上 | 严格模式可保证 |
| **③ 语义正确** | 这个判断**本身**是对的 | `decision="keep"` 但实际该 drop | **没有任何机制能保证** |

### 3.1 为什么这个划分值钱

**因为后面四种方法的差异，只发生在 ① 和 ②。③ 永远是模型能力问题。**

```
      提示词      JSON Mode    假函数     约束解码
       ↓            ↓           ↓           ↓
①    ✗           ✓           ~✓          ✓✓✓      ← 方法之间的差异全在这两行
②    ✗           ✗           ~✓          ✓✓✓
─────────────────────────────────────────────
③    ?           ?           ?           ?        ← 全都一样，谁也保证不了
```

所以：

- **如果你的失败落在 ①/②** → 是工程缺陷，**可以被机制彻底清零**
- **如果落在 ③** → 换任何方法都没用，得治模型或输入

### 3.2 分不清会怎样

会出现这种误判：

> 「换了个更强的模型，失败率从 55% 降到 33%，说明新模型更聪明。」

**未必。** 更强的模型可能只是**更自觉地遵守格式**（① 层改善），判断力（③ 层）一点没变。你为「更聪明」付了钱，买到的其实是「更听话」。

本项目就有这个真实场景：换 judge 后 `context_precision` 的降级率从 26% 掉到 5%——这个改善**大概率发生在 ① 层**，而不是判断质量提升。详见 §05 章。

### 3.3 怎么在代码里分开

关键是**记录足够的归因信息**。最少这三样（§00 §3.2 讲过）：

```python
resp.choices[0].finish_reason         # "length" → ① 层，截断
resp.usage.completion_tokens          # 配合上一条判断是不是推理段吃光了
# 以及：解析失败时，原始文本长什么样
```

有了它们，「解析失败」就能拆成：

| 现象 | 属于 | 修法 |
|---|---|---|
| `finish_reason == "length"` | ① | 调大 `max_tokens` |
| `content` 空但烧了很多 token | ① | 同上（推理段吃光了） |
| 是完整 JSON，但字段名不对 | ② | 换更强的通道（§02 章） |
| 完全合规，但判断本身错 | ③ | 改提示词 / 换模型 / 治输入 |

**没有这层区分，你的所有优化都是盲改**——改完不知道为什么好了，也不知道为什么没好。

> 这是本专题最重要的一条实践建议，会在 §05 章看到它在本项目里缺失的代价。

---

## 4. 本章小结

| 问题 | 答案 |
|---|---|
| 结构化输出解决什么 | 让**本质是字符串**的输出，**可靠地**变成有类型的对象 |
| 什么时候不需要 | 下游是人的时候。字符串就是产物 |
| 三层是哪三层 | ① 语法合法 ② 结构符合 ③ 语义正确 |
| 方法之间差在哪 | **只差在 ① ②**。③ 谁都保证不了 |
| 最该做的一件事 | 记录 `finish_reason` / `usage`，让失败可归因 |
