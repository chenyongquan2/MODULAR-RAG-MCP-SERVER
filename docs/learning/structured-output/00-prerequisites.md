## 1. 模型是怎么生成一个 token 的

### 1.1 token 不是字

模型不认字，只认 **token** —— 一个由词表（vocabulary）定义的编号。词表通常有几万到几十万项。

```
"结构化输出"  →  可能被切成  ["结构", "化", "输出"]  →  [12043, 305, 8871]
"HistorySelectByLogins" → 可能被切成 ["History", "Select", "By", "Log", "ins"]
```

一个 token 可能是一个词、半个词、一个标点，甚至 `":` 这种**跨越语法边界**的组合。这一点在 §03 章讲约束解码时会变得很关键。

> 实用推论：**token 数 ≠ 字数**。中文大致 1 字 ≈ 1-2 token，英文 1 词 ≈ 1.3 token。估 `max_tokens` 时别按字数估。

### 1.2 模型的输出是一张打分表，不是一个词

这是全章最重要的一点。

一次**前向传播**（forward pass，就是把输入喂进神经网络算一遍），模型的输出是 **logits** —— **对词表里每一个 token 打一个分**：

```
输入: [12043, 305]          ← 已生成的 token 序列

        ↓ 前向传播

输出: logits，长度 = 词表大小
      token "输出" → 8.2
      token "过程" → 5.1
      token "的"   → 4.7
      token "{"    → -3.0
      ... （几万个）
```

**模型的工作到此为止。它不选词，它只是给出一张打分表。**

### 1.3 选词的是采样器，不是模型

拿着这张表挑一个出来，是**采样**（sampling）阶段的事，由推理程序完成：

```
   ┌─────────────────────────────────────────┐
   │ ①【模型权重】前向传播                    │
   │    输入 token 序列 → 全词表 logits       │
   │    ⚠️ 到此为止。它不选词。               │
   └──────────────────┬──────────────────────┘
                      │ logits
   ┌──────────────────▼──────────────────────┐
   │ ②【采样器】拿着打分表挑一个              │
   │                                         │
   │    temperature  ← 把分数拉平还是拉尖     │
   │    top_p / top_k ← 只在前几名里挑        │
   │    语法约束      ← 把违规 token 划掉 ❗  │
   │                    （§03 章的主角）      │
   │                  ↓                      │
   │              选出 "输出"                 │
   └──────────────────┬──────────────────────┘
                      │ 拼回序列，回到 ①
                      └──── 循环 ────
```

**`temperature` 你早就在用了**（本项目 `settings.yaml` 里就配着），它就住在第 ② 框里：

- `temperature=0` → 永远选分数最高的那个（确定性最强）
- `temperature=1` → 按原始概率随机挑
- `temperature=2` → 把分数拉平，冷门 token 也有机会（更「有创意」，也更容易胡说）

> **记住这个位置。** §03 章会说「约束解码住在服务层」—— 意思就是它和 `temperature` 是邻居，都在第 ② 框，跟模型权重无关。

## 2. 自回归：一次一个，循环到底

§1.3 那个循环有个名字：**自回归**（autoregressive）。

### 2.1 名字是什么意思

拆开看：

| 字 | 含义 |
|---|---|
| **自**（auto-） | 「用自己的」—— 用自己**已经产出**的东西 |
| **回归**（-regressive） | 统计学术语，这里就是「预测」 |

合起来：**用自己已经产出的内容，来预测下一个内容。**

这个词借自时间序列的自回归模型 **AR(p)** —— 用一个序列**自身的历史值**预测它的未来值（比如用过去 7 天的气温预测明天）。LLM 是同一个结构，只不过序列是 token，历史值是它自己刚写下的字。

> **一句话**：模型写下的每个 token，下一步都会变成它自己的输入。

<details>
<summary><b>📎 插话：「回归」这个词到底什么意思（它的名字是个历史事故）</b></summary>

<br>

**词源。** 1886 年 Francis Galton 研究遗传身高，发现高个父母的孩子倾向于比父母矮、矮个父母的孩子倾向于比父母高——后代身高总往人群平均值靠。他把这叫 *regression toward mediocrity*（向平庸**回归**）。为描述它，他画了一条拟合直线。

后来大家发现「拟合一条线来预测」这方法很有用，于是**方法沿用了现象的名字**。

**所以「回归」二字描述的是那个身高现象，不是这个方法。** 现代统计里的「回归」跟「回到平均」已经毫无关系。

**它现在的意思**，就一句话：**用已知的量，预测一个连续的数值。** 关键是它的对立面：

| | 预测什么 | 例子 |
|---|---|---|
| **回归** regression | **连续数值** | 房价、气温、`confidence: 0.95` |
| **分类** classification | **离散类别** | `keep`/`drop`/`borderline`、是否垃圾邮件 |

**你会遇到的几个「回归」**：

| 术语 | 实际含义 | 跟「回到平均」有关吗 |
|---|---|---|
| 线性回归 | 用直线拟合、预测数值 | ❌ 历史遗留 |
| 逻辑回归 | **其实是分类器**（输出概率再卡阈值） | ❌ 名字最骗人的一个 |
| 自回归 | 用序列**自身历史值**预测下一项 | ❌ |
| **回归测试** | **完全不同的词**：检查新代码有没有让老功能**退步** | ❌ 用的是 regression 的英文本义「倒退」 |

⚠️ 最后一行要特别注意——本项目里两种意思都会碰到：`pytest tests/unit` 的**回归测试**、以及 §04 §5 说的「探针纳入定期回归」，用的都是「**倒退**」那个意思，和统计学的 regression **只是碰巧同一个英文单词**，中文又碰巧都译成「回归」。没有任何关系。

**最后一个坑**：严格说，LLM 每步做的其实是**分类**（在几万个 token 里选一个），不是回归。「自回归」继承的是 AR 模型的**结构**（用自身历史预测下一项），不是它的输出类型。

> 所以如果你觉得「自回归」这名字看起来不太对——**你的直觉是准的。**

</details>

### 2.2 具体走一遍

假设模型要生成 `{"reason": "OK"}`。真实过程是这样的（token 切分做了简化）：

| 步 | 模型这一步的**输入**（= prompt + 已生成的全部） | 输出的 token |
|---|---|---|
| 1 | `判定这条用例...` | `{` |
| 2 | `判定这条用例...` + `{` | `"reason"` |
| 3 | `判定这条用例...` + `{"reason"` | `:` |
| 4 | `判定这条用例...` + `{"reason":` | `"OK"` |
| 5 | `判定这条用例...` + `{"reason": "OK"` | `}` |
| 6 | `判定这条用例...` + `{"reason": "OK"}` | `<结束>` |

**盯着第二列看**：它每一步都在变长，而变长的部分**正是模型自己上一步吐出来的东西**。

这就是「自回归」四个字的全部含义。

### 2.3 三个关键性质

**性质一：prompt 和模型自己的输出，在模型眼里是同一个东西。**

第二列里的「`判定这条用例...`」（你写的）和「`{"reason"`」（它自己写的）**没有任何区别**——都只是「已有的 token 序列」。模型不知道哪部分是谁写的。

> **这条是理解 CoT（让模型「先想再答」）为什么有效的钥匙**：模型写下的推理过程，下一步就成了它自己的输入，它真的能「看着自己的分析」继续往下写。不是比喻，是机制。

**性质二：每生成一个 token，都是一次完整的前向传播。**

生成 100 个 token = 把模型跑 100 遍。这解释了两件你早就观察到的事：

- **输出比输入贵**：处理 prompt（prefill）可以一次并行算完，生成（decode）必须一个一个串行来
- **长回答慢**：慢在 token 数，不在字符数

> 实际实现会用 KV cache 等手段避免重复计算前面 token 的中间结果，所以没有「100 次全量重算」那么夸张——但**串行这一点无法优化掉**。

**性质三：不能反悔。**

没有回溯机制。第 3 步吐了个 `:`，第 5 步发现不该有——**改不了**，因为第 4 步已经基于它生成了。

模型只能将错就错地往下写。

### 2.4 三个推论

**推论 A：字段顺序有意义。**

JSON 对象在规范上是无序的，但**生成顺序**严格有序（§2.2 那张表）。配合性质一：

```python
class ScreeningVerdict(BaseModel):
    reason: str      # ← 先写
    decision: str    # ← 后写。写它时 reason 已经在输入里了，能"看着自己的分析"下结论
```

反过来 `decision` 在前，就变成**先拍板、再编理由**——`reason` 对 `decision` 的质量零贡献。

**字段一模一样，判断质量可能差很多。这不是风格问题，是能力问题**（§04 章展开）。

**推论 B：截断永远可能发生。**

生成是一个一个往外蹦的，随时可能因为达到 `max_tokens` 而停在半路。而停在半路的 JSON **一定语法非法**（少个 `}` 就废了）。

> 这条是本项目历史上最贵的一课，见 §4 和 §05 章。

**推论 C：任何格式约束都必须在「采样之前」介入。**

由性质三推出：token 一旦被采出来就改不了了。所以**不存在「生成完再修正」这种方案**——那时后续 token 早就基于错误内容生成了。

想保证格式，唯一的位置就是 §1.3 那个第 ② 框，**在挑词之前把违规选项划掉**。

> 这就是 §03 章「约束解码」的立足点。先记住这个位置，那一章会顺理成章。

## 3. 一次 API 调用的完整形状

后面所有代码示例都是这个形状，先把每个字段认全。

### 3.1 请求

```python
resp = client.chat.completions.create(
    model="z-ai/glm-5.2",                       # 模型标识
    messages=[{"role": "user", "content": "..."}],  # 对话历史
    temperature=0.0,                            # 采样参数（§1.3）
    max_tokens=3000,                            # 最多生成多少 token，防跑飞

    # ↓ 下面两个是本专题的主角，§02 章详解。现在只需知道它们存在
    response_format={...},                      # 要求返回特定格式
    tools=[...], tool_choice={...},             # 提供"可调用的函数"清单 + 强制策略
)
```

### 3.2 响应

```python
resp.choices[0].message.content       # 模型说的话（字符串，可能是 None）
resp.choices[0].message.tool_calls    # 模型想"调用"的函数（列表，可能是 None）
resp.choices[0].finish_reason         # 为什么停下来  ← 最容易被忽略、最该看
resp.usage.prompt_tokens              # 输入烧了多少 token
resp.usage.completion_tokens          # 输出烧了多少 token
```

### 3.3 `finish_reason` 的取值

| 取值 | 含义 | 你该怎么办 |
|---|---|---|
| `"stop"` | 模型自己认为说完了 | 正常 |
| `"length"` | **撞上 `max_tokens` 被硬切断** | 调大 `max_tokens`。内容一定不完整 |
| `"tool_calls"` | 模型选择"调用函数"而不是说话 | 去 `message.tool_calls` 里取 |
| `"content_filter"` | 被内容过滤拦了 | 换措辞 |

> ⚠️ **`finish_reason` 是排障的第一现场，但绝大多数代码不看它。**
>
> 不看它的后果很具体：解析失败时，你**分不清**「模型格式没遵守」和「模型写到一半被切断」。这两者的修法完全相反——前者要改提示词，后者要调 `max_tokens`。猜错方向就会改一整天没效果。本项目真实发生过（§4）。

## 4. 推理型模型与 reasoning tokens

### 4.1 现象

近年的模型（GLM-4.5+、DeepSeek-R1、o 系列等）在正式回答前会先「想」一段。这段思考**同样消耗 completion token**，但**通常不出现在 `content` 里**。

于是你会遇到一个看起来毫无道理的结果：

```python
resp.choices[0].message.content   # ''  ← 空字符串
resp.usage.completion_tokens      # 854 ← 烧了 854 个 token
```

**烧了 854 个 token，一个字都没返回。**

### 4.2 原因

推理段把 `max_tokens` 预算吃光了，轮到写可见内容时已经没额度了：

```
max_tokens = 800
├── 推理段（不可见）   849 token   ← 超了，在这里就被切断
└── 可见 content         0 token   ← 一个字都没轮到
```

### 4.3 本项目实测数据【实测】

2026-08-16，探针脚本 [`probe_structured_output.py`](../../../scripts/dev/probe_structured_output.py)：

| 模型 | 总输出 token | 其中推理段 | 可见内容 |
|---|---|---|---|
| `z-ai/glm-5.2` | 500 | 429 | **71** |
| `z-ai/glm-5.2-free` | 854 | 849 | **5** |
| `minimax/minimax-m2.7` | 604 | 523 | 81 |

**推理段占 85–90%。**

### 4.4 这条为什么重要

本项目 [`config/settings.yaml`](../../../config/settings.yaml) 里曾把标注模型的 `max_tokens` 硬编码为 **200**。结果是「367 字符的 chunk 就返回空响应」，当时的诊断是「模型不遵从 JSON 格式」。

**真实原因**：200 个 token 全被推理段吃光，可见内容一个字都没轮到。**表象和「模型不听话」一模一样，但修法完全不同。**

> **实用规则**：对推理型模型，`max_tokens` 的安全值 ≈ **你预期可见输出长度的 5–10 倍**。
>
> 想知道某个模型烧多少推理段，就看 `usage.completion_tokens_details.reasoning_tokens`（部分端点提供）；拿不到就用 `completion_tokens - len(content) 的 token 估算` 反推。

## 5. JSON / JSON Schema / pydantic

这三个词在深文里高频出现且经常挨在一起，但它们是三层不同的东西。

### 5.1 三者关系

```
  ┌────────────────────────────────────────────────────────┐
  │ pydantic BaseModel      —— Python 里定义 + 校验的工具   │
  │                                                        │
  │   class ScreeningVerdict(BaseModel):                   │
  │       decision: Literal["keep", "drop"]                │
  │       confidence: float                                │
  └───────────────────────┬────────────────────────────────┘
                          │ .model_json_schema()  一键导出
                          ▼
  ┌────────────────────────────────────────────────────────┐
  │ JSON Schema             —— 描述「合法 JSON 长什么样」    │
  │                            它本身也是一段 JSON          │
  │   {"type": "object",                                   │
  │    "properties": {                                     │
  │       "decision": {"enum": ["keep", "drop"]},          │
  │       "confidence": {"type": "number"}},               │
  │    "required": ["decision", "confidence"]}             │
  └───────────────────────┬────────────────────────────────┘
                          │ 约束
                          ▼
  ┌────────────────────────────────────────────────────────┐
  │ JSON                    —— 具体的一份数据               │
  │   {"decision": "keep", "confidence": 0.95}             │
  └────────────────────────────────────────────────────────┘
```

一句话记忆：

| | 是什么 | 类比 |
|---|---|---|
| **JSON** | 一份具体数据 | 填好的表格 |
| **JSON Schema** | 描述「什么样的数据算合法」，本身也是 JSON | 空白表格 + 填写说明 |
| **pydantic** | Python 库：定义结构、校验数据、导出 JSON Schema | 印表格的机器 |

### 5.2 为什么需要 JSON Schema

因为你要**把「我想要什么形状」告诉一个远程 API**。总不能发一段中文过去说「给我一个有 decision 和 confidence 的对象」——JSON Schema 就是这件事的机器可读格式。

后面 §02 章你会看到：不管走哪条通道，最终发过去的都是一份 JSON Schema。

### 5.3 pydantic 最少必要知识

> **关于 `ScreeningVerdict` 这个名字**：verdict 是英文「裁决 / 判定」（本是法庭术语，陪审团给出的裁定），这里指「对一条金标用例的判定结果」。
>
> **它是本项目真实存在的类** —— [`testset_screener.py:115`](../../../src/observability/evaluation/testset_screener.py#L115)，字段是 `case_index` / `decision` / `confidence` / `reason`。本专题的示例做了简化（去掉 `case_index`），但形状一致。
>
> ⚠️ 注意区分两件事：**类名本身对 API 没有意义**（发过去的只是一个字符串标签，叫 `Foo` 一样能跑，见 §02 §3.3）；但**这个类在你的代码里是真实的下游消费者**，`decision` 用来三路分流、`confidence` 用来卡阈值。见 §05 §1。

```python
from typing import Literal
from pydantic import BaseModel, Field

class ScreeningVerdict(BaseModel):
    reason: str
    decision: Literal["keep", "drop", "borderline"]   # 只能是这三个值之一
    confidence: float = Field(ge=0.0, le=1.0)         # 必须在 [0,1]

# 用法一：从 dict 构造，顺便校验
v = ScreeningVerdict(reason="上下文支持", decision="keep", confidence=0.95)
v.decision            # "keep"，可以用属性访问

# 用法二：非法数据当场抛异常，不会流进下游
ScreeningVerdict(reason="x", decision="maybe", confidence=0.95)   # ← ValidationError

# 用法三：导出 JSON Schema，发给 API
ScreeningVerdict.model_json_schema()
```

**校验（用法二）是它最大的价值**：脏数据在边界就被挡住，而不是在三层调用之后以某个诡异的方式炸掉。

## 6. Python 的 `**` 字典解包

深文的代码里频繁出现 `ScreeningVerdict(**args)`，这不是什么特殊语法，就是 Python 的字典解包：

```python
args = {"reason": "上下文支持", "decision": "keep", "confidence": 0.95}

ScreeningVerdict(**args)
# 完全等价于
ScreeningVerdict(reason="上下文支持", decision="keep", confidence=0.95)
```

`**` 把 dict 的每个键值对拆成关键字参数。仅此而已。

配合 §5，`ScreeningVerdict(**args)` 这一行做的是：**把一个普通 dict 变成有类型、已校验的对象**。

> ⚠️ 常见误解：`ScreeningVerdict(**args)` 看起来像「调用一个函数」，其实是**构造一个对象**（`ScreeningVerdict` 是类不是函数）。这个混淆在 §02 章讲「假函数」时会造成很大困扰，先记住区别。

## 7. 模型、推理服务器、网关

最后一块，本项目特有但绕不开。

### 7.1 模型不是程序，是一堆数字

模型权重就是个文件——几十上百 GB 的浮点数。它自己什么都干不了，像一个 `.mp4` 文件。

**推理服务器**（vLLM、llama.cpp、各家自研）才是真正运行的程序：加载权重、算 §1 那个前向传播、跑 §1.3 那个采样、暴露 HTTP 接口。

> 模型是视频文件，推理服务器是播放器。**倍速播放的能力在播放器里，不在视频文件里。**

**关键推论**：§1.3 第 ② 框里那些能力（`temperature`、`top_p`、语法约束）**全部由推理服务器实现**。同一份模型权重换个服务栈，可能有也可能没有——权重一个字节都不用变。

### 7.2 你的请求要过几道手

本项目用的是 OpenAI 兼容端点，链路是这样的：

```
你的代码
   │  response_format / tools / max_tokens ...
   ▼
兼容端点（网关，本项目的 GLM_BASE_URL）    ← 会不会把参数吃掉？
   │
   ▼
上游 provider                             ← 会不会？
   │
   ▼
推理服务器                                 ← 有没有实现这个能力？
   │
   ▼
模型权重（如 claude / minimax / glm）
```

**这条链上任何一跳丢了参数，最终结果都是「没生效」，而且通常不报错。**

所以下面这个推理是**不成立**的：

> ~~「官方文档说这个模型支持 X」→「我这个网关支持 X」~~

CLAUDE.md 里记着「模型下架是这个网关的常态」，说的是同一件事：**这个网关的行为不能靠上游文档推定，只能实测。**

### 7.3 静默失效

兼容端点最典型的失效方式是**静默的**：

- 参数被接受（HTTP 200，无报错）
- 但被忽略
- 返回一段普通文本

**你唯一能察觉的方式是校验返回结构本身**，而不是看有没有报错。这一点在 §05 章会看到真实案例。
