## 1. 现状：四处判定全在最底一档

【代码】全仓解析 LLM 输出的地方，**没有一处使用任何 API 级保证机制**：

| 位置 | 做法 |
|---|---|
| [`testset_screener.py:438`](../../../src/observability/evaluation/testset_screener.py#L438) | 剥 markdown 围栏 → 截取 `{...}`。**写得最严谨的一处** |
| [`chunk_labeler.py:482`](../../../src/observability/evaluation/chunk_labeler.py#L482) | 同上 **+ 裸数字正则兜底**（见 §5） |
| [`_ragas_wrappers.py:112`](../../../src/observability/evaluation/_ragas_wrappers.py#L112) | 交给 RAGAS 0.1.21 内部解析 |
| `testset_synthesizer.py` | `json.loads` |

**三条独立证据**：

1. `_extract_json_object` 这段容错代码**存在本身**就是证据——走了 §02 §2-4 任何一条通道，这些偏差在 API 层就不会发生。
2. 提示词里写的是 `Respond with STRICT JSON only — no markdown fences`。**提示词里的「STRICT」是请求，不是约束**；真正的 strict 是 API 参数里那个 `"strict": true`。
3. `_ragas_wrappers.py` 把项目 LLM 包成 `langchain_core.language_models.llms.LLM`——这是**文本补全型**基类，只有 `_call(prompt) -> str`，**没有 `bind_tools`**。也就是说 judge 路径的假函数通道**在接口层就走不通**，不是「没选」，是「没得选」。

## 2. 探针怎么设计的（方法本身值得学）

### 2.1 必须用「诱导违规」的提示词做对照

单看一次成功的输出，**无法区分「模型自愿遵守」和「被约束强制」**。所以每种模式跑两个提示词：

- `neutral` —— 正常判定请求
- `adversarial` —— 额外要求「先用两三句散文解释思路，再给判定」

真正的约束解码在 adversarial 下**物理上吐不出散文**；只是自愿遵守的模型会破功。**这一对的差异才是判据。**

### 2.2 必须抓 `finish_reason` 和 `usage`

首轮探针没抓，于是满屏「空响应」**无法归因**——分不清是截断、是推理段吃光预算、还是真的返回空。

> **这正是 §01 §3.3 反复讲的错误，我在探针里原样犯了一遍。** 加上这两个字段后，首轮那批「空响应」全部查明是 `max_tokens=800` 给少了。

### 2.3 分类必须看 HTTP 状态码，不能匹配错误文本

首轮还有一条 **429 限流**，因为错误消息里碰巧含关键词，被字符串匹配误判成 `REJECTED`（「该模型不支持 json_schema」）。

**把「网关现在忙」读成了「网关没这个能力」，结论完全相反。**

## 3. 结果

| 模型 | 用途 | 提示词 | JSON Mode | json_schema | tools |
|---|---|---|---|---|---|
| `z-ai/glm-5.2` | 答案生成 | 围栏/夹带 | OK | **OK** | **OK** |
| `minimax/minimax-m2.7` | judge | 围栏/夹带 | OK | **429，无结论** | **OK** |
| `z-ai/glm-5.2-free` | 预筛 / 标注 | 围栏/夹带 | 返回 list | **OK** | **OK** |

### 发现一：提示词方案六战六败

三模型 × 两提示词，**没有一次产出纯 JSON**——全是 markdown 围栏或前后夹带文字。

**项目当前路径每一次调用都在靠容错解析兜底，不是偶发。**

### 发现二：这个网关上 `tools` 比 `json_schema` 更可靠

**与 §04 §4 决策树的通用排序相反**：

| 通道 | 覆盖 | 备注 |
|---|---|---|
| `tools` | **3/3 模型、6/6 次调用全过**，零限流 | |
| `json_schema` | 2/3 模型有结论 | judge 用的 minimax 三次尝试 1 成功 2 限流 |

而且 `tools` 在 minimax 上**又快又省**：3.0 秒 / 76 token，对比 JSON Mode 的 14.9 秒 / 579 token——**快 5 倍、省 87%**。

> 这是 §03 §2 推论 C（能力住在服务层）的实例：**上游模型支持什么，推不出你这条链路上什么最可靠。** 通用建议在这个网关上被实测推翻——这不说明通用建议错，说明**必须实测**。

### 发现三：推理 token 占 85–90%

| 样本 | 总输出 | 其中推理 | 可见内容 |
|---|---|---|---|
| `z-ai/glm-5.2` | 500 | 429 | **71** |
| `z-ai/glm-5.2-free` | 854 | 849 | **5** |

这精确解释了项目历史上那次误诊（§00 §4.4）：`max_tokens=200` 的失效不是「余量不够写完」，而是**200 个 token 全被推理段吃光，一个字都没轮到可见内容**——所以返回的是彻底的空字符串，而不是半截 JSON。

## 4. `degraded_case_count 54.8%` 的归因困境

CLAUDE.md 记录的 `degraded_case_count: 23/42 = 54.8%`（远超 SC-006 所定 ≤5% 门槛），按 §01 §3 的三层拆开，混着两类原因：

| 原因 | 属于 | 能否消除 |
|---|---|---|
| judge 输出被截断 / 转义炸了 / 带了围栏 | ① 语法 | **能，且可清零** |
| judge 真的判不出来（英文问题产出中文答案等） | ③ 语义 | 不能，得治输入侧 |

**当前架构下这两者分不开**——`_extract_json_object` 返回 `None` 时不区分原因。

### 两个当前配置的具体风险【代码】

**① `labeling_llm.max_tokens: 800` 余量偏薄。**

[settings.yaml:319](../../../config/settings.yaml#L319) 的注释说「800 下全部完整且解析成功」（2026-08-13 在真实 chunk 上测的），但探针在**同一模型**（`z-ai/glm-5.2-free`）的可比任务上，中性提示词就消耗了 **786** 个 completion token——**98% 的利用率**。

> ⚠️ 限定：786 来自「预筛一条金标用例」，prompt 比「给一个 chunk 打分」长；探针里那个 854 来自**故意诱导写散文**的对抗提示词，不代表真实负载。
>
> 所以这是**余量风险，不是已发生的失效**。但 `max_tokens` 是上限不是配额，调高不产生额外成本，没有理由卡在 98%。

**② 一条被否证的假设——`judge_llm` 的 `max_tokens`。**

本章早期版本曾把「给 judge 配 `max_tokens`」列为优先级 1。**这条是错的，项目此前已经否证过**：

- 【代码】`_ragas_wrappers.py` 注释：「judge 路径**刻意不传** max_tokens……T-3.1 归因否证了这条：**595 次成功判定调用零空响应**，最长响应 3378 字符」
- 【代码】`JudgeLLMSettings` **没有 `max_tokens` 字段，是刻意省略**——加一个不解决问题的配置项就是下一个死配置
- CLAUDE.md 完整归因（42 条冻结元组）：14 条真实失败**全部**是「英文问题 + 中文答案」，语言一致的 14 条**零失败**。**病因在输入侧**

> **教训**：探针测出「推理段占 85–90%」是真的，但**从「机制上可能」跳到「就是它」少了一步**——而那一步项目里早有结论。**新证据不自动作废旧归因。**
>
> 这正是 §01 §3 讲的错误：把 ① 层的一个**可能性**，误当成 ③ 层已知病因的替代解释。

## 5. 一处独立风险：`chunk_labeler` 在猜

【代码】[`chunk_labeler.py:474`](../../../src/observability/evaluation/chunk_labeler.py#L474) 在 JSON 解析全部失败后还有一层兜底：

```python
# 裸数字兜底：取第一个 0-3 的独立数字
match = re.search(r"\b([0-3])\b", text)
```

**这不是「解析失败就降级」，是「猜」。** 模型回一句「这段和问题有 2 处关联，但相关度我判不了」——会被解析成 `grade=2`。

而 [`testset_screener.py:441`](../../../src/observability/evaluation/testset_screener.py#L441) 的注释写的是相反原则：

> 但**不**从数组内部挖对象 —— 宁可降级为 borderline 也不猜测其意图

**同一个项目里，两处对「拿不准怎么办」的态度是相反的。** screener 那条才是对的——猜出来的标注会静默污染金标，而**金标是所有评估结论的地基**。

## 6. 符不符合最佳实践

**通道选择：不符合。** 四处全在最底一档，而实测证明至少两条更好的路可用。

**生产纪律（§04 §5 那八条）：一半符合，符合的那部分质量不错**——这点要给项目公道：

| 纪律 | 现状 |
|---|---|
| 1 二次校验 | ✅ `_coerce_confidence` 校验 [0,1] 且排除 bool |
| 2 不炸整批 | ✅ 降级 borderline / `judge_failed`，不抛异常 |
| 3 **失败可归因** | ❌ **最大缺口** |
| 4 max_tokens | ⚠️ labeling 800，实测中性提示词已用 786（98%）。judge 不传是**刻意且已否证** |
| 5 检查 tool_calls | — 不适用（未走 tools） |
| 6 探测纳入回归 | ❌ 无 |
| 7 reason 放最前 | ❌ 提示词里 `reason` 在**最后** |
| 8 拿不准就降级 | ⚠️ screener ✅ / chunk_labeler ❌ |

## 7. 差距清单（按性价比排序）

| 优先级 | 动作 | 成本 | 收益 |
|---|---|---|---|
| **1** | `labeling_llm` 800 → 3000（judge **不要**动，见 §4 ②） | 改 1 行配置 | 消除标注路径余量风险。**不影响 `evaluate.py`** |
| **2** | 判定失败时记录 `finish_reason` / `usage`，区分截断与格式非法 | 约 20 行 | **让后续所有优化可被验证** |
| 3 | 提示词字段顺序 `reason` 提到最前 | 改提示词 | ③ 层可能改善，需对照验证 |
| 4 | 去掉 `chunk_labeler` 裸数字兜底，改为显式 `judge_failed` | 删 3 行 | 消除静默错标 |
| 5 | 判定路径改走 `tools` 通道 | 需动 `BaseLLM` 抽象 | 消灭 ① 层失败，minimax 上省 87% token |
| 6 | 探针纳入定期回归 | 已有脚本 | 防间歇性静默失效 |

> **2 是这份清单里唯一的关键路径。**
>
> `degraded_case_count 54.8%` 的病因已归因清楚（输入侧的语言错乱），**不是 `max_tokens`、不是通道**——所以 1 和 5 都不会显著改善它。
>
> 而 2（失败可归因）是**唯一能让后续任何改动被验证**的前置。先做它。

## 8. 学完本专题你应该能做的事

- [ ] 拿到一个「LLM 返回解析失败」的报错，判断它属于 ①/②/③ 哪一层
